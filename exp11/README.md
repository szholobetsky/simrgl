# exp11 — триангуляція на 20 останніх задачах, код як він є сьогодні

**Питання.** Що повертають simargl, gamayun і svitovyd для найсвіжіших задач, якщо git не
відкочувати, і як ці відповіді правильно читати?

**Постановка.** 20 задач sonar.db з найпізнішими комітами (21–25.10.2024). Кожен інструмент бачить
лише минуле:
- **simargl**: індекс усіх задач, але ці 20 не голосують (клас `Simargl` з exp10, сортування freq);
- **gamayun**: онтологія `out/sonar_latest`, побудована без цих 20. Це `exp7/build_onto.py` з
  часовим поділом замість modn: кожна задача онтології старша за кожну відкладену. Параметри взято з exp9;
- **svitovyd**: карта сьогоднішнього репозиторію, `graph.files_for_text`, тобто рівно те, що
  викликає сторінка «Триангуляція» в simargl.

Шляхи з історії (відповіді й істина) читаються через сьогоднішню карту, як в UI: шлях, якого вже
немає, стає єдиним файлом сьогоднішнього коду з такою самою назвою. Злиття — RRF з рівними вагами,
k = 60.

```
python build_onto.py   # out/sonar_latest/   (~1 хв)
python run.py          # out/runs.json       (~25 с)
python analyze.py      # out/analysis.json, звіт: out/report.txt
python kw.py           # svitovyd через слова → runs.json (lists.svitovyd_kw, fused_kw)
python analyze.py kw   # out/analysis_kw.json, звіт: out/report_kw.txt
python validate_exp10.py  # та сама формула на 200 задачах exp10
```

## Що виявилось про сам код

Задачі «останні» лише в базі. Репозиторій витягнуто до 2026-10-02, на два роки пізніше, і за цей
час з нього винесли весь фронтенд `server/sonar-web/**` (ts, tsx, css).
- Сьогоднішнє дерево має 8 475 файлів, карта svitovyd покриває з них 8 189.
- Без масової задачі SONAR-23206 (2 203 файли) задачі змінили 668 файлів. Java-файли здебільшого
  на місці (344 з 401, 86 %); жодного ts/tsx/css у дереві немає.
- 3 задачі суто фронтендові (SONAR-23232, 23469, 23475). Сьогодні їх не розв'яже жоден інструмент:
  файлів більше немає в цьому репо.
- Переміщених файлів (та сама назва в новому місці) знайшовся лише 1.

Отже, гіпотеза «свіжі задачі → мало змін у коді» справджується для бекенду і хибна для того, що
переїхало в інший репозиторій.

## Результати (16 задач, де хоч один файл ще існує; масова SONAR-23206 окремо)

| | hit@10 | P@10 | R@10 (досяжних) | MRR |
|---|---|---|---|---|
| simargl | 0.69 | 0.14 | 0.28 | 0.42 |
| gamayun | 0.69 | 0.15 | 0.32 | 0.37 |
| svitovyd | 0.06 | 0.04 | 0.03 | 0.03 |
| **RRF усіх трьох** | **0.75** | 0.14 | 0.31 | **0.44** |

Злиття знову краще за кожен інструмент окремо, як і в exp10 (0.62 → 0.755 на 200 задачах).
Тут вибірка мала: одна задача — це 0.06 hit@10.

**Як читати відповідь: згода — це впевненість.** Влучність файлу з топ-10 залежить від того, скільки
інструментів його назвали (19 задач без масової):

| хто назвав | влучних |
|---|---|
| усі три | 1 / 2 |
| двоє (S+G) | 7 / 18 = 0.39 |
| лише один | 31 / 356 = 0.09 |

Те саме видно на рівні задачі. Коли файл №1 злиття підтримують два інструменти, він правильний у 5
з 11 задач. Коли його назвав лише один — у 0 з 6. Тож згоду можна прямо показувати як позначку
впевненості. Якщо жоден файл не має згоди, відповідь краще подавати як «не знаю», а не як ранжований
список.

**Застереження: хаби.** `sonar-core/.../l10n/core.properties` потрапляє в топ-10 simargl або
gamayun у 15 з 19 задач і влучає в 5 з них. За ним ідуть `build.gradle` (2 з 8), `pom.xml` (0 з 7),
`sonar-application/.../sonar.properties` (0 з 6). Частина згоди S+G — це згода на хабах. Якщо
прибрати файли, що трапляються в ≥ 5 задачах, згода дає 2/8 = 0.25 проти 27/294 = 0.09 для одного
інструмента. Різниця лишається, але вибірка крихітна. Хаб варто показувати окремо (як «чорні діри»
в simargl), а не як аргумент згоди.

**svitovyd на назвах задач майже німий.** У 19 задачах лише 5 мали хоч один ідентифікатор. Здебільшого
це `SonarQube`: назва продукту, яку визначає випадковий файл (`DbPrimaryKeyConstraintFinderIT`), тож
вона веде в шум. Спрацювала одна задача, SONAR-23461 з `TelemetryData` та `TelemetryDataJsonWriter`.
Там усі три інструменти зійшлися, і злиття поставило правильні файли на 2 і 3 місця. Висновок:
svitovyd корисний як сильний, але рідкісний сигнал. Йому потрібен фільтр загальних слів (назва
продукту, ідентифікатори з високою df у текстах задач), а таку df знає лише історія, тобто simargl
або gamayun.

**Типи задач, які ніхто не знаходить.**
- Задачі про поведінку без назв: «Rules indexing is not happening consistently», «Scanning alerts
  must work in both STANDARD and MQR mode». Інструменти дають сусідні файли тієї самої теми
  (`RuleDao`, `IssueMapper`), але не ті.
- Задачі, чий код переїхав.
- CODEFIX-75 без назви й опису (порожній текст).

## svitovyd через слова задачі (`kw.py`)

Ідея з `svitovyd keywords extract -f`: слова задачі спочатку стають ідентифікаторами коду, і лише
потім файлами. Слово «telemetry» розгортається в TelemetryData, TelemetryDataJsonWriter і так далі.
Порівняння те саме, що в svitovyd (`_split_identifier`, підслова ≥ 5 літер), але проти ідентифікаторів,
які карта **визначає**. Кожне слово голосує за файли, що визначають його ідентифікатори:

    score(file) = Σ_w  log(N / files(w)) · log(T / (1 + tasks(w)))

- files(w) — у скількох файлах визначено ідентифікатор зі словом w. Слово, яке трапляється в більш
  ніж 2 % файлів, пропускається.
- tasks(w) — у скількох минулих задачах трапляється слово (sonar.db без цих 20).

Другий множник додано після першого прогону. З одним лише першим вели «because», «their»,
«between»: кожне з них є в ідентифікаторах одного файлу, зате в кожній десятій задачі. Рідкісне в
коді ≠ доречне. Слово має бути рідкісним і в коді, і в звичайній англійській трекера. Тепер угорі
стоять Scopes, Qualifiers, TelemetryDataJsonWriter, RuleRegistrant, search_gitlab_repos, liveness.

**20 останніх задач** (`python analyze.py kw` → `out/report_kw.txt`; 16 задач із досяжними файлами):

| | hit@10 | MRR |
|---|---|---|
| svitovyd (ідентифікатори) | 0.06 | 0.03 |
| svitovyd (слова) | 0.50 | 0.21 |
| RRF S+G+V (ідентифікатори) | 0.75 | 0.44 |
| RRF S+G+V (слова) | **0.88** | **0.53** |

Ці числа оптимістичні: форму ваги змінено вже після того, як я подивився на ці задачі. Тому та сама
формула без змін пройшла 200 тестових задач exp10 (`validate_exp10.py`). Там задачі 2014–2024 років,
а svitovyd дивиться на сьогоднішній код, тож окремо пораховано 72 задачі, у яких хоч один файл ще
існує:

| 72 «живі» задачі exp10 | AP | MRR | hit@10 |
|---|---|---|---|
| svitovyd, ідентифікатори | 0.025 | 0.053 | 0.083 |
| svitovyd, слова | 0.029 | 0.092 | 0.236 |
| RRF S+G | 0.277 | 0.558 | 0.889 |
| RRF S+G+V (ідентифікатори) | **0.296** | **0.592** | 0.889 |
| RRF S+G+V (слова) | 0.278 | 0.569 | **0.917** |
| RRF S+G+V+V (обидва) | 0.291 | 0.584 | **0.917** |

Слова знаходять щось у втричі більшій кількості задач, але їхні верхні позиції шумніші. Ідентифікатори
трапляються рідко, зате коли трапляються, то точні. Варіант «обидва» тримає майже ту саму точність, що
й ідентифікатори, і охоплення слів. Утім, одна задача тут — це 0.014, тож різниці між трьома
злиттями лежать у межах шуму. Головний ефект на 20 останніх задачах (0.75 → 0.88) на ширшій вибірці
не підтвердився такою самою силою. Це «інший вимір», який допомагає в простих випадках, як і очікувалось.

## Перевірка на flink: 10 останніх задач (формула з sonar, без змін)

Задачі, яких я не бачив, поки правив формулу. Шлях той самий: `proj.py` — шляхи проєкту,
`python build_onto.py flink`, `run.py flink`, `kw.py flink`, `analyze.py [kw] flink`; результати в
`out/flink/` (`report.txt`, `report_kw.txt`).
- Онтологія gamayun побудована з 16 963 задач (без цих 10). Підібраних параметрів gamayun для flink
  немає, тож узято стандартні з `gamayun.pipeline.DEFAULT_PARAMS`, як у UI.
- simargl використовує свій індекс flink (bge-small), ці 10 задач не голосують. svitovyd бере карту
  сьогоднішнього репозиторію (18 123 файли).
- Останні задачі — 27–31.10.2024 (дати порівняно в UTC: у flink коміти мають різні часові пояси).
  Репозиторій витягнуто до 2026-10-02, але flink, на відміну від sonar, не переїжджав: у всіх 10
  задач файли досяжні (у 9 з 10 — майже всі).
- У клоні flink немає `.git/index`, тому `git ls-files` порожній. Дерево береться з
  `git ls-tree -r HEAD` (для sonar результат той самий: 8 475 файлів).

| 10 задач flink | hit@10 | MRR |
|---|---|---|
| simargl | 0.40 | 0.28 |
| gamayun | 0.30 | 0.23 |
| svitovyd, ідентифікатори | 0.20 | 0.08 |
| svitovyd, слова | 0.30 | 0.20 |
| RRF S+G | 0.60 | 0.29 |
| RRF S+G+V (ідентифікатори) | 0.60 | **0.37** |
| RRF S+G+V (слова) | **0.70** | 0.26 |
| RRF S+G+V+V (обидва) | **0.70** | **0.37** |

Для порівняння: на 16 задачах sonar «обидва» дають hit@10 0.88 і MRR 0.53, рівно як «слова».

**Що з цього випливає**

- **Перевірка 0.50.** На flink svitovyd зі словами дає 0.30. Це краще за ідентифікатори (0.20), але
  нижче, ніж на sonar. Число 0.50 з sonar було частково підігнане під ті задачі.
- **Де слова програють ідентифікаторам.** FLINK-36606 «TimestampITCase generates test artifacts…»: за
  ідентифікаторами svitovyd ставить правильний `TimestampITCase` на 3-тє місце. Через слова цей
  ідентифікатор розпадається на підслово «timestamp», яке трапляється в 240 файлах, і точне влучання
  зникає. Точний збіг з ідентифікатором коду — сильніший сигнал, ніж будь-яке слово.
- **Найкраще злиття — «обидва»:** ідентифікатори і слова як два окремі списки. Це найкращий або рівний
  найкращому варіант на обох проєктах і на 72 «живих» задачах exp10. Ідентифікатори дають точний
  верх списку, слова — охоплення.
- **Нестабільність через нічиї.** На 10 задачах одна задача — це 0.10, і навіть спосіб розбивати рівні
  бали на межі топ-10 змінює hit@10 злиття на 0.10. Числа flink — орієнтир, а не вимір.
- **Згода знову калібрує.** Файл, названий двома-трьома інструментами, правильний у 30–45 %
  випадків, названий одним — у 7 %.

## Один режим svitovyd: спершу ключові слова (`single_mode.py`)

Пошук за текстом задачі без прив'язки до ідентифікаторів для svitovyd сенсу не має: його структура
побудована на ідентифікаторах програми. Тому «слова → ідентифікатори → файли» тепер єдиний і
стандартний режим `svitovyd.graph.files_for_text`, без назви «обидва». Два списки з експерименту
зведено в одне правило:
- слово, яке саме є ідентифікатором, що визначає код (`TimestampITCase`), означає рівно його;
- будь-яке інше слово означає ідентифікатори, у підсловах яких воно є, як у `keywords extract -f`.

Так зникає провал FLINK-36606, коли `TimestampITCase` розпадався на «timestamp».

svitovyd читає **тільки свою карту**. Звичайні англійські слова (because, their, between) відсіюються
вбудованим списком, у базу задач svitovyd не ходить. Проміжна версія ще множила вагу слова на його
рідкість у минулих задачах (база задач, як у `kw.py`). Її рядки в таблиці — для порівняння: вона дала
одну задачу sonar, тож від неї відмовились заради чистоти svitovyd.

| | sonar 16 hit@10 / MRR | flink 10 hit@10 / MRR | exp10 72 AP / hit@10 |
|---|---|---|---|
| svitovyd, лише ідентифікатори | 0.06 / 0.03 | 0.20 / 0.08 | 0.025 / 0.083 |
| **svitovyd, один режим (тільки карта)** | 0.38 / 0.10 | **0.40 / 0.31** | 0.018 / 0.222 |
| svitovyd, один режим + частоти слів з бази задач (відкинуто) | 0.44 / 0.16 | 0.40 / 0.27 | 0.032 / 0.236 |
| RRF S+G | 0.75 / 0.44 | 0.60 / 0.29 | 0.277 / 0.889 |
| **RRF S+G+V, один режим (тільки карта)** | **0.88** / 0.49 | **0.70** / 0.37 | 0.282 / 0.903 |
| RRF S+G+V, + частоти з бази (відкинуто) | 0.81 / 0.49 | 0.70 / 0.36 | 0.286 / 0.903 |
| RRF S+G+V+V, два списки (експеримент) | 0.88 / 0.53 | 0.70 / 0.37 | 0.291 / 0.917 |

Різниці між варіантами — одна-дві задачі, в межах шуму. На flink, де формулу не підганяли, режим
«тільки карта» найкращий як окремий інструмент. Злиття з ним у всіх трьох наборах не гірше за злиття
без svitovyd.

## Висновки

1. Без відкату git триангуляція на свіжих задачах працює приблизно як в exp10: злиття ≥ найкращого
   інструмента.
2. Головне, що дає триангуляція користувачу, — не кращий порядок, а **калібрування**: файл, названий
   двома-трьома інструментами, приблизно вчетверо частіше правильний, ніж названий одним.
3. Для UI з цього випливає:
   - показувати згоду явно (вже є: смуга «усі три / два з трьох / один»);
   - позначати хаби;
   - позначати шляхи з історії, яких немає в сьогоднішньому дереві (svitovyd знає дерево).
4. svitovyd потребує стоп-списку загальних ідентифікаторів, інакше його рідкі влучання тонуть у
   «SonarQube».
5. Пошук svitovyd за текстом задачі — завжди через ключові слова: слово → ідентифікатори → файли,
   причому слово, що саме є ідентифікатором, означає рівно його. Тепер це єдиний режим
   `svitovyd.graph.files_for_text` (див. розділ вище). Окремий список «лише ідентифікатори» не потрібен.
