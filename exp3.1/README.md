# exp3.1: Task-unit criterion — Ticket vs. Commit-message

`exp3` (Task-to-Code Retrieval) was built and validated on `sonar.db`, where
every "task" is a Jira ticket (`TASK` table) linked to commits via
`RAWDATA.TASK_NAME`. The plan is to scale the experiment to 10 more projects
with very different record-keeping cultures — from Apache-style projects
with near-universal Jira linkage, down to plain git repos with no issue
tracker at all. `exp3.1` extends the design to make the experiment work
across that whole spectrum.

## Problem

`exp3`'s retrieval unit is a "task": some text (title/description/comments)
paired with the set of files it touched. That text and that file-set
currently come exclusively from `TASK` + `TASK_NAME`-linked `RAWDATA` rows.
Two things break as we add more projects:

1. **No tracker at all.** `codeXplorer/main_commits_only.py` exists
   specifically for repos without an issue tracker — it only populates
   `RAWDATA`, never `TASK`. For those projects, `exp3` currently has
   nothing to embed.
2. **Weak linkage even with a tracker.** Even in `sonar` — a "clean"
   Apache/Jira-style project — only **64.6%** of distinct commits carry a
   `TASK_NAME` (see `project_stats.csv`). `codeXplorer`'s own connector
   code already flags much worse cases for GitLab-hosted projects
   (Inkscape ~2%, GNOME Shell ~1%, Mesa ~6% commit→issue linkage).

## Proposed fix: task unit as a criterion, not just a fallback mode

Instead of treating "use commit messages" as a degraded fallback for
tracker-less projects, treat **task unit** as a first-class experiment
variable with two possible values:

- **`ticket`** (current behavior): one unit = one `TASK` row.
  `TITLE` / `DESCRIPTION` / `COMMENTS` come from the tracker.
  Ground truth files = `RAWDATA.PATH` where `TASK_NAME` matches.

- **`commit`** (new): one unit = one commit (`RAWDATA.SHA`).
  `TITLE` = first line of `MESSAGE` (git subject-line convention).
  `DESCRIPTION` = full `MESSAGE` (subject + body).
  `COMMENTS` = not available in this mode → **RQ3 (noise from comments)
  is not testable under the `commit` criterion.**
  Ground truth files = `RAWDATA.PATH` grouped by `SHA`.

This works identically across all 10 projects because `RAWDATA.MESSAGE`
and `RAWDATA.PATH` are always populated by `codeXplorer`, regardless of
whether a tracker exists — `main_commits_only.py` guarantees at least this
much.

Needed cleanup before treating a commit as a unit (noise filtering):
- Drop merge commits (`MESSAGE` starting with `Merge `).
- Drop commits touching an excessive number of files (mass reformlibrary /
  rename commits — not a real "task").
- Drop trivially short messages (e.g. `"typo"`, `"bump version"`).

## Comparison plan per project

For each project database, using `db/collect_db_stats.py`:

- **If `TASK` table exists and has enough linked tasks** (see threshold
  below): run `exp3` under **both** criteria (`ticket` and `commit`) and
  compare retrieval quality (MAP/MRR/P@K/R@K) head to head. This tells us
  whether tracker text is actually a better retrieval signal than raw
  commit messages, or whether — given tracker linkage is never 100% — the
  commit-message criterion is competitive or better simply from having
  more usable volume.
- **If no `TASK` table, or too few linked tasks:** only the `commit`
  criterion is usable. Report its metrics standalone (no ticket-based
  comparison possible) — this still answers RQ1/RQ2/RQ4 for that project
  (RQ2 title-vs-description becomes subject-line-vs-full-message-body;
  RQ3 is out of scope).

**Volume threshold:** a criterion is marked usable when it yields **≥600
distinct units** (200 held-out test + safety margin ~3x for training/
windowing, mirroring `exp3`'s existing 9,599 train / 200 test split).
Below that, results would be too noisy to trust.

## Performance note: indexes vs. column pruning

Worth flagging since it came up while looking at the data: `COMMITS` /
`RAWDATA` has **no indexes** beyond the implicit rowid (`TASK` already has
`TASK_ID_INDX` / `TASK_NAME_INDX` from `codeXplorer`'s `db_manager.py`).
That doesn't matter for the experiment pipeline itself — `etl_pipeline.py`'s
`load_data()` always does an unconditional `SELECT * FROM TASK` /
`SELECT * FROM {commits_table}` and filters in pandas afterward, so there's
no `WHERE`/`ORDER BY`/`COUNT(DISTINCT ...)` for an index to speed up; a
full sequential scan reads the same amount either way.

What *does* matter: that `SELECT *` currently pulls `DIFF`, which is dead
weight — `grep` confirms no code anywhere in the pipeline reads it. Measured
on `rubocop.db`: `DIFF` is 82.5% of the combined `DIFF`+`MESSAGE`+`PATH`
byte count (98.5MB of 119MB). On `vscode.db` (12GB) or `kubernetes.db`
(8GB) that's plausibly several GB of unused BLOB read into memory on every
ETL run. Fix: narrow the `SELECT` to `SHA, PATH, MESSAGE, CMT_DATE,
TASK_NAME` (keeps everything the `ticket` criterion uses today, plus
`SHA`/`MESSAGE`/`CMT_DATE` that the `commit` criterion will need) and drop
`DIFF`, `AUTHOR_NAME`, `AUTHOR_EMAIL`, `ID`. Not yet applied — pending
confirmation before editing `etl_pipeline.py`.

Indexes on `COMMITS(SHA)` / `COMMITS(TASK_NAME)` would only pay off for
one-off diagnostic queries like `collect_db_stats.py`'s
`COUNT(DISTINCT SHA)` — not for the experiment's own read path.

## Next steps

1. Implement `TASK_UNIT = 'ticket' | 'commit'` as an ETL parameter (builds
   a synthetic per-commit "task" table when `commit` mode is selected;
   everything downstream — split/window/embeddings/metrics — stays
   unchanged). Needs the noise filtering listed above (drop merges, mass
   diffs, trivial messages).
2. Apply the `SELECT *` → explicit-column fix in `etl_pipeline.py`
   (see performance note).
3. Add project namespacing to collection names and output files (current
   naming — `rag_exp_{source}_{target}_{window}_{split}`,
   `results_<model>.csv` — has no project dimension and would collide
   across projects run back-to-back).
4. Run the `ticket` vs `commit` head-to-head on the 9 comparable projects;
   report `agilebill` as out-of-scope (insufficient volume either way).
