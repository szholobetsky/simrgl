## 1. Що сталося: чому WebAsk нічого не знаходить

Запит у WebAsk (vyrii): *«How to use G^2 distribution for mutual informations analyses in two text corpora?»*
→ нуль результатів. Те саме і на будь-який інший запит, навіть `python requests tutorial`.

**Причина:** DuckDuckGo відповідає `202` і сторінкою `anomaly` (перевірка на бота) на кожен запит
з нашої підмережі, — і `html.duckduckgo.com`, і `lite.duckduckgo.com`, з будь-яким User-Agent, GET чи POST.
Слова тут ні до чого. Найімовірніше, підмережу «засвітили» сусіди, або наші ж серійні запити
(webask / webanalys / deepagent_md шлють їх пачками). Колись так само блокували Google, YouTube і навіть Wikipedia.

**Чому vyrii показує «немає результатів», а не «заблоковано»:** `_web_ddg_search`
(`C:\Projects\vyrii\vyrii\adapter.py`, та сама функція в `C:\Projects\1bcoder\chat.py` і копія в
`vyrii/tools.py`) не перевіряє ні код відповіді, ні сторінку `anomaly` — не знаходить `result__a`
і повертає порожній список.

**Друга вада там же:** результат додається до списку, щойно закривається посилання з заголовком,
а сніпет на сторінці йде *після* нього → сніпети, найімовірніше, завжди порожні (видно з коду;
на живій видачі не перевірено, бо DDG блокує).

## 3. Чому «тільки з браузером»: як працює захист

Два різні механізми:

1. **Обгортки (Programmable Search, Qwant, Swisscows):** сторінка — порожня оболонка, JS іде в API
   по результати, але з **тимчасовим токеном** чи cookies, які видає або обчислює саме JS.
   Приклад: `cse.js` для search.com.ua містить `"cse_token": "AHbIdTgB…:1792495169964"` (друга частина —
   час, токен живе недовго). Qwant API без cookies захисту → 403.
2. **Google:** спершу «доведи, що ти браузер» — сторінка без JS має лише посилання
   `/httpservice/retry/enablejs?sei=…`; обфускований скрипт збирає ознаки середовища й обчислює токен,
   і лише тоді віддає результати. Той самий принцип, що «Just a moment…» у Cloudflare.

**Чому так:** безкоштовний пошук оплачує реклама, яку бачить людина; бот реклами не бачить, а коштує
обчислень; масово викачана видача — готовий матеріал для конкурентів. Доступ для ботів продається
(«grounding with Google Search» у Gemini API / Vertex). Тобто не «тільки для людей», а
«люди платять увагою, боти — грошима».

**Обхід** (витягти токен, емулювати браузер) технічно можливий — так працюють SerpAPI та подібні, —
але це порушення умов сервісів, вічні перегони і важкий headless-браузер. **Не будуємо на цьому.**

## 4. Рівень A: кілька пошуковиків у vyrii та 1bcoder

### 4.1 Рішення (узгоджено)

- **DDG — пошуковик за замовчуванням.**
- **1bcoder:** команда з вибором за номером (pick number) — людина обирає default search engine.
  Зберігається в `~/.1bcoder/search.json` (поруч з `jev.json`, `translate.json`, `visual.json`).
- **vyrii:** вибір пошуковика — на сторінці **WebAsk**; обране значення запам'ятовується, і будь-яка
  інша сторінка чи flow з вебпошуком використовує значення, обране на WebAsk.
- simargl у список пошуковиків **не** входить — для нього є окремий RAG-пошук.

### 4.2 Типи бекендів

| тип | приклади | що задається |
|---|---|---|
| вбудовані, без ключа | DDG, Wikipedia, OpenAlex, Crossref, arXiv | нічого |
| вбудовані, з ключем | Brave Search API, Tavily | ключ |
| `searxng` | свій або публічний SearXNG | URL (формат JSON стандартний) |
| `opensearch` (RSS/Atom) | YaCy, kiwix-serve, багато вікі й бібліотек | шаблон URL з `{q}`, `{n}` |
| `json` (custom) | будь-яке API: Serper, свій сервіс, майбутній 1bsearcher | URL, заголовки, шляхи `list`/`title`/`link`/`snippet` |
| `recoll` | recoll-webui на pantheon | URL (JSON-видачу recoll-webui перевірити на живому сервері) |

Приклад `~/.1bcoder/search.json`:

```json
{
  "default": "ddg",
  "engines": {
    "ddg":       {"type": "ddg"},
    "openalex":  {"type": "openalex"},
    "wikipedia": {"type": "wikipedia", "lang": "en"},
    "brave":     {"type": "brave",  "key": ""},
    "tavily":    {"type": "tavily", "key": ""},
    "recoll":    {"type": "recoll",     "url": "http://panteon.local:8080"},
    "kiwix":     {"type": "opensearch", "url": "http://pi2:8080/search?pattern={q}&format=xml&pageLength={n}"},
    "my-api":    {"type": "json", "url": "https://example.org/api?q={q}&n={n}",
                  "headers": {"Authorization": "Bearer ..."},
                  "list": "results", "title": "title", "link": "url", "snippet": "abstract"}
  }
}
```

### 4.3 Що змінити в коді

- Одна функція пошуку з диспетчером за типом бекенду замість трьох копій DDG-парсера
  (`vyrii/adapter.py`, `vyrii/tools.py`, `1bcoder/chat.py`); flows (`webask`, `webanalys`,
  `deepagent_md`, `deepagent_tree`, `deepagent_tree_md`) кличуть її так само, як зараз `_web_ddg_search`.
- **Явне розпізнавання блоку:** `202`, `403`, `429`, `anomaly`, captcha, «Just a moment» →
  повідомлення «<пошуковик> заблокував запит як автоматичний», а не «немає результатів».
- **Сніпети DDG:** додавати результат після сніпета, а не після заголовка.
- Залежності — лише `requests` і стандартний `xml.etree` (вимога: ставиться на телефон).

Статус на 2026-10-20: **зроблено, без екзотики** — DDG (за замовчуванням), Wikipedia, OpenAlex,
Crossref, arXiv, Brave (ключ), Tavily (ключ), SearXNG (URL). `recoll`, `opensearch`, `json` — не робили.
- Модуль `websearch.py` (`C:\Projects\1bcoder\websearch.py`, ідентична копія `C:\Projects\vyrii\vyrii\websearch.py`);
  `_web_ddg_search` у обох лишився ім'ям для flows і йде через вибраний пошуковик.
- 1bcoder: `/web engine` (список з номерами, `Pick`), `/web engine <N|name> key=… | url=… | lang=…`,
  `/web search -e <engine> …`; налаштування `~/.1bcoder/search.json`; тести `tests/test_websearch.py`.
- vyrii: вибір на сторінці WebAsk → `~/.vyrii/config.json` (`"search"`), API `GET /vyrii/search/engines`,
  `POST /vyrii/search/engine`; WebAsk/WebAnalys показують причину невдачі (напр. «ddg blocked … HTTP 202»).
- `vyrii/tools.py: ddg_search` (ніхто не кличе) лишився як був.

## 5. Офлайн-пошук на pantheon: Recoll і Kiwix

**Recoll** — той самий «локальний Google», про який домовлялися раніше; записаний у
`concepts/UX_DESIGN_IMAGE_SETUP.md`, §3.2:
- повнотекстовий пошук на Xapian, видача з уривками, де виділено слова запиту;
- PDF, doc/odt, HTML, email, архіви; **скановані PDF — через Tesseract OCR** (з версії 1.26);
- на pantheon: `recoll-webui` на порту 8080, нічна переіндексація `recollindex` о 03:00 (cron);
- питання Q4 там же: чи ставити Tesseract і poppler (залежить від того, чи будуть скани).

**Ланцюжок «важливе з інтернету — офлайн»:** краулер vyrii (`~/.vyrii/crawl/`) викачує потрібні
сайти → Recoll індексує теку → пошук без інтернету.

**Kiwix** — Вікіпедія офлайн: ZIM-файли **вже містять готовий повнотекстовий індекс** (Xapian),
`kiwix-serve` шукає по ньому одразу; англійська Вікіпедія з картинками ~100 ГБ. Індексувати не треба.

**Межа Recoll:** це настільний пошук — добре на сотнях тисяч і кількох мільйонах документів.
Для десятків мільйонів — sist2 (колекції файлів, OCR, на Elasticsearch), Elasticsearch/OpenSearch,
Manticore, або свій індекс (рівень B).

## 6. Рівень B: 1bsearcher — концепція

### 6.1 Навіщо

Колись кожна мережа гуртожитку КПІ мала свій FTP-пошук; Яндекс, Рамблер, bigmir — свої пошуковики,
на залізі слабшому за сучасний телефон. Потім Google витіснив усіх, а тепер замінює пошук відповіддю
Gemini. Для програм і агентів пошук закрили (розділ 3).

**1bsearcher** — свій маленький пошуковик у дусі 1bcoder: як 1bcoder вичавлює максимум з моделі на
1B, так 1bsearcher — зі слабкого заліза (міні-ПК, Raspberry Pi, телефон), офлайн, без чужих API.
«Суверенний інтернет на трьох Raspberry Pi».

### 6.2 Головна ідея

**Не зберігати інтернет — зберігати витягнутий текст.**

- Не викачувати картинки, відео, PDF цілком — лише основний текст сторінки (без меню, реклами, футерів).
- Наукова стаття в PDF: 1–3 МБ → тексту 50–100 КБ (3–5 %). HTML-сторінка: 50–500 КБ → тексту 5–20 КБ.
- Над текстом — **інвертований індекс**: слово → номери сторінок; запит із кількох слів = перетин
  множин («гімно» → {1,2,3}, «холодець» → {3,4,5}, «гімняний холодець» → {3}).
- Індекс і текст ріжуться на **багато малих баз** (шардів), а не одну велику.

Це не «інший шлях» порівняно з великими пошуковиками — це **той самий фундамент**, на якому стоять
оригінальний Google 1998 року, Lucene/Elasticsearch, Xapian (Recoll), SQLite FTS5.
Відмінність — у масштабі й у тому, що зберігаємо лише текст.

## 7. Інвертований індекс: як він влаштований

### 7.1 Словник — не 250 тисяч

Живих слів англійської — близько 170 тис., але у вебі є імена, бренди, помилки, ідентифікатори, числа.
Кількість різних токенів росте з обсягом даних (**закон Хіпса**) — до десятків і сотень мільйонів;
більшість трапляється 1–2 рази (**закон Ципфа**). Словник має бути розширюваним
(B-дерево, FST або просто таблиця SQLite).

### 7.2 Бітмап чи список номерів

Голий бітмап (біт на кожну сторінку для кожного слова) не годиться: при 100 млн сторінок це 12 МБ
на **кожне** слово, навіть якщо воно є на двох сторінках. Тому:

| слово | як зберігати |
|---|---|
| рідкісне | **список номерів**, стиснений як різниці сусідніх номерів (дельта + varint) — ~1 байт на входження |
| часте | **бітмап** |
| будь-яке | **Roaring bitmaps** — поєднують обидва автоматично (Lucene, Druid, ClickHouse; для Python — `pyroaring`) |

### 7.3 Ранжування, фрази, сніпети

| що треба | що додати до індексу | ціна |
|---|---|---|
| лише «є / немає» (перетин) | номери сторінок | база |
| ранжування **BM25** | частота слова на сторінці (1 байт на входження) + довжина сторінки | +1 байт |
| пошук фрази («саме разом») | позиції слів | ~×2 індексу — можна не робити |
| сніпети (уривки) | основний текст сторінки, стиснений **zstd** (~4–5 разів) | окреме сховище |

### 7.4 Словоформи

«Гімняний» ≠ «гімно» — без зведення до основи перетин порожній. Англійська: стемер (Porter/Snowball).
Українська: лематизація або підхід gamayun без стемера (`concepts/GAMAYUN.md`, §16.4).

### 7.5 Шарди

**Document-partitioned sharding:** сторінки ділимо на шматки; кожен шматок — окрема SQLite з власним
індексом і текстом. Запит іде в усі шматки паралельно, топ-результати зливаються.
3 Raspberry Pi = 3 шматки, кожен Pi шукає у своєму. Новий шматок додається без перебудови старих.

## 8. Звідки брати текст без краулінгу всього інтернету

| джерело | що | навіщо нам |
|---|---|---|
| **Common Crawl — WET** | щомісячний обхід мільярдів сторінок; WET = **лише витягнутий текст** | саме «текст без інтернету»; через CDX-індекс можна брати лише потрібні домени (`*.edu`, `*.ac.uk`, `*.edu.ua`, університети) |
| **FineWeb / FineWeb-Edu** (Hugging Face) | очищений текст з Common Crawl; Edu — відфільтрований «освітній» | майже готовий «академічний інтернет» |
| **OpenAlex** (snapshot) | метадані й анотації сотень мільйонів наукових робіт | наукова частина без PDF |
| **arXiv** (масові вивантаження) | препринти | повні тексти з дозволу |
| **PubMed Central Open Access** | повні тексти статей | медицина/біологія |
| **Kiwix ZIM** | Вікіпедія та інші вікі | готовий індекс, не індексувати |
| свій краулер | сайти, яких немає в Common Crawl; FTP; локальні теки | точково |

**Права:** «торенти бібліотек» (LibGen, Sci-Hub) — піратські копії; для особистого архіву — власне
рішення, але в дисертації чи публічному продукті на них не спиратися.

**Дублікати:** одна стаття — і в arXiv, і на сайті університету, і в бібліотеці. Дедуплікація за хешем
тексту і DOI.

## 9. Розміри й залізо

Усе — оцінки за порядком величини, не виміряні.

### 9.1 Варіант «лише текст» (1bsearcher)

На 100 млн сторінок:

| що | на сторінку | разом |
|---|---|---|
| основний текст (trafilatura), стиснений zstd | ~2–3 КБ | **200–300 ГБ** |
| індекс: ~400 різних слів × ~1.5 байта (номер + частота, без позицій) | ~0.6 КБ | **~60 ГБ** |

**100 млн сторінок ≈ 1 ТБ SSD.** Індекс — обов'язково на SSD/NVMe (на HDD пошук повільний).

### 9.2 Варіант «викачати все» (для порівняння)

100 ТБ сирих даних (PDF, книги, сторінки) ≈ 50 млн документів ≈ 2–5 ТБ тексту ≈ 2–5 ТБ індексу.
Вузьке місце — не індексація, а **OCR сканів**: Tesseract 2–10 с на *сторінку* на ядро; 1 млн книг ×
300 сторінок ≈ 50 ядро-років на CPU; на GPU (PaddleOCR, docTR) 10–50 сторінок/с → місяці.
Правило: OCR лише вибірково, брати готовий текстовий шар, де він є.

Машина для побудови такого: 16–32 ядра, 128 ГБ RAM, 4 ТБ NVMe під індекс, масив HDD, GPU для OCR.
Для пошуку по готовому індексу: 32–64 ГБ RAM, індекс на NVMe, 8 ядер.

**Краулінг:** 100 ТБ за рік ≈ 275 ГБ/день ≈ 25 Мбіт/с без перерви — домашній канал витримує;
обмежують сайти (банять агресивних ботів).

**Реалістичний старт:** не 100 ТБ, а 4–10 ТБ відібраного академічного (arXiv, OpenAlex, PMC OA,
Kiwix, курси університетів) — або ще краще, «лише текст» з розділу 9.1.

## 10. Архітектура 1bsearcher

```
  джерела                    обробка                          зберігання (шард = одна SQLite)
┌──────────────┐     ┌──────────────────────────┐      ┌───────────────────────────────────┐
│ CC WET       │     │ витягти основний текст   │      │ docs(id, url, title, lang, date)  │
│ FineWeb-Edu  │ ──► │ (trafilatura; для PDF —  │ ──►  │ text(id, zstd blob)  ← сніпети     │
│ свій краулер │     │  pdftotext, OCR вибірково)│      │ індекс: FTS5  →  потім свій        │
│ FTP / теки   │     │ мова, дедуплікація        │      │   (слово → Roaring / delta+varint) │
└──────────────┘     │ токени, леми              │      └───────────────────────────────────┘
                     └──────────────────────────┘                     ▲  ▲  ▲  (шард на кожен Pi)
                                                                       │  │  │
  клієнти: vyrii WebAsk, 1bcoder /web search  ──►  запит у всі шарди паралельно → злиття топ-K
           (тип бекенду `json` або `opensearch`)    → BM25 → сніпети з text
```

**Принципи пантеону:**
- окрема тека `C:\Projects\1bsearcher\`, ніколи не сабмодуль;
- ставиться на телефон: Flask + waitress, без gradio/FastAPI; ядро — Python + SQLite;
- реєстр індексів `~/.1bsearcher/…` (як `~/.simargl/stores.json`, `~/.gamayun/projects.json`);
- **віддає JSON і OpenSearch** — тоді vyrii та 1bcoder підключають його як звичайний бекенд
  (розділ 4) без жодного спеціального коду.

**Цеглинки, що вже є в пантеоні:**
- краулер — vyrii (`~/.vyrii/crawl/`);
- «зібрати джерело → одна SQLite» — патерн mokosh;
- статистика термінів (G², lift, якорі, слова-шум без стоп-словника) — gamayun
  (`concepts/GAMAYUN.md`, теорія — `concepts/GAMAYUN_DETAILS.md`);
- пошук за змістом поверх видачі — simargl (ембедінги) як можливий другий етап ранжування.

## 11. План: етапи з перевіркою на кожному

| етап | що зробити | як перевірити |
|---|---|---|
| **0** | Рівень A: вибір пошуковиків у vyrii/1bcoder (розділ 4) | WebAsk працює, коли DDG заблоковано |
| **1** | Прототип на **SQLite FTS5**: 1 млн сторінок FineWeb-Edu на одному Pi | розмір бази, час побудови, мілісекунди на запит, якість сніпетів |
| **2** | Шарди: 3 бази, злиття топ-K | час запиту не росте лінійно з кількістю шардів |
| **3** | Імпорт CC WET для вибраних доменів (`*.edu.ua`, університети) | дедуплікація, частка корисних сторінок |
| **4** | Свій індекс (Roaring / delta+varint), якщо FTS5 упреться в межі | порівняння з FTS5: розмір і швидкість на тих самих даних |
| **5** | Українська: лематизація / підхід gamayun | перетин «гімняний холодець» знаходить «гімно» + «холодець» |
| **6** | Свій краулер і FTP/теки, OCR вибірково | — |
| **7** | Друге ранжування за змістом (simargl) поверх топ-100 BM25 | якість на наборі запитів |

Принцип: кожен етап закінчується **числами** (розмір, час, якість), перш ніж переходити далі.

## 12. Відкриті питання

- Що саме входить у «корисний інтернет»: які домени, мови, обсяг? Від цього залежить, чи вистачить FTS5.
- Чи робити пошук фраз (позиції слів подвоюють індекс)?
- Українська морфологія: готовий лематизатор (pymorphy-подібний) чи статистичний підхід gamayun?
- Як оновлювати: Common Crawl щомісяця — що робити зі старими версіями сторінок?
- Recoll vs 1bsearcher на pantheon: Recoll — для своїх файлів і PDF з OCR; 1bsearcher — для «тексту
  інтернету». Чи об'єднувати видачу (через рівень A — так, як два бекенди)?
- recoll-webui: чи справді віддає JSON — перевірити на живому сервері.
