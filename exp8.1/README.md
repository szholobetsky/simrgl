# exp8.1 — чи допомагає онтологія коду онтології історії задач

**Питання.** gamayun уміє будувати онтологію двома способами:
- **з бази задач** (`--db`): термін задачі × змінений файл;
- **з файлів** (`--files`, `concepts/GAMAYUN.md` §16): термін або ідентифікатор × одиниця коду.

Чи шукатиме об'єднана онтологія файли для задач краще, ніж онтологія лише з бази?

**Дані.** sonar, ті самі 200 тестових і 199 dev-задач, що в exp7/exp8 (правило `modn`).

| | що | без витоку тестових задач? |
|---|---|---|
| **історія** | онтологія exp7 без тестових (і dev) задач, наївний Байєс, параметри підібрано на dev | так |
| **код** | `gamayun --files` по коду sonarqube на останньому коміті бази (`ef1d41c`, 2024-10-25): 10 474 файли, 75 622 одиниці, 1.39 млн трійок | міток задач не бачить, але код містить і пізніші розв'язки (див. застереження) |

Бал коду для файлу: Σ log lift(термін, файл) + відступ до папки й модуля + збіги з назвою файлу.
Це та сама формула, що в історії, тільки без пріора (у коду немає «скільки задач змінювали файл»).

Варіанти злиття (параметри підібрано на dev, тест прогнано один раз):
- **сума:** історія(f) + w · код(f);
- **зважений RRF** двох ранжувань;
- **сума з умовою:** код додається лише для задач, які називають ідентифікатор, визначений у коді (camelCase / snake_case).

```
git -c core.longpaths=true -C C:\Projects\Data\sonarqube worktree add --detach C:\Projects\Data\wt\sonar\DBLAST ef1d41c122bb
python build_code.py      # ~5 хв -> out/code_triples.txt (220 МБ, у .gitignore)
python combine.py         # ~2.5 хв -> out/sonar.json
```

## Результати (тест, файли, топ-10)

| | усі 200 задач | 97 задач, правильний файл є в знімку | 36 задач називають ідентифікатор |
|---|---|---|---|
| історія (exp7 gamayun) | **0.116** / 0.44 | 0.198 / 0.58 | 0.060 / 0.28 |
| лише код | 0.024 / 0.11 | 0.050 / 0.23 | 0.055 / 0.22 |
| історія + w · код (dev: **w = 0**) | 0.116 / 0.44 | 0.198 / 0.58 | 0.060 / 0.28 |
| RRF (dev: вага коду **0**) | 0.116 / 0.44 | 0.198 / 0.58 | 0.060 / 0.28 |
| історія + 0.25 · код, лише якщо задача називає ідентифікатор | 0.116 / 0.43 | 0.200 / 0.61 | 0.061 / 0.25 |

(MAP / hit@10.) dev, MAP за вагою коду: 0 → 0.096, 0.05 → 0.093, 0.25 → 0.071, 1 → 0.026.
З умовою «називає ідентифікатор»: 0 → 0.096, 0.25 → 0.101.

## Висновки

1. **Об'єднана онтологія не працює краще.** Будь-яка домішка коду до всіх задач лише погіршує dev,
   тому і сума, і RRF вибирають вагу 0. Сама онтологія коду в 5 разів слабша за історію (0.024 проти 0.116).
2. **Чому так.** Текст задачі написано мовою користувача («leak period header», «quality gate fails»).
   Онтологія історії вчиться саме на парі *ця мова → ці файли*. Онтологія коду знає лише, які слова
   характерні для файлу всередині коду. Слова задачі й слова коду перетинаються слабко: це той самий
   розрив словників, що й причина провалу exp0 (TF-IDF по коду). До того ж у коду немає пріора, і всі
   ~10 тис. файлів для нього рівноправні, а історія знає, які файли взагалі змінюються.
3. **Де код майже рівний історії — на задачах з ідентифікаторами.** На 36 таких задачах історія сама
   падає до 0.060, а код дає 0.055. Умовне злиття підняло dev на 5 % (0.096 → 0.101), але на тесті
   вийшло 0.116 → 0.116, тобто приросту немає. Задач з ідентифікаторами лише 18 %, а внесок у них малий.
4. **Онтологію з файлів варто тримати окремим проєктом**, а не зливати з історією: `~/.gamayun/sonar`
   (база) і `~/.gamayun/sonar-code` (код). Вона корисна для іншого: показує, що визначено де
   (`defined_in`, `used_in`), які ідентифікатори пов'язані (`related_to`) і що є ядром предметної
   області. Ранжувати файли під текст задачі вона не допомагає.

## Застереження

- **Знімок коду на кінець історії (2024-10).** Для тестових задач, частина яких давніша, це код
  «з майбутнього»: у ньому вже є ідентифікатори їхніх розв'язків. Тобто код тут мав навіть **перевагу**,
  і все одно не допоміг. Чесніший знімок «перед кожною задачею» (як в exp9.1) коштував би 200 побудов
  по ~5 хв.
- У знімку існує лише 28 % правильних файлів тестових задач. Перевірено окремо на 97 задачах, де
  є хоч один такий файл: висновок той самий.
- Розбиття `modn` не часове, як і в exp3/exp7: навчальні задачі можуть бути пізніші за тестові.
