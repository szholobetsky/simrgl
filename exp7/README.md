# exp7 — онтологія з трекера задач і git-історії без LLM

**Питання.** Чи можна побудувати онтологію «задача — термін — код» без мовної моделі так,
щоб кожен присудок мав перевірюваний критерій, і чи несе така онтологія інформацію для
передбачення файлів, які зміняться за задачею?

**Принцип.** Присудок — це не слово, а *операційне означення*: формула над даними
плюс поріг значущості. Трійка записується лише тоді, коли спрацювало правило, і в `[src: ...]`
лежать числа, через які воно спрацювало. Будь-яку трійку можна перерахувати й оскаржити.

**Перевірка.** Онтологія будується лише з навчальної частини поділу `modn` з exp3 (сортування
за `TASK.ID`, кожна k-та задача, 200 тестових). `evaluate.py` передбачає модулі та файли тестових
задач **тільки з `triples.txt`**, без звернень до бази, і рахує метрики функцією, скопійованою
з `exp3/utils.py` (AP по топ-10, нормування на кількість релевантних).

**Валідація.** Параметри ранжувальників підбираються на 200 dev-задачах. Їх тим самим правилом
`modn` беруть з навчальної частини, а для підбору будують окрему онтологію без них
(`build_onto.py --dev` → `out/<p>/dev/`). Знайдені параметри один раз застосовуються до тесту
з повною онтологією. Тестові задачі не обирають жодного параметра.

```
python build_onto.py --db C:/Projects/Data/sonar.db --repo C:/Projects/Data/sonarqube --out out/sonar
python build_onto.py --db C:/Projects/Data/sonar.db --out out/sonar/dev --dev
python evaluate.py out/sonar
```

**Наївний Байєс** — ранжувальник, що прямо випливає з присудків:

    score(ціль) = log P(ціль) + λ · Σ_{терміни задачі} log lift(термін, ціль)

P(ціль) = `task_count` / `dataset :: train_tasks`. Lift береться з `[src]` трійки `characterizes`;
термін без значущої трійки має lift 1, тобто додає 0. `not_in` додає log(0.5 / очікуване).
Файл додатково отримує докази своєї папки (β) і свого модуля (β₂), `names` додає μ·log(1+n),
`co_changes_with` додає γ·(нормоване G²) від 10 найкращих файлів. λ < 1 послаблює припущення
про незалежність термінів, яке в текстах явно хибне.

## Присудки та їхні критерії

Типи сутностей мають префікси (`term:`, `module:`, `dir:`, `file:`), щоб слово і папка з
однаковою назвою не злилися. Модуль — коренева папка шляху, як у `exp3/utils.extract_module_path`.

| Присудок | Критерій | Поріг |
|---|---|---|
| `file :: part_of :: dir`, `dir :: part_of :: module` | шлях | детерміновано |
| `module/file :: task_count :: N` | у скількох навчальних задачах змінювався | — |
| `term :: characterizes :: module/dir/file` | G² (log-likelihood, Dunning 1993) по таблиці 2×2 «задача містить термін» × «задача змінює ціль», лише позитивна асоціація | G² ≥ 10.83 (p < 0.001); підтримка ≥ 5 (модуль) / ≥ 3 (папка, файл) |
| `term :: anchor_of :: module` | концентрація терміна по модулях, індекс Герфіндаля (HHI, як в exp1) | HHI ≥ 0.5, df ≥ 10 |
| `term :: names :: file` | термін є частиною camelCase-імені файлу **і** трапляється разом із ним у задачах | ≥ 2 спільні задачі |
| `term :: not_in :: module` | за базовою частотою модуля очікуються збіги, а їх 0: P₀ = (1−r)^df | P₀ < 0.001, df ≥ 30 |
| `file :: co_changes_with :: file` | G² по задачах, де змінено ≤ 30 файлів (масові рефакторинги відкинуто) | G² ≥ 10.83, ≥ 3 спільні задачі |
| `term :: narrower_than :: term` | subsumption (Sanderson & Croft 1999): P(A\|B) ≥ 0.8 і df(A) > df(B) | ≥ 5 спільних задач, df ≥ 20 |
| `module :: depends_on :: module` | Java-імпорти на останньому коміті бази (`git cat-file`, без checkout) | ≥ 3 файли, що імпортують |

Терміни — слова назви та опису задачі (довжина ≥ 3, без стоп-слів, плюс частини camelCase і
snake_case ідентифікаторів), df від 5 до 30 % навчальних задач. Коміти без `TASK_NAME`
не використовуються: вони можуть належати тестовій задачі.

Повні таблиці — `out/<project>/results.csv`. Тест-задачі з `files` > 0: sonar 200, flink 197.
Частка тестових файлів у кандидатах ранжувальника: sonar 0.70, flink 0.78 — це стеля R@k.

**Що видно:**
1. **Наївний Байєс — найкращий ранжувальник на обох проєктах і обох рівнях.** На модулях
   sonar він уперше обганяє частотну базову лінію (0.752 проти 0.693), бо, на відміну від суми G²,
   містить апріорну частоту. На файлах він у 2.6 (sonar) і 7 (flink) разів кращий за prior.
2. **Найсильніший присудок — `characterizes`.** Докази папки (β) допомагають на обох проєктах.
   `names` і `co_changes_with` допомагають на flink, а на sonar dev їх вимкнув (вага 0).
   Внесок присудків залежить від проєкту, тому параметри треба підбирати для кожного окремо.
3. `not_in` у Байєсі — малий, але однонапрямлений плюс (+0.005 / +0.002 MAP модулів).
4. Зважена сума з ваговим підбором на sonar вимикає всі компоненти, крім `characterizes`
   файлів. Нормування «на максимум» губить масштаб доказів, а log lift його зберігає.
5. `narrower_than` за subsumption здебільшого ловить кадри стектрейсів (`standardhostvalve ::
   narrower_than :: lang`), а не таксономію понять. В оцінці не використовується.

Довідково: BGE-large у exp3 на sonar `modn` — MAP модулів 0.452, файлів 0.0745
(інше джерело ground truth, див. застереження).

## Застереження

- **Порівняння з exp3 не пряме.** exp3 читав таблицю `RAWDATA`, якої в цих базах немає;
  тут ground truth — `COMMITS.PATH` за `TASK_NAME`. exp3 повідомляє 27 модулів sonar, тут
  їх 64 (усі історичні кореневі папки). Довідково: BGE-large у exp3 на sonar `modn` —
  MAP модулів 0.452, файлів 0.0745.
- **Частотна базова лінія на sonar (MAP 0.693 для модулів) вища за BGE з exp3 (0.452).**
  Якщо на даних exp3 вийде так само, висновки exp3 про модулі треба перевірити проти
  prior. Це варто перерахувати на рідних даних exp3.
- **`DESCRIPTION` у `sonar.db` збережено як Python-repr документа Atlassian (ADF)** — усі
  8041 непорожні описи. Без розбору службові вузли (`mediaSingle`, `hardBreak`, `bulletList`,
  `listItem`, `xa0`) ставали «термінами» з найвищим G². `common.plain_description` залишає
  тільки текстові вузли. Якщо exp3 вбудовував опис як є, BGE отримував цю розмітку в тексті.
- Перша версія файлового ранжування («фіксовані ваги») тепер рахується на тому самому наборі
  кандидатів, що й Байєс, тому її MAP трохи інший, ніж у першому звіті (sonar 0.082 замість 0.087).
- Ранжування детерміноване: терміни й кандидати впорядковані, нічиї розв'язуються однаково
  в кожному запуску.
- `depends_on` побудовано за останнім комітом бази (знімок коду після всіх задач). В оцінці
  не використовується, призначений для навігації.

## Файли

- `common.py` — завантаження, поділ `modn`, токенізація, розбір ADF, G², метрики exp3
- `build_onto.py` — побудова `out/<project>/triples.txt`, `stats.json`, `eval.json` (тест; з `--dev` — dev)
- `evaluate.py` — підбір параметрів на `dev/`, тест лише з онтології, базові лінії, ablation → `results.csv`

`triples.txt` має формат `/flow ontology` (`s :: p :: o  [src: ...]`), тож його можна відкрити
в 1bcoder або вирії. Але вирій перетворює сутності на нижній регістр, тому шляхи файлів там
будуть у нижньому регістрі.
