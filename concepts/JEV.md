# JEV: сприйняття як третя роль у 1bcoder

**Компонент**: 1bcoder, команда `/jev` (і кваліфікатор `--jev` у flow)
**Дата**: 2026-10-02
**Статус**: Концепт. Нічого не реалізовано. Емпірично перевірено лише одне: `tev1:0.8b` швидкий і точний на чистому, невеликому контексті (ручний тест автора).

---

## 0. Коротко

Ollama 0.35 додала decision-моделі й ендпоінт `/v1/systemone`, сумісний із Jev API від TypeSafe. Така модель не пише текст: вона відповідає на закриті питання і повертає ймовірності. Цей документ пропонує вбудувати її в 1bcoder не як окрему фічу збоку, а як **третю роль** у розв'язанні задач:

> **LLM генерує → Jev сприймає → Python вирішує.**

Дієслово для цього — "джевити", так само як "гуглити": "джевнути план рубрикою tree_rules".

---

## 1. Навіщо: автомату бракує зору

Теза External Supervision у 1bcoder: "модель генерує ходи, автомат стежить за полем". Але автомат сам поля не бачить. Кожне його смислове рішення сьогодні спирається на одне з двох:

- **Проксі**: regex на `FAIL:`, косинус 0.85 у `glossary`, "містить код → вузол конкретний" у `deepagent`, детектор bare headings у `deepagent_tree`.
- **Самооцінку генератора**: модель сама вирішує, чи вона закінчила. Цей шлях уже провалився — organic leaf detection спростований трьома реальними прогонами (`DEEPAGENT_SPEC.md` §2.3).

Jev — це орган сприйняття. Він бере розмитий текстовий стан і перетворює його на типізований факт з ймовірністю, а детермінований Python розгалужується вже по цьому факту.

| Роль | Хто | Простір відповідей | Ціна | Калібрування |
|---|---|---|---|---|
| генерує | LLM | відкритий | дорого | немає |
| сприймає | Jev | закритий (питання з варіантами) | ~100 мс | ймовірності |
| вирішує | Python | — | безкоштовно | детермінований |

---

## 2. Три закони

**Закон 1. Суддя ≠ генератор; суддя видає число; поріг зовнішній.** Цей закон уточнює принцип "модель не вирішує, коли зупинитись", а не суперечить йому. Модель, яка генерувала текст, його не оцінює. Окрема decision-модель вимірює, а рішення приймає поріг, який поставила людина.

**Закон 2. Для малих моделей якість походить від відбору, а не від генерації.** 1B-модель не дасть доброго результату з одного пострілу, зате дасть 5–10 дешевих варіантів. Jev робить best-of-N економічно можливим: генеруємо кілька варіантів, джевимо, лишаємо кращі. Це та сама задача відбору з потоку (задача про перебірливу наречену), з якої почався `DEEPAGENT_SEARCH.md`.

**Закон 3. Рубрика пишеться один раз і застосовується будь-де.** Рубрика — це багаторазовий сенсор, а не промпт під конкретну задачу. Одна рубрика `tree_rules` може перевіряти план під час генерації, після генерації і в Alkonost.

---

## 3. Терміни

Під час обговорення слово "рубрика" вживалось для різних речей, і це спричинило плутанину. Тепер вживаємо його лише в класичному значенні: рубрика — це таблиця, де рядки — критерії, а стовпці — рівні.

| Термін | Що це | У Jev API |
|---|---|---|
| **рубрика** | контейнер критеріїв, один файл (напр. `CODE_REVIEW`) | один словник `questions` |
| **критерій** | одне правило, одне питання | одне іменоване питання |
| **рівні** | можливі відповіді на критерій з описом кожної | `criteria` всередині питання |
| **стан** (state) | текст, який оцінюємо | `state` |
| **показання** | що повернув jev на один критерій | одна відповідь |
| **вердикт** | зведення показань через пороги | обчислює Python, не модель |

## 4. Jev API: що відомо

Джерела: офіційний блог Ollama і робочий `curl`-приклад автора. Точні назви полів у відповіді треба звірити з реальною відповіддю сервера до реалізації.

**Запит:** `POST http://<host>/v1/systemone`

```json
{
  "model": "tev1:0.8b",
  "state": "текст, який оцінюємо",
  "questions": {
    "says_hello": { "type": "noul", "instructions": "...", "criteria": { "true": "...", "false": "..." } }
  },
  "keep_alive": "5m"
}
```

`questions` — це словник з іменованих питань, від 1 до 64 в одному запиті. Відповіді приходять під тими самими іменами.

**Три типи питань:**

| Тип | Для чого | Форма `criteria` | Що повертає |
|---|---|---|---|
| `noul` | так/ні з ймовірністю | необов'язковий словник `{"true": "...", "false": "..."}` | ймовірність істинності (напр. 0.997) |
| `choice` | вибір одного варіанта | обов'язковий словник `{"ключ": "опис варіанта", ...}` | обраний ключ, `probabilities` по всіх ключах, `confidence` |
| `score` | рівень на впорядкованій шкалі | обов'язковий **список** описів рівнів, від нижчого до вищого | число (зважене ймовірностями), `legend`, `probabilities`, `confidence` |

**Моделі на момент запуску:**

| Модель | Розмір | Примітка |
|---|---|---|
| `nimble` (Bespoke Labs) | 9B | найточніша, але не для CPU/малої пам'яті |
| `tev1:4b` (Together AI) | 4B | файнтюн Qwen3.5, точніший з двох tev1 |
| `tev1:0.8b` (Together AI) | 0.8B, 812 MB | **перевірено автором**: швидкий і точний, поки контекст чистий; на великому стані, ймовірно, доведеться переходити на 4b |

**Емпіричне спостереження автора.** Якщо звертатись до decision-моделі звичайним текстовим промптом ("Who is Jerry? options: a) cat b) dog c) rabbit d) mouse") без `/v1/systemone`, вона відповідає однією літерою. Річ не в обмеженні моделі: це звичайний completion-режим без того контракту, під який її навчали. Повна сила моделі доступна лише через структурований `questions` з описами варіантів у `criteria`. Звідси вимога до адаптера (§5).

## 5. Адаптер: завжди структурований JSON

Адаптер 1bcoder ніколи не надсилає decision-моделі вільний текст із варіантами. Будь-який вхід він компілює у словник `questions`. Входів два.

**(а) Рубрика-файл (§7)** — основний шлях. Критерії файлу компілюються у `questions` майже дослівно.

**(б) Швидке питання в рядку** — для дослідження, без файлу:

```
/jev "Чи містить цей текст налаштування MCP-сервера?"
```
Компілюється в одне `noul`-питання.

```
/jev "Яка це частина системи?" options: frontend, backend, database
```
Компілюється в одне `choice`-питання. Кожен варіант стає ключем, а описом варіанта поки що служить сама назва. Це вже краще за однолітерний режим, бо модель отримує правильний контракт, але гірше за рубрику з повними описами.

Технічно адаптер — це окремий модуль (`jev.py`) з однією функцією на кшталт `jev_ask(state, questions, model, host, timeout)`. Окремий модуль потрібен, щоб його могли імпортувати flow (так само, як `deepagent_test` імпортує `deepagent_code` через `importlib`), а не лише `chat.py`.

## 6. Команди

```
/jev <рубрика|N> [split:<розділювач>] [threshold:<0..1>]   джевнути останній вивід рубрикою
/jev "<питання>" [options: a, b, c]                         швидке питання без файлу
/jev list                                                   рубрики: глобальні, потім локальні, з номерами
/jev show <рубрика|N>                                       показати критерії рубрики

/jev model                                                  поточна decision-модель і її деталі
/jev model list                                             встановлені decision-моделі
/jev model set <назва|N>                                    вибрати і зберегти

/jev param                                                  показати налаштування
/jev param <ключ> <значення>                                змінити
/jev param clear                                            скинути до значень за замовчуванням

/jev on <рубрика>                                           watch: після кожної відповіді
/jev gate on <рубрика>                                      gate: FAIL: при непроходженні порогу
/jev off                                                    зняти прив'язки
```

**Номери.** Як і скрізь у 1bcoder, працює і назва, і номер: `/jev 3` і `/jev tree_rules` рівнозначні. Номер — позиція в списку `/jev list`, де спершу йдуть глобальні рубрики, потім локальні. Локальних рубрик мало, глобальні додаються рідко, тому зсуву номерів можна не боятись (рішення автора).

**Скрипти.** Окремий `/flow jev` не потрібен: `/script` уже виконує будь-які slash-команди, тож `/jev ...` працює всередині скрипта як є.

### 6.1 `/jev model`

- `/jev model list` бере перелік моделей з Ollama (`/api/tags`). **Відкрите питання:** чи позначає Ollama decision-моделі окремо (наприклад, окремою capability у `/api/show`). Якщо так — фільтруємо за нею. Якщо ні — список відомих назв (`nimble`, `tev1*`) плюс пробний запит до `/v1/systemone`.
- `/jev model` показує те, що повертає `/api/show` для вибраної моделі: розмір, квантизацію, контекст.
- `/jev model set` записує модель у налаштування (§6.2).

### 6.2 `/jev param`

| Ключ | Значення за замовчуванням | Призначення |
|---|---|---|
| `model` | не задано | decision-модель; без неї `/jev` повертає помилку, а не мовчки бере першу доступну (урок із Alkonost `runner.py`, де модель за замовчуванням виявилась reasoning-моделлю) |
| `host` | як основний `host` | decision-модель може жити на іншій машині |
| `timeout` | 30 с | збігається з поточним лімітом `_run_proc` |
| `keep_alive` | `5m` | передається в API; тримає модель у пам'яті між викликами gate |
| `threshold` | 0.5 | поріг за замовчуванням, якщо критерій не задав свій |
| `batch` | 64 | скільки критеріїв в одному запиті; менше значення ділить велику рубрику на кілька запитів (див. §11, питання про 20 критеріїв на 0.8b) |
| `on_error` | `fail` | що робить gate, коли jev недоступний: `fail` (блокувати) або `pass` (пропустити) |

**Де зберігати.** У `.1bcoder/config.yml` (проєкт) і `~/.1bcoder/config.yml` (глобально), як решту налаштувань. Але граматика цього файлу саморобна і дворівнева: верхньорівневі скаляри плюс секції `params`/`vars`/`hooks`/`procs`. Класти `jev_*` у `params` не варто, бо `params` передається моделі в чат-запитах. Чистіше додати нову секцію `jev:`. Це зміна в двох місцях одночасно: парсер у `chat.py` і його дзеркало в Alkonost `settings.py`, яке відтворює ту саму граматику, щоб не залежати від PyYAML.

## 7. Формат рубрики

Рубрика — YAML-файл. Розташування за тією самою конвенцією, що procs/agents/flows:
- `_bcoder_data/rubrics/` — глобальні, поставляються з пакетом;
- `.1bcoder/rubrics/` — локальні, лише для цього проєкту.

```yaml
name: TEACHING_STYLE
description: Стиль текстів навчального проєкту
threshold: 0.5            # за замовчуванням для всіх критеріїв
split: "## "              # як різати стан, якщо не задано в команді

criteria:
  - id: no_em_dash
    check: regex
    pattern: "—"
    fail_if: match
    message: "використано довге тире"

  - id: no_emoji
    check: regex
    pattern: "[\U0001F300-\U0001FAFF]"
    fail_if: match
    message: "використано емодзі"

  - id: narrative_not_bullets
    type: score
    instructions: "Чи викладено матеріал послідовною розповіддю там, де зміст цього вимагає?"
    levels:
      - "Розповідь розбита на буліт-списки без потреби"
      - "Частково списки, частково розповідь"
      - "Послідовна розповідь, списки лише там, де вони доречні"
    threshold: 0.6
```

**Два види критеріїв в одній рубриці.** Довге тире й емодзі ловить regex, і витрачати на них jev-виклик немає сенсу. "Буліти замість розповіді" — смислове судження, тут потрібен jev. Адаптер спершу проганяє механічні критерії, а до jev надсилає лише смислові. Якщо механічний критерій уже провалився, а рубрика працює як gate, jev можна взагалі не викликати.

**Компіляція у Jev API.** Кожен критерій з `check: jev` (за замовчуванням) стає одним питанням у `questions`: `id` → ім'я питання, `type` → тип, `instructions` → `instructions`, `levels` → `criteria` (список для `score`, словник для `choice`, `{true, false}` для `noul`).

**Вердикт.** Python, без моделі:
- для `noul` критерій пройдено, якщо ймовірність ≥ поріг;
- для `score` — якщо нормоване число ≥ поріг;
- для `choice` — якщо обраний ключ входить до `pass:` (список прохідних ключів у критерії).

Рубрика проходить, якщо пройдено всі її критерії.

### 7.1 Приклад: CODE_REVIEW (фрагмент)

```yaml
name: CODE_REVIEW
description: Перевірка змін коду перед комітом
criteria:
  - id: single_purpose
    type: noul
    instructions: "Чи всі зміни в цьому фрагменті служать одній меті?"
  - id: no_silent_except
    type: noul
    instructions: "Чи є тут перехоплення винятку, яке мовчки ковтає помилку?"
    criteria: { "true": "Є except без обробки або логування", "false": "Усі винятки оброблено або прокинуто далі" }
    pass_when: false
  - id: naming
    type: score
    instructions: "Наскільки імена відповідають конвенції цього файлу?"
    levels: ["Порушують", "Частково", "Відповідають"]
  - id: secret_in_code
    check: regex
    pattern: "(api_key|password|secret)\\s*=\\s*['\"][^'\"]+['\"]"
    fail_if: match
```

`pass_when: false` означає, що для цього `noul` прохідною відповіддю є "ні". Деякі критерії природніше формулювати як наявність проблеми.

## 8. Стан, розрізання, прив'язки

**Стан.** За замовчуванням `/jev` оцінює останній вивід (`_last_output`, а для відповіді моделі `last_reply`), так само як `/proc`. Тому `/jev` працює після будь-якої команди, без змін у самій команді:

```
/rag search kafka partitioning
/jev relevance split:"## "
```

**Розрізання (`split:`).** Вивід ріжеться на секції, і кожна джевиться окремо, зі свіжим контекстом. Варіанти: `"## "` (заголовки; можна взяти готовий `_parse_sections` з `deepagent_md`), `blank` (порожні рядки), `tokens:3000` (за розміром). Результат — таблиця: секція × критерій → показання. Це і є "стрім" з попередніх обговорень: окремий pipe-оператор не потрібен, бо стрім — це просто останній вивід, порізаний на шматки.

**Три прив'язки** (дзеркалять наявні режими `/proc`):

| Прив'язка | Команда | Коли | Наслідок |
|---|---|---|---|
| **ask** | `/jev <рубрика>` | вручну | показ таблиці |
| **watch** | `/jev on <рубрика>` | після кожної відповіді | показання логуються поруч з розмовою, нічого не блокують |
| **gate** | `/jev gate on <рубрика>` | після відповіді, до ACTION | контракт gate: тиша = PASS, рядки `FAIL: ...` = провал і ретрай кроку |

Перемикання "режим LLM / режим jev" під час дослідження — це вибір прив'язки, а не новий інструмент під кожну задачу.

Рядок `FAIL:` повинен називати критерій і показання, наприклад: `FAIL: CODE_REVIEW.no_silent_except — 0.91 що проблема є (поріг 0.5)`. Це інформативніше за звичайний бінарний gate, і ретрай отримує точну підказку, а не загальне "не пройшло".

## 9. Куди вставити `--jev`: практичні застосування

Правило: кваліфікатор `--jev <рубрика>` має сенс лише там, де в команді є **власний внутрішній цикл**, якого ззовні не видно. Там jev працює *під час* і може спричинити ретрай або пропуск. Для всього іншого достатньо `/jev` *після* команди. Це та сама пара режимів, що вже є в radogast: `--dedup` всередині flow і `radogast plan analyze` над готовим результатом.

| Команда | Що джевимо | Режим | Що дає |
|---|---|---|---|
| `deepagent_md` / `deepagent_tree` / `deepagent_tree_md` | кожен новий вузол | `--jev tree_rules`, всередині | Правила PART-OF / HOMOGENEITY / CEILING / FLOOR / NO SMEARING (`DEEPAGENT_TREE.md` §2) уперше перевіряються механічно. Ретрай з тією ж точки, що й `--dedup`, з підказкою, яке саме правило порушено. Сюди ж — детектор мета-преамбули ("Okay, here's a breakdown..."), яка в gemma3:1b була у 91% файлів. |
| `deepagent_spec` | кожен spec-юніт | `--jev spec_quality`, всередині | Чи критерії приймання перевірні, чи задані межі. Окремо ловить замасковану відмову ("No actionable specification available..."), яка проходить усі структурні перевірки (`DEEPAGENT_TREE.md` §3.4). |

## 10. Як перевірити, а не повірити

Для першого експерименту вже є розмічена ground truth. `DEEPAGENT_TREE.md` §3 фіксує відомі дефекти планів RRTrack, знайдені вручну:
- надлишковість у гілці 2 plan4 (шість сиблінгів переказують той самий конвеєр);
- винайдений TCP/DNS/TLS-клієнт у гілці 1 plan4;
- bare headings у plan1 і plan5;
- мета-преамбули у 218 з 240 файлів plan5.

Експеримент: зібрати рубрику `tree_rules`, прогнати її по цих планах на `tev1:0.8b` і `tev1:4b` і порахувати, скільки відомих дефектів jev знаходить і скільки дає хибних спрацювань. Заодно цей прогін відповість на три відкриті питання з §11:
1. чи відкалібровані ймовірності tev1 настільки, щоб на них ставити пороги;
2. чи тримається якість, коли в одному запиті 20 критеріїв, а не 1–3;
3. де межа розміру стану для 0.8b.

Для дисертації це результат, який можна цитувати: виміряна точність сенсора на відомих дефектах, а не враження.

## 11. Відкриті питання

1. **`_last_output`.** Його точно виставляють `webask`, `webindex` і procs. Чи виставляють `/rag`, `/find`, `/map` та інші команди, не перевірено. Якщо ні, у кожну потрібен один рядок.
2. **Виявлення decision-моделей** для `/jev model list` (§6.1).
3. **Граматика `config.yml`**: нова секція `jev:` у парсері `chat.py` і в дзеркалі Alkonost `settings.py` (§6.2).
4. **`on_error` для gate.** Що робити, коли jev недоступний. За замовчуванням пропоновано `fail`, тобто блокувати; треба звірити з тим, як `_run_proc` зараз відрізняє збій інфраструктури від справжнього PASS.
5. **Точні назви полів відповіді** `/v1/systemone` звірити з реальною відповіддю сервера.
6. **Великий стан на 0.8b.** Автор бачив, що якість падає, коли контекст перевантажений. Чи `split:` повністю це вирішує, чи деяким рубрикам потрібна 4b за замовчуванням.
7. **Швидкі питання з `options:`** (§5б) поки використовують назву варіанта як його опис. Можливо, варто дозволити `options: frontend="UI на Kotlin", backend="Spring Boot"`.
8. **Таймаут 30 с** у `_run_proc` при gate на кожен ACTION: для tev1 має вистачати, але для `nimble` на CPU — не факт.
