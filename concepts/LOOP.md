# LOOP: стрім з будь-чого, дія над кожним елементом

**Компонент**: 1bcoder, команда `/loop`
**Дата**: 2026-10-02
**Статус**: Концепт. Нічого не реалізовано.

---

## 0. Коротко

Будь-яку структуру, де щось перелічується і ріжеться розділювачем (папку на файли, файл на чанки, відповідь на секції), можна перетворити на **стрім** — упорядкований список елементів. Кожен елемент обробляється окремо і зі свіжим контекстом, однією з дій:

- `--llm "<промпт>"` — модель генерує текст;
- `--jev <рубрика>` — decision-модель перевіряє критерії й повертає ймовірності (див. `JEV.md`);
- `--radogast <ціль>` — геометричний аналіз ембедінгами (§6).

```
/loop dir:concepts/ file:*.md split:"## " --llm "випиши все про налаштування MCP-сервера" --out mcp.md
```

Це звичайний цикл, і саме тому він і потрібен. Ми довго будували для нього складну рамку (`DEEPAGENT_FOREACH_REVIEW.md`: engine/instance, YAML-рубрики, словник `source/filter/map/flatmap`, pipe-оператор), але насправді задача звелась до однієї команди з чотирма частинами: **джерело → різак → дія → вивід**.

---

## 1. Навіщо

Мала модель не втримає в голові папку з сорока файлами чи відповідь `/rag` на десять чанків. Зате один файл чи одну секцію за раз вона опрацює нормально. Відповідно, `/loop` робить для довільних даних те саме, що `deepagent_*` роблять для планів: розбиває задачу на шматки, де кожен поміщається в чистий контекст, і зберігає стан на диску, а не в розмові.

Різниця з `deepagent_*` у тому, що `/loop` нічого не декомпозує сам. Структура вже існує (файли, секції, чанки), і її треба лише перелічити. Тому `/loop` — це команда, а не flow.

---

## 2. Елемент стріму

```
Element(id, source, index, total, text)
```

- `id` стабільний і читабельний: `concepts/JEV.md#3` (третя секція файлу), `logs/app.log@2` (другий чанк), `last#5`.
- `index`/`total` використовуються для прогресу і для breadcrumb у промпті ("секція 3 з 12 файлу JEV.md").
- Стрім **матеріалізується одразу, до обробки**: спершу будується повний список елементів, потім вони обробляються. Усі джерела з §3 скінченні, тож лінивий стрім тут не потрібен, а загальна кількість відома заздалегідь. Необмежений веб-пошук — окрема задача (`DEEPAGENT_SEARCH.md`), і це не `/loop`.

---

## 3. Джерела

| Джерело | Що дає | Приклад |
|---|---|---|
| `dir:<шлях>` | один елемент на файл; `file:<glob>` фільтрує, `-r` шукає рекурсивно | `dir:~/bigdata/logs/2025/november/frontend/ file:*.log` |
| `file:<шлях>` | один елемент на весь файл, тому зазвичай разом зі `split:` | `file:big_book.txt split:tokens:3000` |
| `last` | останній вивід (`_last_output`) | `last split:"## "` |
| `cmd:"<команда>"` | виконати slash-команду і взяти її вивід як джерело | `cmd:"/find mcp -c"` |

### 3.1 Як перехопити вивід `cmd:`

`/rag`, `/find`, `/map` та інші команди наприкінці питають "add to context? [Y/n]", і текст потрапляє в контекст лише після Y. Перевірено в коді: усі вони йдуть через один помічник, `_confirm(prompt, ctx_add=result)` (`chat.py`, рядок 3735), і **повний текст виводу передається туди параметром `ctx_add`**.

Отже, для перехоплення достатньо однієї точки, а не зміни кожної команди:

1. `/loop` вмикає прапорець захоплення і викликає команду з `cmd:`.
2. `_confirm`, побачивши прапорець, зберігає `ctx_add` як джерело стріму, нічого не питає і повертає "ні": у контекст розмови вивід не потрапляє.
3. `/loop` вимикає прапорець і ріже захоплений текст.

Побічний ефект корисний і для `JEV.md`. Якщо `_confirm` завжди запам'ятовує останній запропонований `ctx_add` (незалежно від відповіді Y/n), то `/jev` і `/loop last` працюватимуть після `/rag`/`/find`/`/map`, навіть якщо користувач відповів "n". Це закриває відкрите питання 1 з `JEV.md` §11 однією зміною замість правок у кожній команді.

## 4. Різаки (`split:`)

| Різак | Ріже по | Примітка |
|---|---|---|
| `"## "` | рядках, що починаються з цього префікса | можна взяти готовий `_parse_sections` з `deepagent_md` (він також обробляє першу секцію без номера) |
| `re:"<regex>"` | регулярному виразу на початку рядка | напр. `re:"^## \d+\."` |
| `blank` | порожніх рядках (абзацах) | |
| `line` | кожному рядку | для логів, списків, виводу `/find` |
| `tokens:N` | розміру, приблизно N токенів | ріже на межі рядка, не посеред слова |

Без `split:` один файл — це один елемент.

**Вкладене різання.** `dir:` + `split:` означає: спершу папку на файли, потім кожен файл на секції. `id` тоді має вигляд `шлях#секція`.

**Завеликий елемент.** Якщо елемент після різання все одно більший за бюджет (`--max-tokens`, за замовчуванням близько половини `num_ctx`), він автоматично доріжеться по `tokens:`. Кожен шматок отримує breadcrumb: "частина 2 з 5 секції 3 файлу X". Цей прийом позиційної підказки вже працює в `deepagent_tree`.

## 5. Дії

### 5.1 `--llm "<промпт>"`

Для кожного елемента виконується один виклик моделі з чистим контекстом:

```
system: поточна роль
user:   <промпт>
        [breadcrumb: елемент 3 з 12, джерело ...]
        ---
        <текст елемента>
```

Зразок уже є: `webask.py` збирає тимчасові `temp_msgs` і викликає `chat._stream_chat(temp_msgs)`, не чіпаючи `chat.messages`. `/loop --llm` робить те саме, тільки для кожного елемента окремо.

`--ctx N` додає останні N повідомлень розмови до кожного виклику, так само як у `deepagent_md`. Це корисно, коли перед `/loop` ви обговорили з моделлю, що саме шукаєте. За замовчуванням 0.

### 5.2 `--jev <рубрика|"питання">`

Для кожного елемента рубрика компілюється в `questions` і надсилається одним запитом `/v1/systemone` (деталі в `JEV.md` §5–7). Результат — показання по кожному критерію і вердикт.

### 5.3 Комбінація: jev як фільтр перед llm

Якщо задано обидва, `--jev` спрацьовує першим як фільтр, і `--llm` викликається лише для елементів, що пройшли перевірку. Це закон 2 з `JEV.md`: дешеве сприйняття відсіює, дорога генерація працює тільки над тим, що лишилось.

```
/loop cmd:"/find mcp -c" split:blank --jev "Чи містить ця секція налаштування MCP-сервера?" --llm "Витягни налаштування MCP-сервера" --out settings.txt
```

`--keep pass|fail|all` вирішує, які елементи йдуть далі. За замовчуванням `pass`. `fail` теж корисний: наприклад, щоб показати лише ті секції, що провалили рубрику стилю.

## 6. Radogast: аналіз зв'язків між текстами

Radogast меряє відношення між текстами: елемента до цілі, елемента до елемента. Тому він природно працює на двох рівнях, і саме це пояснює, як його "натравити" на стрім.

**На рівні елемента — відстань до цілі.** Ціль — це `goal`, `key_terms` і `out_of_scope` (той самий формат `task.yaml`, що редагує вкладка Radogast в Alkonost). Для кожного елемента рахується близькість ембедінга до `goal` і перевіряються збіги з `out_of_scope`. Це геометричний фільтр, дешевший за jev, бо не потребує жодного виклику моделі, лише ембедінги. Його можна поставити перед jev і llm як перший грубий відсів.

**На рівні всього стріму — те, що не видно з одного елемента:**
- дублікати між елементами: матриця схожості плюс кластеризація за порогом (`similarity_matrix` і `cluster_by_threshold` з `radogast.metrics.similarity`, які вже використовує `glossary.py`);
- покриття `key_terms`: які терміни з цілі не з'явились у жодному елементі;
- дрейф: які елементи найдальше від цілі.

Другий рівень не є дією над елементом. Він виконується **один раз після циклу**, над усіма елементами разом, і дає звіт. По суті це `radogast plan analyze`, тільки над довільним стрімом, а не лише над деревом плану.

```
/loop dir:.1bcoder/planMD/plan4/ file:item_*.md --radogast .1bcoder/planMD/plan4/.radogast/task.yaml
```

Для плану plan4 такий прогін мав би знайти саме ту надлишковість у гілці 2, яку в `DEEPAGENT_TREE.md` §3.2 помітили лише людським оком.

## 7. Вивід

**На екран** — завжди: компактний рядок на елемент (`[12/48] concepts/JEV.md#3 — PASS 0.82`) і підсумкова таблиця.

**`--out <файл>`** — два файли поруч:
- `<файл>.jsonl` — сирий лог, один рядок на елемент, дописується **одразу** після обробки елемента: `id`, дія, результат llm або показання jev, скори radogast;
- `<файл>` — відрендерений результат у форматі за розширенням: `.md` (заголовок елемента і текст), `.csv` (рядок на елемент, стовпці — критерії), `.txt` (лише текст llm).

Рендер — це детермінований прохід по jsonl без жодного виклику моделі, і його можна повторити з іншим форматом без повторної обробки. Це той самий принцип "сирий лог зараз, артефакт потім", що в `DEEPAGENT_SEARCH.md` §5.

**У контекст** — наприкінці, як у всіх команд 1bcoder: "add to context? [Y/n]" з підсумком, а `-y` пропускає питання в скриптах.

## 8. Прогрес і відновлення

Загальна кількість елементів відома до старту (§2), тому прогрес чесний: `[12/48] 25%`.

**Відновлення.** Якщо `--out` вказано і `<файл>.jsonl` вже існує, `/loop` пропускає елементи, чий `id` уже є в лозі. Окремий файл стану не потрібен: лог і є станом. Принцип той самий, що в усіх `deepagent_*`: "уже оброблено" означає "вже є на диску".

Ctrl+C зупиняє цикл після поточного елемента. Повторний запуск тієї самої команди продовжить роботу з місця зупинки.

---

## 9. Паралельність (необов'язково)

Елементи незалежні, тому їх можна роздати воркерам через наявний `--profile`, round-robin, як у `deepagent_md`. Для `--jev` це майже не потрібно, бо він і так швидкий. Для `--llm` на кількох машинах — корисно.

---

## 10. Зв'язок з іншими командами

- **`/jev <рубрика> split:...`** (`JEV.md` §8) — це скорочення для `/loop last split:... --jev <рубрика>`. Обидві форми лишаються: коротка для щоденного вжитку, `/loop` для всього складнішого.
- **`scan`** — його основну дію (сумаризувати кожен чанк, за `--query` відкинути нерелевантні) можна виразити через `/loop file:... split:tokens:... --llm "..."`. Але `scan` лишається як є: він має рекурсивне стискання (`--rounds`, `--target`), якого в `/loop` немає, і ним користуються.
- **`deepagent_search`** — не `/loop`: у нього джерело необмежене і саме себе розширює (`add:`, pseudo-relevance feedback).
- **`/proc`** — обробляє один блок тексту за раз і не вміє ітерувати. `/loop` дає саме ітерацію.
- **`DEEPAGENT_FOREACH_REVIEW.md`** — надто складна рамка для цієї ж ідеї. Корисне з неї перенесено сюди: адаптери джерел, різання з breadcrumb, сирий лог плюс рендер. Решту (engine/instance, YAML-рубрики для LLM, pipe-оператор) замінюють `/loop` і `JEV.md`.

## 11. Принцип реалізації

Одна команда в `chat.py` (`_cmd_loop`) і чотири функції, кожна з яких відповідає за свою частину:

```python
elements = _loop_collect(source_spec)        # §3: dir / file / last / cmd -> list[Element]
elements = _loop_split(elements, cutter)     # §4: різання + дорізання завеликих
for el in elements:                          # §8: пропуск уже оброблених id
    result = _loop_apply(el, actions)        # §5–6: radogast-фільтр -> jev -> llm
    _loop_append(out_jsonl, el, result)      # §7: одразу на диск
_loop_report(elements, actions)              # §6: radogast на рівні стріму, підсумкова таблиця
_loop_render(out_jsonl, out_file)            # §7: детермінований рендер
```

Що береться готовим:

| Потреба | Звідки |
|---|---|
| виклик LLM з чистим контекстом | патерн `temp_msgs` + `chat._stream_chat` з `webask.py` |
| різання по `## N.` | `_parse_sections` з `deepagent_md.py` |
| виклик jev | адаптер `jev.py` з `JEV.md` §5 |
| схожість і кластери | `radogast.metrics.similarity` (`similarity_matrix`, `cluster_by_threshold`), як у `glossary.py` |
| перехоплення виводу команд | один прапорець у `_confirm` (§3.1) |
| воркери | наявний `--profile` |

Нове лише одне — сама команда `/loop` та прапорець у `_confirm`.

# Відфільтрувати вивід /find через jev і витягнути налаштування

## 13. Відкриті питання

1. **Перехоплення через `_confirm`** (§3.1) не перевірено на всіх командах. Якщо якась команда друкує результат, не передаючи його в `ctx_add`, її вивід `cmd:` не захопить. Потрібно пройтись по всіх викликах `_confirm`.
2. **`cmd:` з командами, що питають щось ще**, крім "add to context?" (вибір зі списку, підтвердження дії). Мабуть, такі команди в `cmd:` треба забороняти або вимагати від них `-y`.
3. **Бюджет елемента за замовчуванням** (половина `num_ctx`) — це здогадка. Для jev на `tev1:0.8b` межа, імовірно, значно менша (автор бачив падіння якості на перевантаженому контексті).
4. **Радогаст на рівні елемента**: який поріг близькості до `goal` вважати "релевантним" без калібрування на реальних даних.
5. **Порядок дій** зафіксовано як radogast → jev → llm. Чи потрібна можливість змінювати його, поки невідомо.
6. **Що віддавати в контекст наприкінці** (§7): весь результат, лише підсумкову таблицю чи лише елементи, що пройшли фільтр. Для великих стрімів увесь результат може не вміститися.
