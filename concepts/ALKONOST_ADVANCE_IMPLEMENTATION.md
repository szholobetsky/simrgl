# ALKONOST_ADVANCE — Implementation Working Doc

Робочий документ для покрокової реалізації `ALKONOST_ADVANCE.md`. Формат: під кожним пунктом спочатку те, що вже відомо/вирішено (з посиланням на код чи попередню розмову), потім — **Питання** там, де рішення ще нема. Наступна сесія (можливо з чистим контекстом, можливо через скіл `grill-me`) дописує відповіді прямо під питаннями.

Зафіксовані рішення цієї сесії:
- **Гамаюн скасовано повністю.** Ніякого окремого продукту/назви — все йде у вкладки Алконоста.
- **Інтеграційні скрипти називаються `alkonost_*.txt`**, не `gamayun_*.txt` (виправлено і в `ALKONOST_ADVANCE.md`).

## 0. Загальне / наскрізне

**Відомо:**
- Стек — Flask + vanilla JS, той самий стиль, що вже в `alkonost/` (без збірки, без фреймворків).
- Механізм запуску всіх flow — `1bcoder --scriptapply alkonost_<action>.txt --param k=v ...`, без `--host`/`--model` (їх бере `.1bcoder/config.yml`/`~/.1bcoder/config.yml`, які редагує SETTINGS-вкладка). Деталі — `ALKONOST_ADVANCE.md` §3.2.
- Скрипти `.1bcoder/scripts/alkonost_*.txt` — тонкі (2-4 рядки `/flow ...`), створюються Алконостом при першому запуску, якщо відсутні (та сама конвенція, що й `colors.md`).

**Питання:**
- Чи тримати весь новий бекенд-код в одному пласкому `alkonost/`-пакеті (як зараз — `tasks.py`, `spec.py`, `colors.py`, `discovery.py`...), чи розбивати на підпакети (`alkonost/plan/`, `alkonost/settings/`...), раз обсяг суттєво росте?
- Чи є в тебе вже встановлений/налаштований Ollama-бекенд, яким я можу реально прогнати `--scriptapply` наскрізно, чи вважати, що такого нема і перевіряти лише структурно (unit-тести на файлові операції, без реального LLM-виклику)?

## 1. PLAN tab

**Відомо:**
- Запускає `deepagent_md` (опційно, проза-дослідження) → `deepagent_tree`/`deepagent_tree_md` через `alkonost_plan_*.txt`.
- Дерево файлів — переюзати `alkonost/planmd.py` (`build_tree`, `read_item`, `write_item_raw`) без змін, воно вже читає/пише `item_<id>.md`.
- `redo <node_id>` і `--review` вже реалізовані в 1bcoder (`DEEPAGENT_AND_DEEPAGENT_MD.md` §9) для `deepagent_md`/`deepagent_tree_md`/`deepagent_tree` — залишається тільки UI-кнопки + wrapper-скрипти.
- Фінальний batch-аналіз radogast — `radogast.plan_analyzer.analyze_plan(plan_dir)` напряму як бібліотека, не субпроцес.

**Питання:**
- Який flow за замовчуванням для кнопки "Generate Plan" — `deepagent_tree_md` (повні документи), `deepagent_tree` (те саме, інший генераційний промпт), чи вибір з випадаючого списку всіх трьох (+ `deepagent_md`)?
- Скільки прапорців flow показувати в формі запуску — всі (`--maxdepth`, `--profile`, `--web`, `--rag`, `--rw`, `--ctx`, `--scan`, `--prescan`, `--ref`, `--finalize`, `--noposition`...), чи курований підмножина + "advanced" розгортка?
- **Прогрес живого прогону.** Ми свідомо відмовились від live IPC (§3.2 в ADVANCE) — субпроцес `--scriptapply` летить у фоні без жодного зв'язку з UI. Як тоді PLAN-вкладка дізнається "процес ще працює / уже завершився / впав з помилкою"? Варіанти: (а) клієнтський polling `/api/planmd/tree` кожні N секунд, поки триває запуск; (б) редірект stdout субпроцесу в лог-файл + новий ендпоінт `/api/plan_log` (tail). Треба вибрати один, чи обидва.
- **Найважливіше технічне питання цього документа.** `--review`'s інтерактивний y/n/b/a запит читає з stdin. Я сам це писав (`_review_prompt()` у `deepagent_md.py`/`deepagent_tree.py`/`deepagent_tree_md.py`): `if not sys.stdin.isatty(): print("no interactive terminal -- auto-continuing"); return 'y'`. Тобто якщо запустити `--review`-прогін через `--scriptapply` як фоновий субпроцес без прив'язаного терміналу (а це буде саме так, якщо запускає Flask-сервер) — **воно автоматично підтверджує кожен вузол як `y`, ревью фактично не працює**. Кнопка "--review" на PLAN-вкладці зараз була б обманкою. Треба або (а) новий вхідний канал для `--review` — не stdin, а маленький control-файл/черга, яку `_review_prompt()` перевіряє замість `input()`, і Алконост туди пише відповідь користувача; або (б) чесно прибрати `--review`-кнопку з v1 UI, лишити тільки non-interactive кнопки (`redo`, batch radogast-аналіз), і `--review` лишається command-line-only фічею, поки цей канал не зроблено. Це рішення реально впливає на обсяг роботи.

## 2. SPEC tab (axis-plan)

**Відомо:**
- Концепція з `ALKONOST_ADVANCE.md` §1-2: `deepagent_spec` зараз сліпо йде за секціями дослідницького плану (1:1), а треба — за окремим, новим "axis-план"-деревом (інша вісь нарізки, напр. архітектурна замість user-facing), яке генерується окремим `deepagent`-проходом, обов'язково затверджується користувачем, і лінкується назад до дослідницького плану через radogast-similarity і/або RAG.
- Це резолвить відкрите "open question 6" з `DEEPAGENT_SPEC.md` §2.5/§2.6 (лінковка C4-дерева і epic/story-дерева).

**Питання (найбільше з усього документа — це і є той "вектор-поворот тексту", який завтра розбираємо детально):**
- Яким саме двигуном генерувати axis-план — `deepagent` (лише лейбли, найлегший) чи `deepagent_md` (повні документи)? `ALKONOST_ADVANCE.md` §5.1 сам це залишає відкритим.
- Як конкретно виглядає крок "затвердити і розширити план" в UI — inline-редагування дерева (додати/видалити/перейменувати вузли) до лінковки, чи спочатку лінковка, а редагування потім (ризик: перейменування вузла осиротить його лінки)?
- radogast-similarity vs RAG (simargl) для лінковки — використовувати один, чи обидва одночасно з підсвіченням розбіжності (той самий принцип "показуй невизначеність, не розв'язуй мовчки" з §9 deepagent-документа)?
- Де саме на диску живе axis-план — новий `.1bcoder/axis/<plan>/`, чи всередині `spec/`?
- Чи `deepagent_spec.py` взагалі треба міняти (щоб він читав axis-план замість research-плану), чи можна обійтись тим, що axis-план генерує СВОЇ Ж item_x.x-файли в окремій теці, і `deepagent_spec` просто запускається НАД тією текою замість оригінальної planMD (без жодних змін у самому deepagent_spec.py)? Другий варіант набагато дешевший — вартий розгляду першим.

**Виправлення під час реалізації (2026-09-09):** другий варіант реалізовано, але не так, як тут написано. Плоский `deepagent` (лише лейбли) пише ОДИН файл `deepplan.md`, а не `item_<id>.md`-дерево — під нього довелось би писати окремий парсер/viewer, чого MVP уникає. Тому axis-план тепер генерується через **`deepagent_md`** (не плоский `deepagent`) — це вже дає повний `item_<id>.md`-конвент, той самий tree-viewer/редактор перевикористовується без жодних змін. Окремої теки `.1bcoder/axis/` теж нема — `deepagent_md` не має прапорця для теки виводу, тож axis-план — це просто ЗВИЧАЙНИЙ план під `.1bcoder/planMD/planN/`, позначений сайдкар-файлом `_alkonost_role.txt` = `"axis"` (пише сам алконост, не 1bcoder). "Seed from existing plan" на PLAN-вкладці підставляє в поле задачі текст кореневої задачі обраного дослідницького плану + інструкцію нарізати за архітектурною/реалізаційною віссю. Автопошук/лінковка через radogast/RAG — не реалізовано, як і планувалось.

## 4. ARCHITECT tab

**Відомо (з дослідження цієї сесії):** `deepagent_architect` має власний фіксований 5-рівневий пайплайн (`interface→abstract→approach→class→method`), власну систему резюме через claim-файли (`--next`/`--loop`, не `resume`/`continue`), і НЕ має numbered-section parent→child зв'язку — тобто `redo`'s семантика "піддерево" тут не мапиться так само напряму, як у tree-двигунах.

**Питання:**
- `redo`/`--review` для `deepagent_architect.py` **ще не реалізовано в 1bcoder взагалі** (§9 deepagent-документа покриває лише md/tree_md/tree/spec/test). Чи варто спочатку зробити engine-рівень для architect (окремий дизайн, бо структура інша — фіксований лінійний пайплайн, не дерево), перш ніж малювати цю вкладку? Чи ARCHITECT-вкладка v1 обходиться взагалі без redo/review, лише переглядом файлів і запуском `--next`/`--loop`?

## 5. CODE tab

**Відомо:** `deepagent_code.py` має реальні dotted node-id, LLM на вузол, і справжній parent→child зв'язок (дитячий код парситься з батьківського) — структурно добре підходить під `redo`/`--review` (Tier 1, з піддеревом).

**Питання:**
- Так само як з ARCHITECT — `redo`/`--review` для `deepagent_code.py` **ще не реалізовано**. Робимо це як окрему підзадачу (за тим самим патерном, що й для md/tree/tree_md) до чи паралельно з CODE-вкладкою?

## 6. TEST tab

**Відомо:** `deepagent_test.py` вже має `redo`/`--review` (Tier 2, зроблено цієї сесії) — двигунова частина готова.

**Питання:** немає суттєвих — тільки та сама stdin/isatty-проблема з п.1, якщо `--review` тут теж плануємо в UI.

## 7. SETTINGS tab

**Відомо:** два окремі стори — `.1bcoder/config.yml`/`~/.1bcoder/config.yml` (host/model/ctx/params) і `~/.alkonost/config.json` (тема, майбутня мова). Merge-запис, ніколи не чіпати `vars`/`procs`/`hooks`/`active_project`.

**Питання:**
- Показувати в UI взагалі `vars`/`procs`/`hooks`/`active_project`, чи повністю ховати їх (моя схильність — ховати, це не "налаштування", а робочий стан сесії, редагувати через GUI ризиковано) — підтвердь.
- Один глобальний вибір моделі на все, чи можливість задати різну модель per-flow (напр. дешевшу для TEST, сильнішу для SPEC)? Раніше в розмові про pi/віддалені машини звучало, що гнучкість per-stage може бути потрібна.
