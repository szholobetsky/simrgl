## 1. Задача і ідея

**Задача** (та сама, що й у всій дисертації): за текстом задачі з трекера (Jira, GitHub Issues)
передбачити, які файли й модулі коду доведеться змінити.

**Проблема, яку розв'язує Гамаюн.** Мова задач і мова коду різні. У задачі пишуть «sticky scroll»,
у коді — `StickyScrollController`. Ембедінги (Симаргл) частково долають цей розрив, але не пояснюють,
*чому* вони запропонували файл. LLM може побудувати онтологію з тексту, але вона повільна, вигадує
факти й не дає критерію, за яким присудок «правильний».

**Ідея Гамаюна.** Історія проєкту — це тисячі вже розв'язаних задач, для кожної відомо, які файли
змінились. Якщо слово «scanner» у тексті задачі *статистично значуще* частіше трапляється разом зі
змінами в модулі `sonar-scanner-engine`, ніж це можна пояснити випадком, — це факт про проєкт.
Записуємо його як трійку:

```
term:scanner :: characterizes :: module:sonar-scanner-engine  [src: n=202;df=381;g2=807.3;lift=10.96]
```

**Головний принцип: присудок — це операційне означення.** Ми не питаємо «чи правда, що scanner
характеризує цей модуль» у когось розумного. Ми задаємо *формулу над даними* і *поріг*. Трійка
з'являється тоді й лише тоді, коли формула перевищила поріг, а в `[src: ...]` записано числа, через
які це сталося. Будь-хто може перерахувати й оскаржити кожну трійку. Це і є відповідь на питання
«за якими критеріями визначати присудок між об'єктами»: критерій — це тест значущості, а не думка.

## 2. Звідки беруться дані

Бази `sonar.db`, `flink.db` мають дві таблиці:

| Таблиця | Поля | Що це |
|---|---|---|
| `TASK` | `NAME`, `TITLE`, `DESCRIPTION`, `COMMENTS` | задачі з трекера (`SONAR-23469`) |
| `COMMITS` | `SHA`, `AUTHOR_NAME`, `CMT_DATE`, `MESSAGE`, `PATH`, `DIFF`, `TASK_NAME` | **один рядок на пару (коміт, файл)** |

Для кожної задачі збираємо множину змінених файлів: усі `PATH` рядків `COMMITS` з її `TASK_NAME`.
Коміти без `TASK_NAME` не використовуємо: вони можуть належати тестовій задачі й «підглянути» її
відповідь.

Три рівні цілей (від грубого до точного):

- **модуль** — коренева папка шляху (`server/sonar-web/src/.../Foo.ts` → `server`), як у exp3;
- **папка** — шлях без імені файлу (`server/sonar-web/src/...`);
- **файл** — повний шлях.

Обсяги: sonar — 9799 задач, 469 836 рядків комітів, у середньому 18.6 файлу на задачу;
flink — 17 073 задачі, 372 550 рядків, 12.2 файлу на задачу.

## 3. Підготовка тексту: розбір ADF і токенізація

### 3.1 Що таке ADF і навіщо його розбирати

**ADF (Atlassian Document Format)** — формат, у якому сучасна Jira зберігає форматований текст.
Це не простий текст, а *дерево*: документ складається з абзаців, абзац — з текстових шматків,
шматок може мати позначки (жирний, код), між ними можуть бути картинки, списки, переноси рядків.

У `sonar.db` **усі 8041 непорожні описи** збережено як Python-запис такого дерева:

```python
{'type': 'doc', 'version': 1, 'content': [
    {'type': 'paragraph', 'content': [
        {'type': 'text', 'text': 'I have a portfolio, with a sub-portfolio, ...'}]},
    {'type': 'mediaSingle', 'attrs': {'layout': 'center'}, 'content': [
        {'type': 'media', 'attrs': {'id': '95c7b7e7-...', 'height': 183, 'width': 200}}]},
    {'type': 'paragraph', 'content': [{'type': 'text', 'text': 'and in the structure interface '}]}]}
```

Справжній текст задачі — лише значення полів `'text'`. Усе інше (`mediaSingle`, `hardBreak`,
`bulletList`, `listItem`, ідентифікатори картинок, розміри) — службова розмітка. **Якщо її не прибрати,
вона стає «термінами»**, причому дуже частими. У першій версії онтології найсильнішими зв'язками були
`mediasingle :: characterizes :: server` і `bulletlist :: narrower_than :: listitem`: статистика чесно
знайшла закономірність, але це закономірність *формату*, а не проєкту.

**Алгоритм розбору — обхід дерева в глибину зі стеком:**

```
1. node ← ast.literal_eval(рядок)        # безпечно перетворює Python-запис на словник
2. стек ← [node]; результат ← []
3. поки стек не порожній:
     n ← стек.pop()
     якщо n — словник:
         якщо в n є 'text' → додати n['text'] до результату
         покласти дочірні вузли n['content'] у стек (у зворотному порядку,
             щоб текст вийшов у правильній послідовності)
     якщо n — список: покласти його елементи у стек (теж у зворотному порядку)
4. повернути ' '.join(результат)
```

Чому стек, а не рекурсія: глибина дерева може бути великою, а рекурсія в Python обмежена ~1000 рівнями.
Чому `ast.literal_eval`, а не `eval`: `literal_eval` розбирає лише літерали (рядки, числа, списки,
словники) і не виконує код — небезпечний рядок не зможе нічого запустити. Якщо запис пошкоджений,
є запасний варіант: регулярний вираз, що витягує всі `'text': '...'`.

> **Побічна знахідка для дисертації.** Якщо exp3 вбудовував `DESCRIPTION` без такого розбору,
> BGE отримував у тексті розмітку ADF. Це варто перевірити.

### 3.2 Токенізація

**Токен** — одиниця тексту, з якою працює статистика. У Гамаюна токен — слово:

1. Беремо всі послідовності `[A-Za-z][A-Za-z0-9_]{2,}` (слово з літери, щонайменше 3 символи).
2. Переводимо в нижній регістр, викидаємо **стоп-слова** (`the`, `with`, `should`, `http`, ...) —
   вони є майже в кожній задачі й нічого не розрізняють.
3. **Розбиваємо ідентифікатори.** Задачі часто цитують код: «NPE in `QualityGateDao`». Регулярний
   вираз `[A-Z]+(?=[A-Z][a-z])|[A-Z]?[a-z]+|[A-Z]+|\d+` ділить camelCase на частини:
   `QualityGateDao` → `quality`, `gate`, `dao`; `snake_case` ділиться за `_`. У множину термінів задачі
   йдуть і ціле слово (`qualitygatedao`), і його частини.
4. Кожна задача — це **множина** термінів (не список): нас цікавить, *чи є* слово в задачі, а не скільки
   разів його повторили. Так одна багатослівна задача не перекриває решту.

**Фільтр за частотою документів (df — document frequency).** df терміна — у скількох задачах він є.
Залишаємо терміни з `5 ≤ df ≤ 0.3·N`:
- менше 5 задач — замало даних для будь-якого статистичного висновку;
- більше 30 % задач — слово надто загальне (`fix`, `error`), воно ні на що не вказує.

## 4. Таблиця спряженості 2×2 — фундамент усього

Майже всі присудки Гамаюна — відповідь на одне питання: **дві події відбуваються разом частіше,
ніж це пояснюється випадком?** Подія A — «задача містить термін *t*», подія B — «задача змінює модуль *m*».

Розкладемо всі N задач на чотири клітинки:

|  | змінює *m* | не змінює *m* | разом |
|---|---|---|---|
| **містить *t*** | a | b | a+b = df(t) |
| **не містить *t*** | c | d | c+d |
| **разом** | a+c = count(m) | b+d | N |

**Приклад (sonar, навчальні задачі):** *t* = `scanner`, *m* = `sonar-scanner-engine`.

|  | змінює | не змінює | разом |
|---|---|---|---|
| **містить `scanner`** | **202** | 179 | 381 |
| **не містить** | 262 | 8949 | 9211 |
| **разом** | 464 | 9128 | **9592** |

**Скільки було б, якби зв'язку не було?** Якщо термін і модуль незалежні, то ймовірність потрапити в
клітинку a дорівнює добутку ймовірностей рядка й стовпця:

$$
E_a = N \cdot \frac{a+b}{N} \cdot \frac{a+c}{N} = \frac{(a+b)(a+c)}{N}
$$

Для прикладу: E_a = 381 · 464 / 9592 = **18.43**. Тобто за незалежності `scanner` і `sonar-scanner-engine`
зустрілися б разом приблизно у 18 задачах, а насправді — у **202**. Очікувані значення для всіх клітинок:

|  | змінює | не змінює |
|---|---|---|
| **містить** | 18.43 | 362.57 |
| **не містить** | 445.57 | 8765.43 |

Тепер потрібно число, яке скаже, *наскільки* спостереження відрізняються від очікуваного,
і поріг, після якого відмінність не можна списати на випадок. Це робить G².

## 5. G² — тест відношення правдоподібності

### 5.1 Формула

$$
G^2 = 2 \sum_{\text{клітинки } i} O_i \ln \frac{O_i}{E_i}
$$

де O_i — спостережене число в клітинці, E_i — очікуване за незалежності, ln — натуральний логарифм.

**Як це читати.** Доданок `O ln(O/E)` дорівнює нулю, коли O = E (ln 1 = 0). Він тим більший за модулем,
чим сильніше O відрізняється від E. Сума по чотирьох клітинках, помножена на 2, — це загальна «відстань»
між реальністю і гіпотезою незалежності.

**Приклад:**

| клітинка | O | E | O·ln(O/E) |
|---|---|---|---|
| a | 202 | 18.43 | 202 · ln(10.96) = **483.64** |
| b | 179 | 362.57 | 179 · ln(0.494) = −126.34 |
| c | 262 | 445.57 | 262 · ln(0.588) = −139.12 |
| d | 8949 | 8765.43 | 8949 · ln(1.021) = 185.48 |

G² = 2 · (483.64 − 126.34 − 139.12 + 185.48) = **807.3**.

### 5.2 Звідки поріг 10.83

Математична статистика доводить: якщо зв'язку **немає**, G² для таблиці 2×2 розподілений приблизно за
законом **χ² (хі-квадрат) з одним ступенем свободи**. Для цього розподілу відомо, що значення більше
за **10.83** трапляється випадково лише у **0.1 %** випадків (p = 0.001). Тому:

- G² ≥ 10.83 → «такий збіг випадково трапився б рідше, ніж раз на тисячу» → записуємо трійку;
- G² < 10.83 → доказів недостатньо → мовчимо.

У прикладі G² = 807.3 — у 75 разів вище за поріг. Зв'язок не випадковий.

**Чому саме 0.001, а не звичні 0.05?** Ми перевіряємо сотні тисяч пар (термін, модуль). За порогу 0.05
навіть за повної відсутності зв'язків кожна двадцята пара пройшла б тест випадково — десятки тисяч
хибних трійок. Суворіший поріг — проста форма поправки на множинні порівняння.

**Ступінь свободи** — кількість клітинок, які можна заповнити довільно, коли суми рядків і стовпців
відомі. У таблиці 2×2 досить знати a — решта (b, c, d) обчислюється з сум. Тому ступінь свободи один.

### 5.3 Чому G², а не звичайний χ² Пірсона

Формула Пірсона `Σ (O−E)²/E` дає схожий результат на великих числах, але **погано працює з малими
очікуваними значеннями**: коли E_a < 5, вона сильно завищує значущість. Слова в текстах майже всі
рідкісні (закон Ціпфа), тож малі E — норма. Тед Даннінг (Dunning, 1993, *Accurate Methods for the
Statistics of Surprise and Coincidence*) показав, що G² на таких даних значно надійніший. Тому в
комп'ютерній лінгвістиці для пошуку колокацій і ключових слів використовують саме G².

### 5.4 Лише позитивні зв'язки й мінімальна підтримка

G² великий і тоді, коли термін **уникає** модуля (O_a < E_a). Для `characterizes` ми беремо лише
позитивну асоціацію: a > E_a. (Негативні зв'язки має окремий присудок `not_in`, розділ 8.3.)

Крім порогу G² вимагаємо **мінімальну підтримку**: a ≥ 5 для модулів, a ≥ 3 для папок і файлів.
G² на крихітних числах (a = 1 або 2) нестабільний: одна задача може дати великий G², якщо і термін,
і файл рідкісні.

## 6. Lift — у скільки разів частіше, ніж випадково

$$
\text{lift}(t, m) = \frac{P(t \wedge m)}{P(t)\,P(m)} = \frac{a \cdot N}{(a+b)(a+c)} = \frac{a}{E_a}
$$

У прикладі lift = 202 / 18.43 = **10.96**: серед задач зі словом `scanner` модуль `sonar-scanner-engine`
змінюється в 11 разів частіше, ніж у середньому.

**G² і lift відповідають на різні питання:**
- **G²** — *наскільки ми впевнені*, що зв'язок є (залежить від обсягу даних);
- **lift** — *наскільки сильний* зв'язок (не залежить від обсягу).

Рідкісна пара може мати lift = 50 і G² = 4 (сильно, але ненадійно). Часта — lift = 1.13 і G² = 31.8
(слабко, але напевно), як `quality :: characterizes :: server`. Гамаюн **фільтрує** трійки за G²
(надійність), а **ранжує** за lift (сила) — див. наївний Байєс у розділі 10.

## 7. Індекс Герфіндаля (HHI) — наскільки термін зосереджений

**Індекс Герфіндаля–Гіршмана** прийшов з економіки, де ним міряють концентрацію ринку. Якщо частки
ринку фірм — s₁, s₂, ..., то

$$
\text{HHI} = \sum_i s_i^2, \qquad \sum_i s_i = 1
$$

**Інтуїція на прикладах:**
- одна фірма має весь ринок: HHI = 1² = **1**;
- дві фірми порівну: 0.5² + 0.5² = **0.5**;
- чотири порівну: 4 · 0.25² = **0.25**;
- n фірм порівну: HHI = **1/n** (мінімум).

Квадрат «карає» дрібні частки й підсилює великі, тому HHI близький до 1, коли домінує хтось один.

**У Гамаюні** фірми — це модулі, а частки — розподіл значущих зустрічей терміна по модулях:
s_m = a(t, m) / Σ_m a(t, m). Якщо HHI ≥ 0.5 (і df ≥ 10), термін — **якір** свого модуля:

```
term:scanner :: anchor_of :: module:...   — коли майже всі його значущі появи в одному модулі
```

Якір — найкращий навігаційний орієнтир: побачив слово — знаєш, куди йти. Загальне слово
(`error`, `test`) має низький HHI, бо розмазане по всьому проєкту. Цей самий показник
використовувався в exp1 для аналізу розподілів (Бредфорд, HHI); тут він стає конструктивним: не лише
описує розподіл, а й створює знання.

## 8. Решта присудків

### 8.1 Структура з шляхів: `part_of`, `task_count`

```
file:server/.../QualityGateDao.java :: part_of :: dir:server/.../qualitygate
dir:server/.../qualitygate          :: part_of :: module:server
module:server                       :: task_count :: 6535
```

Детерміновано, точність 100 %. `task_count` — у скількох навчальних задачах змінювалась ціль; з нього
пошук рахує апріорну ймовірність P(ціль) = task_count / N.

### 8.2 `names` — термін є частиною імені файлу

`term:gate :: names :: file:.../QualityGateTest.java` записується, коли:
1. термін є частиною camelCase-імені файлу (`QualityGateTest` → `quality`, `gate`, `test`), **і**
2. термін і файл трапилися разом щонайменше у 2 задачах.

Друга умова відсікає випадкові збіги: слово `test` є в імені тисяч файлів, але з конкретним файлом воно
в задачах майже не зустрічається. Це міст між словником задач і словником коду — саме той розрив,
з якого почалась дисертація.

### 8.3 `not_in` — значуща відсутність

Іноді корисно знати, де термін **ніколи** не трапляється. Нехай модуль *m* змінюється в частці
r = count(m)/N задач. Якби термін був незалежний від модуля, імовірність, що **жодна** з df(t) задач
з цим терміном не зачепила *m*, дорівнює:

$$
P_0 = (1 - r)^{\,df(t)}
$$

(кожна задача незалежно «промахується» повз модуль з імовірністю 1 − r).

**Приклад:** модуль `sonar-server` змінюється в 1175 з 9592 задач, r = 0.1225. Термін `scanner` має
df = 381. Очікувано він мав би зустрітися з модулем 381 · 0.1225 ≈ **46.7** разу, а зустрівся **0** разів.
Імовірність такого випадково: P₀ = 0.8775³⁸¹ ≈ **2.4·10⁻²²**. Записуємо:

```
term:scanner :: not_in :: module:sonar-server  [src: expected=46.7;observed=0;p0=2.4e-22]
```

Поріг: P₀ < 0.001 і df ≥ 30. Заперечне знання відсікає хибні гілки пошуку: якщо в задачі є `scanner`,
`sonar-server` можна понизити.

### 8.4 `co_changes_with` — файли, що змінюються разом

Та сама таблиця 2×2 і той самий G², тільки події — «задача змінює файл A» і «задача змінює файл B».
Поріг: G² ≥ 10.83 і щонайменше 3 спільні задачі. Це класичний аналіз спільних змін
(Zimmermann et al., 2004, *Mining Version Histories to Guide Software Changes*, система ROSE).

**Фільтр масових рефакторингів:** задачі, що змінюють більше 30 файлів (перейменування пакета,
оновлення ліцензії в усіх файлах), для `co_changes_with` ігноруються. Інакше одна така задача створила б
сотні тисяч хибних пар.

Приклад: `package.json :: co_changes_with :: yarn.lock` (67 спільних задач, lift 94).

### 8.5 `narrower_than` — включення понять (subsumption)

Метод Сандерсона і Крофта (Sanderson & Croft, 1999): термін B **вужчий** за A, якщо майже завжди, коли є
B, є і A, але не навпаки:

$$
P(A \mid B) = \frac{\text{df}(A \wedge B)}{\text{df}(B)} \geq 0.8 \quad \text{і} \quad \text{df}(A) > \text{df}(B)
$$

**Чесний результат: на задачах це працює погано.** Найсильніші знайдені пари — кадри стектрейсів:
`standardhostvalve :: narrower_than :: lang`. У задачі зі стектрейсом Tomcat ці слова завжди йдуть
разом, але це не таксономія понять, а структура логу. Присудок будується, але в пошуку не
використовується. Справжній `is_a` між бізнес-поняттями з частот не виводиться — тут потрібна або LLM,
або додатковий фільтр.

### 8.6 `depends_on` — залежності модулів з коду

Береться **знімок коду на останньому коміті бази** (через `git cat-file`, без checkout — робоча папка
репозиторію не змінюється). Для кожного `.java` файлу читаємо `package` і `import`. Пакет належить
модулю, де лежить більшість файлів цього пакета. Якщо файли модуля A імпортують пакети модуля B
(≥ 3 файли), записуємо `module:A :: depends_on :: module:B`.

Це єдиний присудок, побудований з коду, а не з історії. У пошуку поки не використовується — призначений
для навігації.

## 10. Пошук: наївний Байєс

### 10.1 Теорема Байєса

Ми хочемо знайти модуль *m*, найімовірніший для задачі з термінами t₁, ..., tₖ:

$$
P(m \mid t_1, \dots, t_k) = \frac{P(t_1, \dots, t_k \mid m)\; P(m)}{P(t_1, \dots, t_k)}
$$

- **P(m)** — апріорна ймовірність: як часто модуль змінюється взагалі (`task_count / N`);
- **P(t₁...tₖ | m)** — правдоподібність: наскільки типові ці терміни для задач цього модуля;
- знаменник однаковий для всіх модулів, тому для ранжування його можна відкинути.

### 10.2 «Наївне» припущення

Порахувати P(t₁...tₖ | m) для всіх комбінацій слів неможливо — даних не вистачить. **Наївне
припущення:** терміни незалежні одне від одного, якщо модуль відомий. Тоді спільна ймовірність
розпадається на добуток:

$$
P(t_1, \dots, t_k \mid m) \approx \prod_{i} P(t_i \mid m)
$$

Припущення явно хибне (`quality` і `gate` майже завжди йдуть разом), але класифікатор на ньому
працює напрочуд добре — відомий результат (Domingos & Pazzani, 1997): для **ранжування** важливо лише,
хто попереду, а не точні ймовірності.

### 10.3 Логарифми і lift

Добуток багатьох малих чисел у комп'ютері швидко стає нулем (переповнення знизу), тому беремо логарифм
— добуток стає сумою. Ще один крок: ділимо кожен множник на P(tᵢ), що не змінює порядку модулів
(P(tᵢ) однакове для всіх *m*):

$$
\text{score}(m) = \log P(m) + \sum_i \log \frac{P(t_i \mid m)}{P(t_i)} = \log P(m) + \sum_i \log \text{lift}(t_i, m)
$$

Бо P(t|m)/P(t) = P(t∧m)/(P(t)P(m)) = lift. **Тобто весь пошук — це апріорна частота плюс сума
логарифмів lift, які вже лежать у `[src]` трійок `characterizes`.** Нічого не перераховується з бази.

**Термін без значущої трійки має lift = 1 → log 1 = 0** — він нічого не додає. Це свідоме рішення:
ми довіряємо лише зв'язкам, які пройшли тест G².

### 10.4 Чотири поправки

**(а) Температура λ.** Через хибне припущення про незалежність схожі терміни (`quality`, `gate`,
`qualitygate`) рахуються кілька разів, і сума доказів завищена. Множник λ < 1 її послаблює:

$$
\text{score}(m) = \log P(m) + \lambda \sum_i \log \text{lift}(t_i, m)
$$

λ підбирається на валідаційних задачах (розділ 11). На sonar найкраще λ = 0.25, на flink — λ = 1.

**(б) `not_in` як від'ємний доказ.** Для пари з `not_in` спостережено 0 зустрічей при очікуваних E.
Lift = 0/E = 0, а log 0 = −∞ — один термін назавжди заборонив би модуль. Тому згладжуємо: замість 0
беремо 0.5 (класичне згладжування «плюс половина»):

$$
\text{доказ} = \log \frac{0.5}{E}, \qquad \text{напр. } \log\frac{0.5}{46.7} = -4.54
$$

**(в) Відступ до папки й модуля для файлів.** Для конкретного файлу даних мало, а для його папки й
модуля — більше. Файл отримує власні докази плюс частку доказів папки (вага β) і модуля (вага β₂):

$$
\text{score}(f) = \log P(f) + \lambda\left(\sum_i \log\text{lift}(t_i, f) + \beta \sum_i \log\text{lift}(t_i, \text{dir}(f)) + \beta_2 \sum_i \log\text{lift}(t_i, \text{mod}(f))\right) + \mu \log(1 + n_{\text{names}}(f)) + \gamma\,\text{cc}(f)
$$

**(г) `names` і спільні зміни.** μ·log(1+n) — бонус файлу, ім'я якого містить термін задачі.
γ·cc(f) — бонус від 10 найкращих файлів: якщо файл часто змінюється разом із ними, він теж імовірний
(нормоване G² пари).

### 10.5 Приклад

Задача: *«Scanner crashes when analysing a branch with a quality gate»*.
Терміни: `analysing`, `branch`, `crashes`, `gate`, `quality`, `scanner`. λ = 0.25.

| модуль | log P(m) | log lift значущих термінів | not_in | score |
|---|---|---|---|---|
| `server` | −0.38 | branch 0.20, gate 0.26, quality 0.12 | — | **−0.24** |
| `sonar-scanner-engine` | −3.03 | branch 0.98, scanner 2.39 | — | −2.19 |
| `sonar-core` | −1.52 | gate 0.35, quality 0.29 | — | −1.36 |
| `sonar-server` | −2.10 | — | scanner −4.54 | −3.23 |

Видно, як працює кожна частина. `server` виграє завдяки величезній апріорній частоті: він є в 68 %
задач. `sonar-scanner-engine` має найсильніший доказ (`scanner`, lift 11), але рідкісний. `sonar-server`
понижено через `not_in`. Баланс між апріорною частотою і доказами задає λ. Саме через цей баланс
перша версія (сума G² без log P(m)) на sonar програвала простому «найчастіший модуль».

### 10.6 Пояснюваність

Кожен бал розкладається на внески конкретних трійок. Гамаюн може сказати не лише «змініть
`SensorContext.java`», а й «бо в задачі є `scanner` (lift 11 для модуля, трійка №…) і `sensor`
(ім'я файлу)». Ембедінги так не вміють: косинусна схожість векторів не розкладається на причини.

## 11. Як ми перевіряємо якість

### 11.1 Поділ даних

Чесна перевірка вимагає, щоб відповіді тестових задач ніяк не потрапили в модель. Три частини:

| Частина | Скільки | Як обрано | Для чого |
|---|---|---|---|
| **тест** | 200 | `modn` з exp3: задачі за ID, кожна k-та | лише фінальна оцінка, один раз |
| **dev (валідація)** | 200 | те саме правило `modn` усередині навчальних | підбір λ, β, β₂, μ, γ |
| **навчальні** | решта | | побудова онтології |

Для підбору параметрів будується **окрема онтологія без dev-задач**. Параметри перебираються сіткою
(до 960 комбінацій) і обирається комбінація з найкращим MAP на dev. Потім онтологія будується з усіх
навчальних задач і з цими параметрами **один раз** оцінюється на тесті. Тестові задачі не обирають
жодного параметра. Інакше ми б «підганяли під відповідь» і отримали завищену оцінку.

### 11.2 Метрики

Для задачі є список із 10 запропонованих файлів (ранжування) і множина правильних R.

- **P@k (точність на k):** частка правильних серед перших k. P@1 — чи правильний перший файл.
- **R@k (повнота на k):** частка правильних, знайдених у перших k: |правильні у топ-k| / |R|.
- **RR (обернений ранг):** 1 / позиція першого правильного. Перший правильний на 3-му місці → RR = 1/3.
- **AP (середня точність):** середнє P@k по позиціях, де стоїть правильний файл, поділене на |R|:

$$
\text{AP} = \frac{1}{|R|} \sum_{k:\, \text{файл}_k \in R} P@k
$$

*Приклад:* R = {A, B, C}, ранжування [A, X, B, Y, ...], C не знайдено.
P@1 = 1/1 (A), P@3 = 2/3 (B) → AP = (1 + 0.667) / 3 = **0.556**.

- **MAP / MRR** — середні AP / RR по всіх тестових задачах.

Ці формули скопійовано з `exp3/utils.py`, тож числа порівнювані з exp3 (з поправкою на джерело
правильних відповідей, розділ 15).

**Чому файли такі важкі.** У середній задачі sonar змінюється 18.6 файлу. Навіть ідеальна десятка
дає R@10 ≤ 10/18.6 ≈ 0.54. Тому MAP файлів ніколи не наблизиться до MAP модулів.

## 13. Синергія з Симарглом і Світовидом

### 13.1 Три незалежні сигнали

| Інструмент | Що «бачить» | Сильне місце | Сліпа пляма |
|---|---|---|---|
| **Симаргл** | смисл тексту (ембедінги задач і файлів) | перефразування, синоніми | не пояснює; плутає схоже за темою, але різне за кодом |
| **Світовид** | структура коду зараз (визначення, виклики) | точні ідентифікатори з тексту задачі | не знає історії; не розуміє бізнес-слів |
| **Гамаюн** | статистика історії (хто з чим змінювався) | бізнес-слово → модуль/файл, з поясненням | нові файли (не було в історії), рідкісні слова |

Сигнали побудовано **різними методами з різних джерел**, тож їхні помилки мають бути слабко корельовані.
Це і є умова, за якої поєднання дає більше, ніж кожен окремо (той самий принцип, що й в ансамблях
моделей машинного навчання).

### 13.2 Способи поєднання

**(1) Reciprocal Rank Fusion (RRF)** — найпростіший і найстійкіший спосіб злити кілька списків
(Cormack et al., 2009). Файл отримує бал за позицію в кожному списку:

$$
\text{RRF}(f) = \sum_{\text{списки } s} \frac{1}{k + \text{rank}_s(f)}, \qquad k = 60
$$

Файл на 1-му місці в одному списку дає 1/61, на 10-му — 1/70. Перевага RRF: не потрібно зводити різні
шкали балів (косинус, log-ймовірність, кількість посилань) до однієї — важливі лише позиції. У Симаргла
RRF уже реалізовано (`simargl.searcher.rrf_search`).

**(2) Навчене зважування.** Ваги w_s для кожного джерела підбираються на dev — так само, як параметри
Байєса.

**(3) Перерангування моделлю (Jev / LLM).** Беремо top-5 з кожного джерела (до 15 кандидатів) і для
кожного питаємо модель: «чи стосується файл X задачі Y?» (Jev: ймовірність «так»). Найдорожчий спосіб,
але єдиний, що читає сам файл, а не лише статистику.

### 13.3 Про «90 % на файлах» — що реально досяжно

Ціль треба сформулювати точно, бо «точність 90 %» означає різне:

- **Hit@k** — «серед k запропонованих є хоча б один правильний». Найдосяжніша ціль: навігатору
  (людині або агенту) досить однієї правильної точки входу, далі він піде за посиланнями (Світовид).
- **R@k** — «яка частка всіх змінених файлів знайдена». Обмежена зверху: при 18.6 файлу на задачу і
  15 кандидатах навіть ідеальний вибір дає ≤ 0.8 у середньому, а на великих задачах — набагато менше.
- **P@k** — «яка частка запропонованих правильна». Залежить від того, скільки файлів реально змінюється.

**Ключове обмеження будь-якого перерангування:** воно не може знайти файл, якого немає серед кандидатів.
Тому перший експеримент — не перерангування, а **оракульна стеля**: яка частка правильних файлів
потрапляє в об'єднання top-5 трьох джерел. Якщо стеля Hit@15 — 95 %, перерангування має сенс і 90 %
Hit@5 досяжне. Якщо стеля — 60 %, ніякий Jev не дасть 90 %, і треба спершу розширювати кандидатів.

### 13.4 План експерименту (exp8)

1. На тих самих 200 тестових задачах (`modn`) отримати top-N від кожного джерела. Симаргл
   індексується лише з навчальних задач (копія бази без тестових задач), Світовид будує карту знімка
   коду на останньому коміті бази.
2. Для кожного джерела й для об'єднання порахувати стелю: Hit@k і R@k об'єднання top-5/top-10.
3. Порахувати RRF і навчене зважування (ваги на dev).
4. Якщо стеля висока: перерангування Jev на підвибірці (наприклад, 50 задач), бо це дорого:
   15 кандидатів × 50 задач = 750 викликів моделі.
5. Головне питання для дисертації: **чи кореляція помилок джерел справді низька**. Міра: частка
   правильних файлів, знайдених лише одним джерелом. Висока частка = справжня синергія.

### 13.5 Перші результати (exp8)

Деталі — `exp8/README.md`. Тест 200 задач, MAP файлів:

| | sonar | flink |
|---|---|---|
| gamayun | 0.116 | 0.124 |
| simargl (bge-small, задачі) | 0.132 | 0.142 |
| svitovyd (карта HEAD) | 0.004 | 0.038 |
| поєднання (RRF / квоти, з dev) | **0.149** | **0.165** |

- **Синергія є.** gamayun і simargl разом знаходять лише 27–28 % правильних файлів; приблизно третину
  кожен знаходить сам. Поєднання дає +13 % і +16 % MAP відносно кращого окремого джерела.
- **Пропорції залежать від проєкту:** квоти з 10 — sonar 1 / 9 (gamayun / simargl), flink 6 / 4.
  RRF з рівними вагами — стійкий варіант за замовчуванням.
- **Стеля hit:** об'єднання top-5 трьох джерел — 0.50 / 0.61, top-50 — 0.76 / 0.79. Отже, 90 % hit

- svitovyd оцінено несправедливо: його карта — код 2026 року, а в ньому існують лише 20 % / 40 %

## 14. Інструмент gamayun

Окремий інструмент пантеону (`C:\Projects\gamayun\`), за зразком Симаргла й Світовида:

```bash
gamayun index --db sonar.db --repo ./sonarqube --project sonar   # онтологія з усіх задач (синонім: build)
gamayun tune  --db sonar.db --project sonar                      # підбір λ, β... на dev
gamayun eval  --db sonar.db --project sonar                      # dev + тест, як у exp7
gamayun search "scanner crashes on quality gate" --project sonar # top модулі й файли + пояснення
gamayun ui --port 8095                                           # Flask-інтерфейс
```

Дані — у `~/.gamayun/<проєкт>/`: `triples.txt`, `params.json` (підібрані параметри), `stats.json`.

Інтерфейс — **Flask + статичний HTML/JS без збирання**, як у Вирію й Алконоста: мінімум залежностей
(flask, numpy, scipy), без Gradio. Головна сторінка — пошук із **поясненням кожного результату**
(які трійки дали бал), друга — перегляд сутності (усі трійки терміна, модуля чи файлу), третя —
стан проєктів і запуск побудови.

Надалі: MCP-сервер (`gamayun-mcp`) з інструментами `search` і `explain` для агентів (Claude Code,
1bcoder, Вирій). Формат `triples.txt` уже сумісний з вкладкою «Онтологія» Вирію.

## 15. Обмеження і відкриті питання

1. **Нові файли невидимі.** Онтологія знає лише файли зі змінами в навчальних задачах. На тесті
   5–6 % правильних файлів ніколи раніше не змінювались. Частково це закриють Світовид (поточна
   структура) і Симаргл (`file`-режим за вмістом).
2. **Кандидати обмежують повноту.** Пошук розглядає лише файли з доказами, файли найкращих папок і
   модулів. Серед них — 70 % (sonar) і 78 % (flink) правильних файлів.
3. **Порівняння з exp3 непряме.** exp3 читав таблицю `RAWDATA`, якої в цих базах немає; тут правильні
   відповіді — `COMMITS.PATH`. exp3 повідомляє 27 модулів sonar, тут — 64.
4. **Частотна базова лінія сильна.** На модулях sonar «найчастіший модуль» дає MAP 0.693 — вище за BGE
   з exp3 (0.452). Варто перерахувати prior на даних exp3: якщо там так само, висновки exp3 про модулі
   потребують перегляду.
5. **`is_a` з частот не виводиться** (див. `narrower_than`). Логічні присудки (`can`, `cannot`, `must`)
   — справа LLM-онтології 1bcoder/Вирію. Дві онтології доповнюють одна одну: статистична каже «де»,
   логічна — «що можна і що не можна».
6. **Онтологія старіє.** Потрібна інкрементальна перебудова після нових задач (Observer Loop з концепту
   Мурашника, `ANTHILL_DISTRIBUTED_COGNITIVE_OS.md`).

## 16. Онтологія з файлів без бази задач (`--files`)

```bash
gamayun index --files ./docs --project docs        # документи, код або обидва разом
gamayun search "фінальний період бюджету" --project docs
gamayun show ident:final_period --project docs
```

### 16.1 Що змінюється, коли бази задач немає

Онтологія з бази спирається на **два погляди на одну подію**: текст задачі та файли, які для неї змінили.
У папці погляд один — сам текст. Тому таблицю 2×2 для G² рахуємо не по задачах, а по **одиницях тексту**:

- **у документі** одиниця — абзац; заголовки утворюють розділи (вкладені за рівнем);
- **у коді** одиниця — тіло одного визначення (класу, функції, методу). Кожен рядок належить найглибшому
  визначенню, в якому лежить. Визначення шукаються простими правилами для рядків, без парсера конкретної
  мови: Python, Java/Kotlin/C#, JS/TS, Go, Rust, SQL.

Кожна одиниця лежить у ланцюжку цілей: **модуль ⊃ папка ⊃ файл ⊃ символ** (клас або розділ документа).
Той самий G² ≥ 10.83 (p < 0.001), що й для задач, каже, які терміни й ідентифікатори **характерні** для якої цілі.

### 16.2 Ідентифікатори — окремі сутності

`final_period`, `BudgetService` — це не просто слова, а **імена** речей системи. Вони стають сутностями `ident:`
і отримують зв'язки на всіх рівнях:

| присудок | приклад | правило |
|---|---|---|
| `ident defined_in sym` | `ident:close_period :: defined_in :: sym:budget/calc.py#BudgetService.close_period` | визначення в коді |
| `ident used_in sym/file` | `ident:g2_vec :: used_in :: sym:gamayun/builder.py#build.characterizes` | рідкісний ідентифікатор (≤ 20 одиниць) ужито там |
| `ident has_part term` | `ident:final_period :: has_part :: term:period` | розбиття camelCase / snake_case |
| `ident characterizes file/sym/...` | | той самий G² |
| `term is named_entity` | `term:user :: is :: named_entity [src: in_filenames=195]` | слово є в назвах файлів — це майже сутність |

Решта присудків — `anchor_of`, `narrower_than`, `names` — як і в онтології з бази. Нові присудки:
`related_to` (G² спільної появи в одиницях, 10 найсильніших партнерів на термін) і, лише з документів,
шаблонні `is_a` / `same_as`:

- **Шаблони Херста** (Hearst, 1992): «*fuels such as petrol and diesel*» → `petrol is_a fuels`;
  «*X and other Y*»; «*X is a Y*»; українською «*X — це Y*», «*Y, такі як X*». Елементи переліку беремо
  по одному слову. Без розмітки частин мови не можна знати, що в «diesel *are*» друге слово — дієслово.
- **Абревіатури**: «*Total Cost of Ownership (TCO)*» → `tco same_as total cost of ownership`. Ініціали
  збираються з великих літер, а малі сполучники всередині розшифровки пропускаються.

Шаблони дають мало трійок і помиляються частіше за статистику. Тому в `[src]` завжди є місце в тексті
(`at=файл:рядок`), а перевіряти їх природно рішальною моделлю (Jev, `triple_grounded`).

### 16.3 Які слова не несуть інформації — без словника стоп-слів

Готовий список стоп-слів прив'язаний до мови. Нам потрібне правило, що однаково працює для англійської,
української й коду. Службові слова відрізняються не значенням, а **розподілом**:

- `the`, `для`, `public`, `return` розсипані по файлах рівномірно, як випадкові;
- слова теми згущуються: `бюджет` трапляється в небагатьох файлах, але там помногу.

**Залишковий IDF** (residual IDF, Church & Gale, 1995) міряє саме це. Нехай слово трапилось cf разів
у n файлах, а частка тексту файлу d дорівнює ℓ_d. Якби появи падали на файли випадково, у пропорції
до їхнього розміру (пуассонівська модель), слово було б приблизно в стількох файлах:

```
очікувана кількість файлів   E = Σ_d (1 − e^(−cf · ℓ_d))
RIDF = log₂(E / df)          df — у скількох файлах слово є насправді
```

- RIDF ≈ 0: слово розподілене, як випадкове → **службове**.
- RIDF великий: слово «злипається» в менше файлів, ніж велить випадок → **слово теми**.

Числа з коду SonarQube (9 605 файлів):

| слово | файлів | cf | RIDF | вердикт |
|---|---|---|---|---|
| `copyright` | 8 310 | 8 600 | −0.97 | службове (ліцензійна шапка) |
| `the` | 8 517 | 97 323 | 0.07 | службове |
| `public` | 8 371 | 74 502 | 0.06 | службове |
| `user`, `issue`, `rule`, `group` | — | — | > 1 | слова теми |

**Чому файли, а не абзаци.** Абзац закороткий: майже кожне слово трапляється в ньому один раз, тож
«злипнутись» ніде не може. На рівні абзаців RIDF < 0.3 мали `structure`, `python`, `database`, `pipeline`.
На рівні файлів — лише справді загальні слова.

**Судимо лише часті слова** (у ≥ 5 файлах, ≥ 2 % файлів, cf ≥ кількість файлів / 2). Слово, яке трапилось
5 разів у 5 файлах, не може злипнутись, і його RIDF ≈ 0 нічого не означає.

**Слово з назв файлів — не службове, а центральне поняття.** Візьмімо систему обліку бензину: слово
`бензин` трапляється скрізь, і за розподілом воно як `the`. Для пошуку це правда: воно не допомагає
вибрати файл (у G² воно нічого не набере). Але викидати його не можна: це **ядро предметної області**.
Його видає те, що воно **називає речі**: `FuelPriceService`, `fuel_purchase.py`. Правило:

```
назва          : слово є в назвах файлів, і таких файлів ≥ 5 % від тих, де воно трапляється
function_word  : RIDF < 0.3 і не назва
domain_core    : назва, і (RIDF < 0.3 або слово є в > 30 % файлів)
```

Поріг 5 % відсікає випадкові збіги: `public` є у 2 назвах із 8 371 файлу (`PublicApi…`).
Довжина слова **не враховується**: дво- й трилітерні абревіатури (UI, DB, SQL, LLM) часто є
найважливішими словами домену. Обидва вердикти записуються трійками з числами, тож будь-яке рішення
можна перевірити:

```
term:the     :: is :: function_word  [src: ridf=0.07;files=8517;cf=97323;in_filenames=0]
term:agent   :: is :: domain_core    [src: ridf=0.72;files=42;cf=802;in_filenames=4]
```

**Сліпа пляма — мовні острови.** У змішаній папці (англійські й українські документи) або в коментарях
коду англійська живе окремими «островами». `the` там злипається разом зі своєю мовою, і RIDF його
не впізнає (у `concepts/` RIDF(`the`) = 0.57). У коді SonarQube `the` все одно спіймано: він є в
ліцензійній шапці кожного файлу. Пробували **адаптацію** (Church, 2000: чи повторюється слово в одиниці
частіше, ніж за Пуассоном); вона острови теж не розрізняє.

### 16.4 Словоформи без стемера

`users` і `user`, `онтології` й `онтологія` ділять між собою частоту. На sonar це означало, що `users`
міг потрапити в Q1 Ципфа, а `user` — у Q2. Зливаємо їх статистично, без словника мови:

1. Кожне слово ріжемо як *основа + закінчення*: основа ≥ 4 літер і ≥ 60 % слова, закінчення ≤ 4 літер.
   Основа з ≥ 2 словами корпусу утворює групу: `user|{-, s}`, `онтолог|{ія, ії, ію}`.
2. Два закінчення вважаються формами одного слова, лише якщо **пара повторюється** в багатьох основах
   (сигнатури Голдсміта, 2001). Пара `{-, s}` чи `{ія, ії}` має сотні основ; `{ains, ent}`
   (contains / content) чи `{-, ial}` (part / partial) — одиниці. Пара з порожнім закінченням потребує
   ≥ 5 основ, пара двох непорожніх — ≥ 10.
3. Часті форми (df ≥ 5) мають ще й уживатися в схожих місцях: косинус їхніх розподілів по файлах ≥ 0.3.
   Так відсіюється `position` / `positive`.

Назвою групи стає найчастіша форма. Злиття записується трійкою, і пошук зводить слова запиту до тих самих форм:

```
term:users   :: variant_of :: term:user    [src: endings=s/-;cos=0.49;df=25]
term:periods :: variant_of :: term:period  [src: endings=s/-;cos=0.64;df=220]
```

Злиття ловить і словотвір (`encoded`/`encode`, `persistence`/`persistent`). Для пошуку це радше на
користь, але це не лематизація в лінгвістичному сенсі.
