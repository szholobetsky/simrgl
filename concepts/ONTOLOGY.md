# ONTOLOGY — база знань на трійках із перевіркою суперечностей

> Статус: v1 реалізовано в 1bcoder — `_bcoder_data/flows/ontology.py` (`/flow ontology`),
> рубрика `triple_grounded`, тести `tests/test_ontology.py`. Розділ §10 — що показав перший живий прогін.
> Споріднені документи: `GLOSSARY.md` (`/flow glossary`), `JEV.md` (рубрики),
> `AUTOMATICAL_AGENTS_LOGICAL_EXTERNAL_APPROACH.md` §1.4 (трійки + nogood),
> `KEYWORD_ENTITY_MAPPING.md` (бізнес-терміни ↔ ідентифікатори коду).

## 1. Ідея

`/flow glossary` читає чанки тексту і накопичує про кожен термін DEFINITION: і FACTS:
вільним текстом. Він нічого не забороняє: два факти, що суперечать один одному,
спокійно лежать поруч у FACTS:.

`/flow ontology` — той самий конвеєр (чанк → LLM → регекс → файл), але одиниця знання
не речення, а **трійка**:

```
A :: B :: C
жінка :: може :: взяти декретну відпустку
```

`A` і `C` — сутності, `B` — тип зв'язку. Головна відмінність від глосарію — **строгість**:
перш ніж трійка потрапить у базу, Python перевіряє, чи вона не суперечить тому, що
вже записано. Суперечність → червоний прапорець, трійка не приймається, людина вирішує.

Розподіл ролей той самий, що в JEV.md: **LLM генерує → Jev сприймає → Python вирішує.**
LLM лише витягує кандидатів. Перевірку суперечностей робить детермінований автомат,
а не модель: суперечність — механічна властивість набору трійок, а не думка.

## 2. Приклад, який має працювати

Ваш приклад, розписаний як база:

```
користувач :: is_a :: людина
жінка      :: is_a :: користувач
чоловік    :: is_a :: користувач
жінка      :: disjoint_with :: чоловік

жінка   :: can    :: взяти декретну відпустку      ✓ прийнято
чоловік :: cannot :: взяти декретну відпустку      ✓ прийнято (жінка і чоловік не перетинаються)
```

Тепер хтось (LLM з іншого чанку) пропонує:

```
користувач :: can :: взяти декретну відпустку      ✗ ЧЕРВОНИЙ ПРАПОРЕЦЬ
```

Чому: `can` на батьківському класі успадковується всіма нащадками. Отже з неї випливає
`чоловік :: can :: взяти декретну відпустку`, а в базі вже є `чоловік :: cannot :: ...`.
Повідомлення має показати весь ланцюжок, а не лише «конфлікт»:

```
CONFLICT  користувач :: can :: взяти декретну відпустку   [file: hr/policy.md:12]
  via     чоловік :: is_a :: користувач                    [file: hr/roles.md:3]
  vs      чоловік :: cannot :: взяти декретну відпустку    [file: hr/policy.md:40]
```

Другий приклад — пряма суперечність без ієрархії:

```
жінка :: can    :: народжувати дітей     (уже в базі)
жінка :: cannot :: народжувати дітей     ✗ ЧЕРВОНИЙ ПРАПОРЕЦЬ — той самий суб'єкт, протилежна полярність
```

Тобто умову «якщо користувач жінка» ми не зберігаємо як окреме поле `| if ...`.
Умова **стає класом**: «користувач, який жінка» = `жінка`, підклас `користувача`.
Це саме те, що ви запропонували («чоловік НЕ МОЖЕ, жінка МОЖЕ»), і воно дає
перевірку батьківського класу безкоштовно — через успадкування.

## 3. Модель даних

### 3.1 Трійка

```
суб'єкт :: предикат :: об'єкт   [джерело]
```

Кожна трійка зберігає джерело (`[file: path:line]`, як у глосарії) — без нього
червоний прапорець неможливо розібрати.

### 3.2 Предикати: закритий набір + відкритий

Предикати діляться на дві групи, бо по-різному поводяться в перевірці.

**Структурні (закритий набір, їх розуміє автомат):**

| Предикат | Значення | Властивості |
|---|---|---|
| `is_a` | A — підклас / різновид C | транзитивний, нащадок успадковує твердження батька |
| `instance_of` | A — конкретний екземпляр класу C | екземпляр успадковує твердження класу |
| `part_of` | A — складова частина C | транзитивний, **не** успадковує (колесо не є машиною) |
| `disjoint_with` | A і C не мають спільних екземплярів | симетричний, успадковується вниз |
| `same_as` | A і C — одна сутність (синонім) | зливає сутності (див. §5.3) |

**Модальні з полярністю (у них живуть суперечності):**

| Позитивний | Негативний | Конфлікт |
|---|---|---|
| `can` | `cannot` | `can` ↔ `cannot` |
| `must` | `cannot` | `must` ↔ `cannot` (`must` ↔ `can` — не конфлікт) |
| `is` | `is_not` | властивість: `договір :: is :: підписаний` |
| `has` | `has_not` | `рахунок :: has :: валюта` |
| `does` | `does_not` | звичайні дієслова: `жінка :: does :: народжувати дітей` |

**Доменні (відкриті):** `видає`, `списує`, `належить` тощо. Автомат їх зберігає і шукає,
але суперечностей у них не бачить, поки предикат не зведено до одного з модальних.
Тобто `не видає` LLM має записати як `does_not :: видавати`, а не як новий предикат
`не_видає`. Це правило промпту, і його перевіряє регекс (заборона `не_` / `not_` у
назві предиката).

### 3.3 Сутності

Нормалізація назв як у глосарії (lowercase, однина, без артиклів). Список сутностей
спільний із глосарієм того ж `--project`: термін глосарію = сутність онтології.
Це дає зв'язок «визначення (глосарій) ↔ правила (онтологія)».

## 4. Перевірка суперечностей (Python, без LLM)

### 4.1 Замикання

1. `is_a`-замикання: для кожної сутності — множина всіх предків (транзитивно).
   Цикл `A is_a B`, `B is_a A` без `same_as` → червоний прапорець.
2. Успадкування тверджень: кожне модальне твердження про `Y` діє для всіх `X ⊑ Y`.
3. Несумісність: `X` і `Y` несумісні, якщо для будь-яких їхніх предків оголошено
   `disjoint_with`.

### 4.2 Правило конфлікту

Два твердження `(S1, p, O)` і `(S2, p̄, O)` з протилежною полярністю про той самий об'єкт
конфліктують, якщо `S1` і `S2` **можуть мати спільний екземпляр**. Рівні строгості:

| Ситуація | Рівень | Дія |
|---|---|---|
| `S1 = S2` | RED | відхилити |
| `S1 ⊑ S2` або `S2 ⊑ S1` (через успадкування) | RED | відхилити |
| `S1`, `S2` оголошені несумісними | — | не конфлікт (жінка / чоловік) |
| `S1`, `S2` нічого не відомо про перетин | YELLOW | прийняти з попередженням або спитати |

YELLOW — наслідок відкритого світу. Приклад: `резидент :: can :: X` і
`жінка :: cannot :: X`. Резидент може бути жінкою, але база про це мовчить.
Строгий режим (`--strict`) трактує YELLOW як RED і вимагає явного `disjoint_with`
або уточнення суб'єкта.

### 4.3 Структурні суперечності

- `X is_a Y` і `X disjoint_with Y` → `X` порожній → RED.
- `X is_a A`, `X is_a B`, `A disjoint_with B` → RED.
- `instance_of` двох несумісних класів → RED.

### 4.4 Мінімальний набір конфлікту

Повідомлення показує **мінімальний набір трійок, що разом дають суперечність**
(вивідний ланцюжок з §2). Це nogood з ATMS (`AUTOMATICAL_AGENTS_LOGICAL_EXTERNAL_APPROACH.md`
§1.3–1.4): відхилена пара записується в `nogood.txt`, щоб ту саму суперечність
не пропонувати людині вдруге.

### 4.4а Журнал суперечностей: реальність не ідеальна

Суперечність у джерелах — теж знання. Документи реально суперечать один одному (FAQ
каже «кожен користувач може», політика — «чоловік не може»), і база не повинна мовчки
вибрати одну сторону. Тому відхилений факт не зникає — він записується в журнал так:

```
НЕ ЗАПИСАНО: user :: can :: take maternity leave
знайдено в:  docs/faq.md:3
бо:          'user' і 'man' мають спільних членів — 'can' і 'cannot' суперечать
суперечить записаним фактам:
  - man :: cannot :: take maternity leave   — docs/policy.md:5
  - man :: is_a :: user                     — docs/roles.md:2
```

Рядки журналу ніколи не видаляються — рішення людини лише змінює статус. Так людина
бачить і зараз, і потім, які суперечності треба деталізувати умовами, а які є справжнім
провтиком у самих джерелах:

| Статус | Значення |
|---|---|
| `open` | чекає рішення |
| `refined` | новий факт звужено умовою (`\| woman`) і записано — суперечність була недодеталізованою |
| `known` | справжня суперечність у джерелах — нічого не змінюємо, рядок лишається як знання (з приміткою) |
| `rejected` | новий факт хибний (помилка екстракції) → `nogood.txt` |
| `replaced` | новий факт записано, старе твердження прибрано → старе в `nogood.txt` |
| `disjoint` | (YELLOW) суб'єкти оголошено такими, що не перетинаються, факт записано |
| `accepted` | (YELLOW, утриманий `--strict`) записано як є |

Той самий факт, знайдений ще в одному файлі, не створює новий рядок — додає джерело
до відкритого (`знайдено в: a.md:3; b.md:7`). Журнал — `conflicts.jsonl` (машинний)
і `conflicts.md` (для людей, перегенерується після кожної зміни).

### 4.5 Винятки — свідомо заборонені (поки що)

Класична проблема «птахи літають, пінгвіни — ні»: більш специфічне правило перекриває
загальне. Логіки за замовчуванням (default logic) це вміють, але саме вони роблять базу
нестрогою. Стартова позиція: **винятків немає**, кожне таке перекриття — RED.
Якщо колись знадобиться, — лише явним маркером:

```
пінгвін :: cannot :: літати   !except  птах :: can :: літати
```

щоб виняток був рішенням людини, а не мовчазним наслідком того, що LLM щось витягла.

## 5. Конвеєр `/flow ontology index`

```
чанк → LLM: трійки → регекс-парсер → нормалізація → Jev: обґрунтованість →
      → Python: суперечності → прийнято / YELLOW / RED → файли
```

### 5.1 Екстракція (LLM)

Для малих моделей — строгий рядковий формат з маркером, як у глосарії:

```
TRIPLE: жінка :: can :: взяти декретну відпустку
TRIPLE: жінка :: is_a :: користувач
```

Промпт містить: перелік структурних і модальних предикатів (§3.2), правило
«умова стає класом» з одним прикладом, заборону заперечень у назві предиката,
і вимогу писати лише те, що прямо сказано в чанку.

Головний ризик — 1B-модель не зможе перетворити «користувач може, якщо він жінка» на
клас `жінка ⊑ користувач`. Запасний варіант: дозволити синтаксис з умовою

```
TRIPLE: користувач :: can :: взяти декретну відпустку | gender = жінка
```

і перетворювати його в Python: умова `gender = жінка` → клас `користувач[gender=жінка]`
з `is_a користувач`. Значення одного атрибуту (`gender = жінка`, `gender = чоловік`)
автоматично `disjoint_with` одне одному. Тоді й LLM простіше, і автомат має
несумісність без явного оголошення.

### 5.2 Обґрунтованість (Jev)

Окрема від суперечностей перевірка: чи трійка **справді випливає з чанку**, а не
вигадана моделлю. Це параметризована рубрика (тепер вони є):

```yaml
name: triple_grounded
criteria:
  - id: grounded
    type: noul
    instructions: "Does this text state that {{subject}} {{predicate}} {{object}}?"
```

`state` = чанк, з якого трійку витягли. Нижче порогу — трійка відкидається ще до
перевірки суперечностей. Обмеження з JEV.md: чанк + питання ≤ 2050 токенів, тож
`--chunk` за замовчуванням ~1500 токенів.

### 5.3 Синоніми

Найбільше джерело хибних конфліктів і пропущених: `працівник` і `співробітник`
як різні сутності. Кандидати в `same_as` — через embedding-близькість (radogast,
як `--synonyms` у глосарії), підтвердження — людина. `same_as` ніколи не ставиться
автоматично: злиття двох сутностей може породити десятки нових конфліктів.

### 5.4 Файли

```
.1bcoder/ontology/<project>/
    triples.txt      прийняті трійки, по одній на рядок, з джерелом (джерело правди)
    conflicts.jsonl  журнал суперечностей зі статусами (§4.4а): RED і утримані --strict YELLOW
    conflicts.md     той самий журнал для людей
    nogood.txt       відхилені трійки, щоб не пропонувати повторно
    ontology.ttl     експорт у Turtle (генерується, не редагується)
```

Джерело правди — plain text (git-diff, редагування руками, читається малою моделлю),
а не бінарне сховище. Turtle — похідний експорт для зовнішніх інструментів.

**Вирій.** Той самий `ontology.py` без змін лежить у `vyrii/flows/` (синхронізація = копія файлу).
Відмінність лише в корені сховища, як і в глосарія: вирій задає модульні змінні
`ROOT = ~/.vyrii/ontology` і `SRC_BASE = ~/.vyrii`, тож проєкти лежать у
`~/.vyrii/ontology/<project>/`, а не поруч з індексованою папкою. Вкладка «Онтологія»
показує журнал суперечностей картками з кнопками рішень (той самий `resolve_row`), запити
show/ask/sparql і список трійок; результат запиту можна додати в чат блоком.

## 6. Рушій: що взяти з Python

| Бібліотека | Що дає | Чому так / чому ні |
|---|---|---|
| **rdflib** | RDF-граф у пам'яті, SPARQL 1.1, Turtle | Чистий Python, стабільний. Основне сховище і мова запитів. |
| **pyoxigraph** | швидкий SPARQL-рушій (Rust) | Якщо rdflib стане повільним на великих базах. |
| **owlrl** | RDFS / OWL-RL замикання над rdflib | Чистий Python; але `is_a`-замикання ми й самі робимо за 20 рядків. |
| **pySHACL** | перевірка форм (shapes) над rdflib | Чистий Python; добре для «у кожного договору є дата», не для конфліктів полярності. |
| **owlready2** | OWL + резонери HermiT / Pellet | Резонерам потрібна Java. OWL — відкритий світ: `can` / `cannot` у ньому не виражаються напряму. |
| **clingo** (ASP) | логічне програмування з обмеженнями | `pip install clingo`. Обмеження-цілісності (`:- can(X,O), cannot(X,O).`) — рівно наша перевірка конфліктів; потенційно v2. |

Рекомендація для v1: **rdflib для зберігання і запитів + власний перевіряльник
суперечностей (~200–300 рядків Python)**. Причини:

1. Те, що нам потрібно (полярність `can`/`cannot`, рівні RED/YELLOW, мінімальний
   набір конфлікту з джерелами), не є стандартною OWL-семантикою. Втиснути це в OWL
   означає моделювати дозволи через класи-обмеження, а OWL у відкритому світі
   мовчатиме там, де ми хочемо червоний прапорець.
2. Без Java, без важких залежностей — та сама філософія, що в глосарії
   (stdlib для ядра, опційні залежності через `try/except ImportError`).
3. Перевіряльник детермінований і пояснюваний — кожен RED має вивідний ланцюжок.

SPARQL при цьому залишається доступним: трійки в rdflib-графі, і хто знає SPARQL —
пише його напряму.

## 7. Команди (ескіз)

```
/flow ontology index <path> [--project P] [--chunk N] [--strict] [--no-jev]
/flow ontology add "жінка :: can :: взяти декретну відпустку" [--project P]
/flow ontology check [--project P]            повна перевірка всієї бази (після ручних правок)
/flow ontology conflicts [--project P]        RED/YELLOW по одному: залишити A / залишити B /
                                              уточнити суб'єкт / оголосити disjoint / відкинути обидва
/flow ontology show <сутність> [ctx]          усі трійки про сутність, з успадкованими (позначені)
/flow ontology ask "? :: can :: взяти декретну відпустку"     шаблонний запит, ? = змінна
/flow ontology sparql "SELECT ?s WHERE { ... }"
/flow ontology export ttl
```

`ask` повертає й виведені відповіді: на `чоловік :: can :: взяти декретну відпустку ?`
відповідь «ні, `cannot`, ланцюжок: ...». Це дає агенту перевірку бізнес-правил без LLM:
`/flow ontology ask` як ACTION у циклі агента або як gate.

## 8. Зв'язки з іншими частинами

- **Глосарій.** Глосарій — словник (що таке термін), онтологія — правила (що з ним можна).
  Спільний простір сутностей; `/flow glossary show X` може показувати й трійки про X.
- **Jev.** Обґрунтованість трійки (§5.2); також можлива рубрика `triple_wellformed`
  (чи предикат справді з дозволеного набору за змістом, а не лише за формою).
- **codeXport / KEYWORD_ENTITY_MAPPING.** Бізнес-сутність онтології ↔ ідентифікатор коду:
  `жінка :: implemented_by :: Gender.FEMALE`. Тоді правило онтології можна звіряти з кодом
  через `implements_rule` (`/loop dir:src --jev implements_rule rule="чоловік не може взяти декретну відпустку"`).
- **External supervision / ATMS.** §1.4 того концепту вже описує трійки `[система, обрана_БД, sqlite]`
  і nogood. Онтологія — та сама машинерія, застосована до знань предметної області,
  а не до рішень плану.

## 9. Відкриті питання

1. **Часткові та статистичні твердження.** «Жінки народжують дітей» — правда як загальне
   твердження, неправда як універсальне. Чи потрібен модальний рівень `typically`, який
   не конфліктує з `does_not` для підкласу? Чи це той самий виняток з §4.5?
2. **Ієрархія об'єктів.** `жінка :: can :: взяти декретну відпустку` і
   `чоловік :: cannot :: взяти відпустку` (будь-яку): декретна ⊑ відпустка, тож це конфлікт?
   Для `cannot` — так (заборона на загальне закриває окреме), для `can` — ні. Потрібне
   замикання по об'єкту з різними правилами для різних полярностей.
3. **Числові та часові умови.** «Може взяти відпустку, якщо стаж > 6 місяців» — умова-атрибут
   з порівнянням. Атрибутні класи з §5.1 працюють для рівності, але не для `>`.
   Можливо, це межа v1.
4. **Чи здатна 1B-модель** стабільно видавати `A :: B :: C` з закритим набором предикатів.
   Перевірити на тих самих даних, що й глосарій (`simargl-rag-demo`), і на реальних
   бізнес-правилах (amortization у RRTrack чи схожий домен).
5. **Мова.** Сутності українською чи англійською? Змішані тексти дадуть дублікати
   `користувач` / `user` — це знову `same_as`.
6. **Порядок обробки.** Що прийшло першим, те й «правильне», а пізніше — RED. Але перше
   могло бути помилкою екстракції. Конфлікт має показувати обидві сторони рівноправно,
   без презумпції правоти старої трійки.

## 10. Перший живий прогін (2026-10-02)

Два маленькі HR-документи з навмисною суперечністю між ними (`policy.md`: «чоловік не може
взяти декретну», «кожен працівник мусить підписати договір»; `faq.md`: «кожен користувач
може взяти декретну», «інтерн — працівник; інтерн не може підписати договір до 18 років»).

**Екстракція (LLM):**

- `gemma3:1b` — формат тримає, зміст ні: умову «якщо жінка» загубила (`user :: can :: take
  maternity leave`), «чоловік не може» пропустила, вигадала `man :: is_not :: employee` і
  `contractor :: is_a :: user`. Один рядок розбила на 4 частини (`sign :: employment contract`) —
  парсер тепер склеює хвіст.
- `qwen2.5-coder:7b` — правило «умова стає класом» виконала сама (`woman :: is_a :: user`,
  `woman :: can :: ...`), сама ж оголосила `man :: disjoint_with :: woman` і
  `contractor :: disjoint_with :: employee`. Журнал отримав рівно ту суперечність, що закладена
  в документах: `employee :: must :: sign the employment contract` НЕ ЗАПИСАНО, бо
  `intern :: is_a :: employee` + `intern :: cannot :: sign ...` — класичний випадок `refined`
  (умова «до 18 років»). Пара FAQ/політика про декретну дала лише YELLOW: жоден документ не
  каже, що чоловік — користувач, тож перетин `user`/`man` невідомий — коректно для відкритого світу.

**Обґрунтованість (Jev, рубрика `triple_grounded`), 9 трійок з відомою відповіддю:**

| Модель | Результат | Що ловить |
|---|---|---|
| `tev1:0.8b` | 5/9 | лише сторонні твердження (`work from home` 0.28); хибні на ту саму тему проходять (0.61–0.78) |
| `tev1:4b` | 8/9 | справжні 0.98–1.00, хибні 0.00–0.39; пропустила лише `man :: is_not :: employee` (0.72) |

**Висновки для v1:** екстракція потребує моделі ~7B, перевірка обґрунтованості — `tev1:4b`.
Порядок обробки має значення (`faq.md` іде раніше за `policy.md`, тож хибне загальне твердження
потрапило в базу першим) — саме тому журнал показує обидві сторони рівноправно, а `override`
дозволяє замінити раніше записане (§9.6).
