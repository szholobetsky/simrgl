**Пов'язані**: `CROSS_LAYER_TRANSFORMATION_EMBEDDINGS.md` (семантична половина тієї самої задачі, §9), `INCIDENCE.md`, `GAMAYUN.md`, `GLOSSARY.md`, `KEYWORD_ENTITY_MAPPING.md`, `COMPOSITIONAL_CODE_EMBEDDINGS.md`, `HEALTH_EVALUATION.md`, `JEV.md`

## 0. Коротко

**Магура** показує, як одна бізнес-сутність або одне поле проходить систему: звідки значення входить, як його перекладають, де зберігають, хто його читає і куди воно виходить. Наприклад:

- `weight` з KYC-пакета записується в БД, а далі ним ніхто не користується;
- `amount` з платежу через БД доходить до балансового звіту.

Таку задачу називають **лінією даних (data lineage) на рівні поля**. Відомі інструменти відповідають на неї двома способами:
- за метаданими ETL і SQL — на рівні таблиць і колонок (OpenLineage, DataHub, Atlas);
- статичним аналізом потоку даних — з AST, типами і збіркою проєкту (CodeQL, FlowDroid).

Магура робить це **без збірки, для будь-якої мови і з бізнес-словником**. Свідчення вона бере з того, що пантеон уже вміє індексувати:
- синтаксис карти (svitovyd);
- статистику коду та історії (gamayun);
- ембедінги (simargl);
- факти історії (mokosh);
- бізнес-терміни (глосарій).

Результат — **схема по шарах**: смуги шарів зліва направо, рядки — варіанти поля, стрілки — копія, перетворення або споживання. Біля кожної стрілки стоїть позначка, яким джерелом її знайдено. Висновок на кшталт «поле тільки записується» — це **кандидат для людини, а не вирок** (§10).

Магура — **структурна половина** задачі, яку `CROSS_LAYER_TRANSFORMATION_EMBEDDINGS.md` (CLTE, 2026-01) поставив семантично: як значення проходить UI → Service → Entity → DB і як такий шлях знайти за текстом задачі. CLTE моделював переходи між шарами як операції у просторі ембедингів, але не мав джерела самих шляхів: його екстрактор спирався на граф викликів і потоку даних, якого так і не побудували. Магура дає ці шляхи без збірки, а CLTE дає Магурі мости через перейменування, шар за ембедингом і пошук шляху за задачею (§9).

Ім'я: **Магура** — дочка Перуна, крилата діва-войовниця, що світиться в бою, вселяє надію і проводжає душі полеглих до вирію. Так само вона проводжає значення крізь усі шари системи: освітлює його шлях від входу до місця, де воно спочиває — у виході або в глухому куті ∅. Вирій тут не випадковий: проводжати є куди, бо в пантеоні вже є vyrii. Сама сутність у неї постає як *образ* — те, як річ виглядає в кожному місці, де її видно. Сутність одна, а образів у неї стільки, скільки шарів: ключ JSON, поле DTO, колонка, рядок звіту.

## 1. Задача на прикладах

### 1.1 KYC: зайве поле

Продюсер надсилає JSON: ім'я, рік народження, номер паспорта, вага. Система дзеркально пише все в БД.

```
json:weight → KycPacket.weight → KycMapper: user.setWeight(p.getWeight())
            → User.weight → users.weight (міграція) → UserRepository.save → ∅
```

`weight` трапляється в п'яти місцях, і в кожному лише визначається або переноситься. Споживання немає: ні умови, ні обчислення, ні звіту. Тож **вага — це надлишковість класу Користувач**. До того ж це персональні дані без мети обробки, а принцип мінімізації даних GDPR (ст. 5(1)(c)) таке забороняє.

Для порівняння `birthYear` проходить той самий конвеєр, але має гілку `AgeCheck: if (now - birthYear < 18)`. Тут поле споживається.

### 1.2 Платіж → баланс

```
json:amount → PaymentDto.amount → Payment.amount → payments.amount
            → LedgerService.post: entry.debit = payment.amount            (перетворення: amount → debit)
            → ledger.debit → SELECT SUM(debit) … GROUP BY account         (споживання в запиті)
            → BalanceSheet.total → templates/balance.html: {{ total }}    (вихід)
```

Значення тричі змінює ім'я (`amount` → `debit` → `total`). Лексичний пошук губить його на першому ж перейменуванні. Тому в Магури є стрілки «перетворення» і міст через simargl (§4).

### 1.3 GRN → від'ємний залишок (приклад CLTE)

```
GRNEditForm: quantity=50 → GRNService.updateGRNQuantity: delta = old_qty - new_qty
  → Inventory.adjustQuantity(delta): balance = balance + delta      (споживання без перевірки < 0)
  → UPDATE inventory SET balance = ? → INSERT INTO balance_snapshots
```

CLTE питав, як за текстом «редагування GRN дає від'ємний залишок» знайти цей шлях. Магура відповідає з іншого кінця: `magura back balance_snapshots.balance` показує всі входи, з яких складається залишок, і кожне споживання на шляху. Місце, де бракує перевірки, — це вузол споживання `balance + delta` без умови поруч. Обидві відповіді разом дають і шлях, і його збіг із задачею.

## 2. Сутність — це образ, а не ідентифікатор

Перший крок — зібрати **усі імена, під якими сутність живе в системі**. Кожне джерело дає свою частину:

| Джерело | Що дає | Приклад для «вага» |
|---|---|---|
| глосарій (`/flow glossary`) | бізнес-термін, синоніми, SEEN-місця в документах | `Вага (weight): маса тіла клієнта, кг` |
| gamayun (код) | `has_part`, `variant_of`, `same_as`, `related_to` | `ident:getWeight has_part term:weight`, `term:weight related_to term:passport` |
| svitovyd `keywords -f` | ідентифікатори, що містять частини слова | `weight`, `getWeight`, `WEIGHT_KG`, `weightValue` |
| simargl (код) | семантичні сусіди, яких лексика не бачить | `bodyMass`, `massKg`, `bmi` |
| mokosh (diff історії) | перейменування: у тому самому hunk видалено `weight` і додано `bodyMass` | `weight → bodyMass` у коміті X |
| конвенції | camelCase ↔ snake_case ↔ UPPER, JPA-імена колонок, ключі JSON | `birthYear` ↔ `birth_year` ↔ `BIRTH_YEAR` |

**Образ** — це множина пар (ім'я, свідчення). Людина може прибрати хибне ім'я або додати пропущене, і ця правка зберігається (§7).

## 3. Шари

Шар визначається без збірки, евристиками, які людина може перевизначити:

| Шар | Ознаки |
|---|---|
| Вхід (ingress) | контролери, обробники черг, `@PostMapping`, `@KafkaListener`, схеми JSON/Avro/OpenAPI |
| DTO / схема | класи з полями й без поведінки; `*Dto`, `*Request`, `*Packet`; файли `schema/` |
| Перетворення | `*Mapper`, `*Converter`, `*Assembler`; рядки, де ліва й права частини мають різні імена |
| Сутність | `@Entity`, ORM-моделі, `models.py` |
| Сховище | міграції, DDL, `*.sql`, `*Repository` |
| Запит | SELECT, JPQL, ORM-запити, `*Dao` |
| Логіка | сервіси, правила, перевірки: місця споживання |
| Вихід | відповідь API, шаблони звітів, експорт, i18n-підписи, логи |

Що ще допомагає визначати шар:
- **svitovyd:** напрям посилань (вхідні точки не мають вхідних `call`/`ref`), розширення файлів і шляхи;
- **gamayun:** `characterizes`, `anchor_of` (модуль, який характеризує термін).

- **simargl (за гіпотезою CLTE H3):** шари займають різні підпростори ембедингів. Тоді файл без явних ознак шляху можна віднести до шару за найближчим центроїдом шару в індексі simargl. Це перевіряється на тих самих даних (§9).

Шари записуються в `.magura/layers.yaml` як шаблони шляхів, і людина може їх виправити. Тут Магура повторює підхід health-square: шари — це місце в системі, а не стан коду (`HEALTH_EVALUATION.md`).

## 4. Згадки і стрілки

### 4.1 Вид кожної згадки (рівень рядка)

| Вид | Правило (лексичне) | Приклад |
|---|---|---|
| **визначення** | поле, колонка, параметр, ключ схеми | `private int weight;`, `weight INT` |
| **копія** | той самий корінь імені ліворуч і праворуч від присвоєння | `user.setWeight(p.getWeight())`, `INSERT … (weight) VALUES (:weight)` |
| **перетворення** | ліворуч інше ім'я або є обчислення | `entry.debit = payment.amount`, `kg = lb * 0.4536` |
| **споживання** | умова, арифметика, параметр з іншим іменем, `WHERE`/`SELECT`/`GROUP BY`, шаблон | `if (age < 18)`, `SUM(debit)`, `{{ total }}` |
| **вихід** | шаблон, відповідь API, експорт, лог | `{{ total }}`, `return ResponseEntity.ok(dto)` |
| **невідомо** | `SELECT *`, серіалізація всього об'єкта, рефлексія, generic-маппер | `objectMapper.writeValueAsString(user)` |

Рядок, який лексичне правило не може однозначно віднести до одного виду, потрапляє до jev як закрите питання: «чи цей рядок лише переносить значення поля X?» (`noul` з імовірністю). Рішення приймає Python за порогом, як в усьому пантеоні (`JEV.md`).

### 4.2 Стрілки між згадками

1. **Усередині рядка:** ім'я праворуч → ім'я ліворуч (копія або перетворення).
2. **Між файлами:** посилання svitovyd `call`/`ref`/`import` між символами, які містять згадки.
3. **Через БД:** запис колонки (`INSERT`, ORM-мапінг, міграція) → читання тієї самої колонки (`SELECT`, ORM-запит). Сховище стає вузлом, через який лінія проходить на інший бік системи.
4. **Мости simargl (пунктир):** якщо лінія обірвалась на перетворенні з новим ім'ям, simargl пропонує фрагменти коду, семантично близькі до обох кінців. Така пропозиція — це метрика CLTE «передбачення наступного вузла»: `embedding(вузол) + r_шар→шар ≈ embedding(наступний)`. Вектор переходу `r` навчається на лініях, які Магура вже знайшла лексично (§9). Такий міст має упевненість і потребує підтвердження людиною.
5. **Мости історії:** gamayun `co_changes_with` і mokosh-коміти, які змінювали обидва кінці разом. Це свідчення, що файли пов'язані тим самим полем.

## 5. Картинка

### 5.1 Основний вигляд: смуги шарів

```
            ВХІД          DTO               ПЕРЕТВОРЕННЯ        СУТНІСТЬ      СХОВИЩЕ          ЗАПИТ / ЛОГІКА           ВИХІД
weight      json:weight ─▶ KycPacket.weight ─▶ setWeight(getW…) ─▶ User.weight ─▶ users.weight ─▶ ∅  (тільки запис)
birthYear   json:birth… ─▶ KycPacket.birth… ─▶ setBirthYear(…)  ─▶ User.birth… ─▶ users.birth_ ─▶ ◆ AgeCheck <18 ──▶ KycReport.age
amount      json:amount ─▶ PaymentDto.amou… ─▶ ─ ─ debit = amount ─ ─▶ ledger.debit ─▶ ◆ SUM(debit)  ──▶ BalanceSheet.total
                                                (перетворення: ім'я змінилось)                                 ─▶ balance.html
```

Позначки:
- **─▶** копія;
- **─ ─▶** перетворення (нове ім'я);
- **◆** споживання;
- **∅** глухий кут;
- праве поле — вихід.

Колір стрілки показує джерело свідчення:
- S — svitovyd (синтаксис);
- G — gamayun (статистика);
- R — simargl (ембедінг);
- H — історія (mokosh, `co_changes_with`);
- Γ — глосарій.

Товщина стрілки — упевненість.

### 5.2 Взаємодія

- **Клік на вузол** відкриває рядок коду (як картка файла в svitovyd) і всі свідчення за ним.
- **Фільтр шарів і видів:** наприклад, «покажи тільки споживання».
- **Повзунок часу (історія):** коли з'явився кожен вузол і чи поле колись споживалось (споживання є в історії, а в сьогоднішньому коді вже ні).
- **Від сутності до сутностей:** клас `User` розгортається в рядки за всіма своїми полями. Глухі кути видно відразу, бо стовпчик ∅ стає списком надлишкових полів класу.
- **Від виходу назад:** клік на `BalanceSheet.total` показує, з яких вхідних полів він складається. Це зворотна лінія, `trace`, а не `deps`.

### 5.3 Другий вигляд: матриця «поле × шар»

Рядки — поля сутності, стовпці — шари, клітинки — вид згадки (·, ─, ◆, ▶). Цей вигляд для огляду цілого класу на одному екрані:

```
            вхід  DTO  map  entity  db   logic  out
name         ─     ─    ─     ─     ─     ◆     ▶
birthYear    ─     ─    ─     ─     ─     ◆     ▶
passportNo   ─     ─    ─     ─     ─     ◆     ·
weight       ─     ─    ─     ─     ─     ·     ·     ← тільки запис
```

## 6. На які питання відповідає

| Питання | Що шукаємо на схемі |
|---|---|
| Надлишкові поля (KYC-вага) | лінії, що закінчуються в сховищі без жодного ◆ |
| Поля-привиди | поле читається (◆ або вихід), але жоден вхід його не заповнює |
| Загублені на шляху | вхідне поле, лінія якого не доходить до сховища (не зберігається, хоча приймається) |
| Перейменування | ланцюг через ─ ─▶: `weight → bodyMass` |
| Розгалуження | куди потрапляє `amount`: баланс, податок, звіт, лог |
| Вплив зміни | змінюємо тип або сенс поля → які шари й файли зачепить |
| Карта персональних даних | де живуть PII, у які виходи вони потрапляють; основа для реєстру обробки (GDPR ст. 30) |
| Дрейф словника | бізнес-термін у глосарії ↔ імена в коді ↔ підписи у звіті (термін є в документах, але в коді не має образу, або навпаки) |

## 7. Архітектура

```
 глосарій ─┐
 svitovyd ─┤  (map.txt, keywords)       ┌──────────────┐
 gamayun  ─┼──────────────────────────▶ │    magura    │ ─▶ .magura/<entity>.json  (граф образу)
 simargl  ─┤  (code index: мости)       │ образ, шари, │ ─▶ magura ui (Flask, 8 тем, 6 мов)
 mokosh   ─┘  (diff: перейменування)    │ види, стрілки│ ─▶ MCP: magura trace <entity|field>
 jev      ──── (сумнівні рядки)         └──────────────┘
```

Принципи:
- **Магура нічого не збирає.** Вона читає індекси інших богів і сирці для класифікації рядків, а записує лише свої файли `.magura/`. Так само simargl читає тільки те, що записав mokosh.
- **svitovyd лишається картою.** Він не читає історію і не знає Магури. Класифікацію рядків може робити або сама Магура над сирцями, або індексатор svitovyd: «поле, рядок, вид» — це структура коду, тобто його роль. Це рішення приймемо після прототипу.
- **Правила ролей.** Багатоінструментна функція за правилом іде в simargl або alkonost. Магура — виняток з тієї самої причини, з якої з'явився gamayun: це окремий вид знання, а не сторінка в чужому UI. simargl і alkonost можуть показувати її схему в себе (як Triangulation збирає три інструменти).
- **Телефон.** Ядро Магури — Python без torch і без збірки, UI на Flask. Мости simargl працюють, коли є його індекс, а без нього схема лише бідніша.
- **Команди:**
  - `magura image <термін|поле>` — образ (§2);
  - `magura trace <поле>` — лінія вперед;
  - `magura back <вихід>` — лінія назад;
  - `magura dead <клас>` — глухі кути класу;
  - `magura ui`.
- **Правки людини** (`.magura/edits.yaml`): прибрати ім'я з образу, підтвердити міст, позначити поле «зберігається на вимогу регулятора». Наступний прогін їх застосовує.

## 8. Внесок кожного джерела

| Джерело | Шукає | Сліпа зона, яку закриває |
|---|---|---|
| svitovyd | згадки в рядках, посилання між файлами | основа схеми; без неї немає стрілок |
| gamayun (код) | у яких символах поле, з якими термінами ходить | `related_to` тільки з полями-сусідами = ознака копіювання; `used_in` дає символи |
| gamayun (історія) | термін у задачах; `co_changes_with` | чи поле взагалі потрібне комусь у задачах; зв'язки, яких немає в синтаксисі |
| simargl (код) | семантичні сусіди | перейменування, які губить лексика |
| simargl (історія) | задачі, що торкались поля | контекст «навіщо це поле додали» |
| mokosh | diff комітів | перейменування в історії; коли зник останній споживач |
| глосарій | бізнес-термін, визначення, синоніми | назва сутності людською мовою; виходи-підписи |
| jev | сумнівні рядки | рядки, які лексичне правило не віднесло до одного виду |

Висновок «тільки запис» сильний, коли незалежні свідчення збігаються:
- svitovyd: споживань 0;
- gamayun: `used_in` лише транспортні символи, `related_to` лише сусіди;
- simargl: жодного семантичного споживача поза конвеєром;
- історія: термін є тільки в задачі, що додала поле.

Це та сама логіка, що в тріангуляції exp10: кожне джерело сліпе по-своєму.

## 9. Зв'язок із CROSS_LAYER_TRANSFORMATION_EMBEDDINGS (CLTE)

CLTE і Магура відповідають на одне питання з різних боків. Порізно кожна з половин не працює, а разом вони замикають одна одну.

| | CLTE (семантика) | Магура (структура) |
|---|---|---|
| Що є шляхом | послідовність сутностей, з'єднаних переходами в просторі ембедингів | лінія згадок поля: визначення, копія, перетворення, споживання, вихід |
| Звідки беруться шляхи | граф викликів і потоку даних (javaparser/tree-sitter), **не побудований** | карта svitovyd, класифікація рядків, перехід через БД, без збірки |
| Шари | евристика шляхів + гіпотеза окремих підпросторів (H3) | шаблони шляхів, напрям посилань, `characterizes` |
| Головне питання | який шлях відповідає тексту задачі? | де значення входить, змінюється, споживається і виходить? |
| Слабке місце | немає шляхів і золотого стандарту; композиція накопичує похибку | губиться на перейменуванні; не бачить сенсу задачі |

### 9.1 Що Магура дає CLTE

- **Шляхи без збірки.** Лінії Магури — це реальні шляхи `[e_1, r_1, e_2, …]` з шаром кожного вузла і видом кожного переходу (копія, перетворення, споживання). CLTE більше не потрібен граф потоку даних, а його експерименти стають можливими на наших датасетах.
- **Обмежений набір кандидатів.** CLTE боявся «мільйонів можливих шляхів» (Challenge 4). Лінії полів — це скінченна множина, яку можна індексувати.
- **Типи переходів.** Замість абстрактних `calls/transforms/reads/writes` CLTE отримує шари на кінцях і вид переходу з рядка коду. Відповідно, вектор `r` навчається окремо для кожної пари (шар→шар, вид).
- **Золотий стандарт для навчання і перевірки.** Лексично знайдені лінії з копіями (той самий корінь імені на обох кінцях) майже безпомилкові. На них CLTE навчає вектори переходів, а перевіряє — на лініях з перейменуванням, де лексика безсила.

### 9.2 Що CLTE дає Магурі

- **Мости через перейменування** (§4.2 п.4) — передбачення наступного вузла (CLTE Metric 3).
- **Шар за ембедингом** (§3) — якщо гіпотеза підпросторів підтвердиться.
- **Від задачі до лінії.** CLTE Experiment 4 (top-K path retrieval) над лініями Магури: за текстом задачі знайти поля і шляхи, яких вона стосується. Це продовжує головне питання дисертації (задача → код) на рівні «задача → лінія даних».
- **Аналіз впливу і локалізація помилки** (CLTE Applications 1–2) — тепер над конкретними шляхами полів, а не над усіма можливими шляхами.

### 9.3 Що в CLTE варто переглянути

- Очікувані числа CLTE (`cos_sim > 0.7`, «скорочення часу локалізації на 30–50 %») — це гіпотези, а не результати. Вони перевіряються тільки на лініях Магури.
- `embedding(e_1) + Σ r_i ≈ embedding(задача)` — найсміливіша гіпотеза CLTE. Нам відомо (exp2, exp12), що ембединги задач і коду розходяться навіть без композиції. Тож її варто ставити після перевірки простішої: чи `r` хоча б передбачає наступний вузол лінії.
- Шар у тексті ембединга (`"[Service] …"`, CLTE Ablation 1) дешево перевірити на simargl-індексі коду.

## 10. Межі

- **Лексика, а не потік даних.** Магура бачить імена, а не значення. Поле, скопійоване в змінну з чужим іменем і передане далі, — це перетворення, яке треба зв'язати мостом.
- **Неявне читання** дає вид «невідомо», а не «копія»: `SELECT *`, серіалізація цілого об'єкта у відповідь, рефлексія, MapStruct/ModelMapper, ORM-конвенції, SQL у рядках, збережені процедури.
- **Межі репозиторію.** ETL, BI-звіти й інші сервіси поза репозиторієм не видно. Лінія, що виходить назовні (API, черга, експорт), позначається як вихід із невідомим споживачем.
- **Відсутність доводиться гірше за наявність.** Ембедінги завжди щось повертають, лексика пропускає синоніми. Тому вердикт «тільки запис» — це кандидат, а остаточне рішення приймає людина.
- **Регуляторні поля.** Поле може зберігатись, бо цього вимагає закон, а не логіка. Для цього є позначка в `edits.yaml`.

## 11. Перевірка (план експерименту)

1. **Демо-проєкт із закладеними відповідями:**
   - `weight` — тільки запис;
   - `birthYear` — споживається;
   - `bodyMass` — перейменування ваги у вихідному класі;
   - `amount → debit → total` — шлях до балансу;
   - поле-привид, яке читається у звіті, але не заповнюється входом.
   Мірило: яку частку закладених стрілок і висновків знайдено.
2. **Реальний бізнес-проєкт** з `datasets/bizprojects.csv`, наприклад fineract (кредити, баланси) або ofbiz. Людина вручну простежує 10–20 полів від API до звіту; це золотий стандарт. Мірила:
   - повнота стрілок (recall переходів між шарами);
   - точність висновків «тільки запис» і «привид»;
   - внесок кожного джерела (ablation: без simargl, без історії, без глосарію).
3. **Час і залізо:** CPU, без збірки, з малою моделлю тільки для jev.

4. **Експерименти CLTE над лініями Магури:**
   - передбачення наступного вузла (Metric 3, MRR) на лініях з перейменуванням;
   - розділення шарів у підпросторах (Experiment 3) на simargl-індексі коду;
   - top-K пошук лінії за текстом задачі з mokosh (Experiment 4).

Гіпотези:
- **H1.** Лексика (svitovyd) знаходить більшість переходів у дзеркальних конвеєрах.
- **H2.** Мости simargl і історії піднімають повноту на ланцюгах з перейменуванням.
- **H3.** `related_to` тільки з полями-сусідами відрізняє «копійовані» поля від «споживаних» без аналізу рядків.
- **H4 (з CLTE).** Вектор переходу `r`, навчений на лексично знайдених копіях, передбачає наступний вузол на лініях із перейменуванням краще за simargl без `r`.

## 12. Чим це нове

- **Лінія даних на рівні поля через усі шари коду (вхід → сховище → вихід) без збірки і для будь-якої мови.** Існуючі інструменти або працюють на рівні таблиць і колонок з метаданих ETL, або потребують AST, типів і компіляції однієї мови.
- **Сутність як образ:** бізнес-термін з глосарія, ідентифікатори коду, колонки, ключі JSON і підписи звітів зводяться в одну множину імен зі свідченнями.
- **Свідчення різної природи на одній схемі:** синтаксис, статистика коду та історії, ембедінги, факти комітів, судження jev. Кожна стрілка показує, звідки вона взялась (`INCIDENCE.md`: та сама таблиця «об'єкт × ознака», нове прочитання).
- **Структура і семантика однієї задачі:** лінії Магури стають шляхами і золотим стандартом для композиції ембедингів CLTE, а CLTE закриває лексичні розриви Магури.
- **Практичні наслідки:** надлишкові поля, поля-привиди, карта персональних даних — без ручного обходу коду.
