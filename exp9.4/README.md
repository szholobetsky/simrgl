# exp9.4 — пасивний пошук + супутники: 3 моделі × 10 задач, з часом і токенами

**Питання.** exp9.3 показав механізми на двох задачах. Чи тримаються вони на всіх 10 задачах
exp9.1, і скільки це коштує в часі й токенах? Три моделі різного класу:

| Модель | Клас | Де |
|---|---|---|
| qwen3:1.7b | найкраща мала модель exp9.3 (T05: 3/5) | локально, CPU |
| gemma4:e4b | 4b, «дослідник» | panteon, CPU |
| gpt-oss:20b | MoE 20b, говорить нативними tool calls | panteon, CPU |

## Сетап

Те саме, що в exp9.3 (`git worktree` кожної задачі на коміті до розв'язку, `exp9.3/idx.py` без витоку
відповіді, правильні файли `exp9.3/truth_9.1.json`), але кожна пара (модель, задача) — **одна сесія
1bcoder**, яка дає дві відповіді (`pipeline.txt`):

```
/ctx 8192 · /param num_ctx 8192 · temperature 0 · repeat_penalty 1.2 · repeat_last_n 256 · num_predict 4096
/read tasks/<id>.txt -> task
/run idx.py gamayun <id>          # індекси в контекст до першого ходу моделі
/run idx.py simargl <id>
/ask -t 10 print out list of the most relevant files for fix the task: {{task}}
/save output-<id>.txt             # 1. своя відповідь
/stats save json stats-ask-<id>.json
/run idx.py companions <id> output-<id>.txt     # 5 файлів, що змінювались разом з названими
<прохання: залиш свої файли, додай потрібних супутників, решту відкинь, надрукуй список>
/save review-<id>.txt             # 3. після перегляду
/stats save json stats-<id>.json
```

Третій варіант — **своя відповідь + 5 супутників, дописаних механічно** — рахується в `score.py` без моделі.
Час і токени розкладено на дві фази за статистикою самого 1bcoder (знімок після `/ask` і в кінці).

```
start.bat            # обидва драйвери: qwen3 тут, gemma4 + gpt-oss на panteon; готові пари пропускаються
python score.py      # -> out/score.md, out/score.json
```

## Результати

Дві мети пошуку — дві групи метрик. **Компас**: чи вказує система правильний напрям — перший названий файл
правильний або хоча б лежить там, де треба. Для людини, яка не знає код (підрядник), один впевнений правильний
файл — це вже більша частина локалізації. **Повнота**: чи знайдено всі файли, які зміна зачепила (метрика
exp2–exp9.2). Легкі задачі = T01 T02 T03 T04 T09 T10 (з буквальним якорем у тексті), складні = T05–T08.
Усі метрики — по топ-10 списку в порядку першої згадки (`score.py`).

(`server/sonar-web`, `sonar-core`…), що й правильний · MRR — 1 / позиція першого правильного файлу.

## Що з цього видно

**Компас і повнота розходяться.** Як компас gemma4:e4b сильніша за індекси (P@1 0.60 проти 0.50 у gamayun,
на складних задачах 4 з 4). За повнотою жодна модель не зібрала всі файли частіше, ніж gamayun без моделі
(усі знайдено: 0.10–0.20 проти 0.30; у Haiku — 0.70). Модель уміє вказати напрям, але не зібрати повний
список; повноту дають рейки — індекси і супутники.

**Найкращий компас у цьому експерименті — без LLM.** Правило «рідкісний якір → `grep`, інакше gamayun» має
P@1 0.70 за секунди (оптимістично, див. ‡), більше за будь-яку з трьох моделей. Якір і gamayun доповнюють
одне одного: на легких задачах gamayun влучає першим файлом рідко (0.17), а якір веде просто до файлу; на
складних якоря немає, а перший файл gamayun правильний у 4 з 4. Для малої моделі звідси роль **судді між
готовими кандидатами**, а не шукача: на T09 grep дає 6 файлів, правильний серед них, і вибрати, котрий із
шести справді надсилає заголовок, — коротке судження на малому контексті.

**Супутники — інструмент повноти, а не компаса.** У gemma4 recall@10 зростає з 0.30 до 0.45, на складних
задачах з 0.38 до 0.74; перший файл при цьому не змінюється.

1. **gemma4:e4b з супутниками — перша мала модель, яка разом з індексами перевершила індекси без моделі.**
   MAP 0.409 (механічно) і 0.378 (після перегляду) проти 0.345 у gamayun; на складних задачах після
   перегляду 0.569 проти 0.487 у gamayun і 0.188 у найкращої малої моделі exp9.2. Ціна — найдорожча з
   трьох: 18 хв на задачу, 206k токенів промпта; на T01, T04, T10 по 33–45k токенів дослідження дали 0.
2. **Механічні супутники ≥ перегляду моделлю** для qwen3:1.7b (0.212 проти 0.170) і gemma4 (0.409 проти
   0.378) — як і в exp9.3: моделі, вибираючи зі списку, відкидають частину правильних супутників.
   Перегляд помітно допоміг лише на складних задачах gemma4 (0.383 → 0.569).
3. **qwen3:1.7b — пасивна, дешева і сліпа на легких задачах.** 8 з 10 задач вона закрила одним викликом
   `/ask` за ~2–4 хв, але легкі задачі (буквальний якір у тексті) — усі нуль: вона не робить `find`/`grep`
   за очевидним словом, а вибирає з підказок індексів. Тут найкращою з малих лишається exp9.2 qwen3:4b
   (легкі 0.542), яка сама шукала.
4. **Супутники нічого не дають, коли своя відповідь порожня.** T01, T02, T04 — нуль у всіх трьох моделей
   у всіх варіантах: правильні файли (по 1–2) не потрапили ні в підказки індексів, ні в пошук моделі,
   а супутники будуються від того, що модель назвала.
5. **gpt-oss — головна недороблена частина харнесу.** Нативні виклики адаптер переписує (exp9.3), але
   після інструменту модель часто повертає порожню відповідь, і агент зупиняється. Окремо вона пише
   `python - <<'PY' ...` як у bash; на Windows під cmd heredoc не працює, а без stdin (виправлення exp9.3)
   команда повертає порожньо. Поки це не розібрано, gpt-oss в агенті 1bcoder недооцінена; там, де вона
   відповідає без агента (перегляд), вона на рівні qwen3:1.7b.

## Як ішов прогін

- **Перший старт (18:07)** — `repeat_penalty` лише для gpt-oss, як в exp9.3. qwen3:1.7b на T01 за 25 хв
  видала 207 рядків `ACTION:` в одній відповіді. Обидва драйвери зупинено, `repeat_penalty 1.2` — для всіх;
  ці спроби (gemma4 T01 без штрафу — 1506 с, зациклена qwen3 T01) лежать в `out_rp-default/`.
- **qwen3:1.7b T04 (19:08)** зациклилась навіть зі штрафом: 56 хв, вигадані `[tool result]` + `ACTION`
  по колу з 10 рядків. Штраф Ollama дивиться лише на останні `repeat_last_n` = 64 токени, цикл був довший.
  Додано `repeat_last_n 256` і `num_predict 4096`; лог — `out_rp-default/qwen3_1.7b_T04_loop-rp1.2/`.
  Обидва драйвери перезапущено з новим скриптом (panteon — після gemma4 T04). На вже пораховані пари це
  не впливає: у них максимум 4982 згенерованих токени за всю пару (≈ 400–1200 на виклик), до 4096 на
  одну відповідь далеко, і зациклень не було.
- Два драйвери одночасно дописують у `out/run.log`, кілька рядків старту загубились; на результати
  не впливає (`out/timing.csv`, `stats-*.json` у кожної пари свої).
