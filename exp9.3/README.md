# exp9.3 — пасивний пошук: індекси шукають, мала модель судить

**Питання.** Чи може мала локальна модель (0.8–9b, CPU, 4–8k контексту) знайти файли для
задачі, якщо пошук за неї роблять індекси? В exp9.2 індекси лежали в моделі «на полиці»
як інструменти, і малі моделі ними не користувались: щоб покликати індекс, модель мусить
знати, що шукати, а саме цього їй і бракує. Теза exp9.3: **замінити намір моделі зв'язками
індексів.** gamayun і simargl запускаються на тексті задачі до першого ходу моделі, їхній
вивід потрапляє в контекст, а модель лише вирішує, що з цього прочитати й що назвати.

Це не окремий харнес, як в exp9.2, а справжній **1bcoder**: headless-скрипт `/script`
з агентом `/ask`. Тобто міряється продукт, яким користуються, а не лабораторна модель продукту.

## Сетап

**Задачі.** T09 і T05 з exp9.1 (той самий код до розв'язку: `git worktree` для кожної задачі
в `C:\Projects\Data\wt\sonar\T??`, ті самі правильні відповіді `truth_9.1.json`).

| | Задача | Чому вона |
|---|---|---|
| **T09** (легка) | *Remove no more used Sonar-Version HTTP header* | буквальний якір: `find "Sonar-Version" -c` одразу дає всі 4 правильні файли |
| **T05** (складна) | *Project creation form validation is buggy* | якоря немає; в exp9.2 усі малі моделі на ній отримали 0. Правильні: `ManualProjectCreate.tsx`, `.css`, тест, снепшот тесту, `core.properties` |

**Скрипт** `passive.txt`, один запуск 1bcoder на пару (модель, задача), з теки checkout задачі:

```
/ctx {{ctx}}
/param num_ctx {{ctx}}
/param temperature 0
/param repeat_penalty 1.2        # додано для gpt-oss; решта моделей рахувалась без цього рядка
/param timeout 900
/param run_timeout 300
/read C:/Projects/simrgl/exp9.3/tasks/{{id}}.txt -> task
/run python C:/Projects/simrgl/exp9.3/idx.py gamayun {{id}}
/run python C:/Projects/simrgl/exp9.3/idx.py simargl {{id}}
/ask -t 10 print out list of the most relevant files for fix the task: {{task}}
/save C:/Projects/simrgl/exp9.3/out/{{tag}}/output-{{id}}.txt
/ctx save exp9.3-{{tag}}-{{id}}
/stats save json C:/Projects/simrgl/exp9.3/out/{{tag}}/stats-{{id}}.json
```

**`idx.py`** — тонка обгортка над gamayun і simargl, тільки для експерименту (у продукті
скрипт кличе `gamayun search` / `simargl search` напряму, див. `TaskIndexSearch.txt` нижче):
1. **без витоку відповіді**: індекс simargl побудований з усіх задач, тож на текст T05 він першою
   знайшов би саму T05 (перевірено: `SONAR-12360` з оцінкою 0.848). Обгортка кличе `exp9/tools.py`,
   який вирізає відкладені задачі; gamayun бере онтологію exp7, побудовану без них;
2. **без лапок у shell**: тексти задач містять `"`, переноси й `#`, тому в командний рядок іде лише id,
   текст береться з `tasks/<id>.txt`;
3. **короткий вивід**: 8 файлів gamayun зі словами-доказами + 4 схожі задачі simargl по 5 файлів,
   ~1.3k токенів на обидва — щоб лишилось місце агентові в 4k.

**Запуск і оцінка.**
```
start.bat              # локальні моделі (localhost:11434), пропускає вже пораховані пари
start_panteon.bat      # більші моделі: модель на panteon, індекси й 1bcoder тут
python score.py truth_9.1.json
```
`score.py` бере з `output-<id>.txt` шляхи (повний шлях або однозначне ім'я файлу в цьому checkout)
у порядку першої згадки і рахує скільки правильних у топ-10 та AP; час — з `out/timing.csv`
(уся сесія 1bcoder: індекси + агент), токени — зі статистики самого 1bcoder (`/stats save json`).
Окремо рахуються «індекси без моделі»: списки gamayun і simargl так, як їх бачить модель.

## Гіпотези і що з ними сталося

**1. Пасивний старт замінює намір моделі.** *Частково підтверджено.* На T05, де без підказки малі
моделі в exp9.2 мали 0, тут qwen3:1.7b назвала 3 з 5 (AP 0.60) — удвічі краще за найкращий з індексів
(simargl 0.28) і найкращий результат експерименту на цій задачі. jamba 2/5, gemma4:e4b 2/5,
qwen2.5-coder:7b 2/5. Модель не шукала: вона вибрала з того, що дали індекси, і поставила правильне першим.
Але на T09, де індекси промахнулись (0/4), пасивний старт моделям не допоміг — і навіть завадив:
у exp9.2 tev1:4b сам зробив `find "Sonar-Version"` і отримав 4/4, а тут більшість малих моделей
одразу відповідала зі списку індексів, не перевіряючи. **Пасивність допомагає, коли зв'язки влучають,
і шкодить, коли промахуються: у малої моделі немає рефлексу перевірити очевидне.**

**2. Розмір моделі визначає стиль, а не лише якість.** *Спостереження.* До ~3b моделі роблять
**один** виклик LLM: прочитали вивід індексів — і відповіли (колонка «викликів»). Від 4b
(nemotron, ornith, qwen3.6, tev1:4b) моделі досліджують: 4–10 викликів, десятки тисяч токенів,
читання файлів. Дослідження допомагає на T09 (усі «дослідники» мають 2/4 через власний `find`)
і шкодить на T05: ornith:9b пішов за схожою задачею про фільтр дат, прочитав `DateInput.tsx`
шматками в 13 читаннях і вичерпав 10 ходів без відповіді (0/5 при 53k токенів промпта).
qwen3:1.7b на тій самій T05 витратила 1.5k токенів промпта і отримала 3/5.

**3. Супутники за історією змін підтягують пропущене.** *Підтверджено на T05.* Те, що моделі
систематично пропускають — `.css`, снепшот, тест, `core.properties` поруч з обраним `.tsx` — це
не слова задачі, а файли, що змінюються разом. Кожна відповідь з ≥ 1 правильним файлом після
5 супутників доходить до 3–4 з 5. Звідси нова команда `gamayun companions` і крок перевірки в
`TaskIndexSearch.txt`.

**4. Онтологія коду (`gamayun --files`) як повторна перевірка.** *Не підтверджено.*
`gamayun search --project sonar-code` на тексті T05 + ключових словах: 80 с на запит, 0/5 у топ-10
(переважно Java IT-тести бекенду, притягнуті словами `manual`, `projectkey`). Онтологія коду рахує
збіг слів у визначеннях і не знає, що змінюється разом — для перевірки списку файлів вона слабша
за co-change з історії.

**5. Модель «живе інше життя» в різних харнесах.** *Знайдено конкретний механізм.*
gpt-oss:20b і lfm2.5:8b не дали жодної відповіді: у логах довгі змістовні роздуми (gpt-oss
в роздумах склала правдоподібний список з `ManualProjectCreate.tsx`), а потім порожня відповідь.
Гіпотеза — ці моделі дотреновані на нативний tool calling і видають дію в `message.tool_calls`,
а 1bcoder читав лише текст. **Підтверджено.** З адаптером, що переписує нативний виклик у `ACTION:`,
gpt-oss на T09 зробила два пошуки (`Sonar-Version`, потім `setHeader("Sonar-Version"`) і дала
найкращу відповідь експерименту: 4 з 4 на перших місцях, AP 1.0, з поясненням до кожного файлу.
«Німа» модель стала найкращою на легкій задачі. Перший прогін з адаптером зупинився на другому
ході порожньою відповіддю; з `repeat_penalty 1.2` цього вже не було — найімовірніше, модель тоді
теж пішла в повтор (сирої відповіді того ходу не збережено).
Далі виявились наступні шари того самого розриву: модель пише так, як у bash — `bash -lc sed -n
'1,200p' файл`, `grep -R ... | head` — і 1bcoder мав це зрозуміти (баги 14–16).
Ширше: протокол `ACTION:` зроблений для gemma3:1b (1b модель не розставить дужки JSON, а рядок
`ACTION:` напише), і саме тому великі моделі в ньому «плутаються». Числа цього експерименту
міряють «модель + 1bcoder», а не модель саму по собі.

**6. temperature 0.** *Не перевірено, але є підозра.* Я поставив `temperature 0` для відтворюваності
(як в exp9.2). Для малих моделей жадібне декодування схильне до циклів: tev1:0.8b повторив
`-k sonar-webserver-core` сотні разів (6.6k згенерованих токенів на обох задачах). Розробники
моделей рекомендують інший семплінг (для Qwen3: 0.7 / top_p 0.8 / top_k 20). Наступний прогін —
без `/param temperature 0`, по 2–3 повтори на пару.

## Чому прогонів було так багато

Більшість перезапусків — це не експеримент, а дефекти 1bcoder і харнесу, знайдені тим, що
headless-скрипт уперше пройшов шлях «індекси → агент → файл» від початку до кінця. Усі виправлені
в `C:\Projects\1bcoder` (234 тести, нові в `tests/test_script_context.py`, `test_colors.py`,
`test_tool_calls.py`, `test_grep.py`) і в `C:\Projects\gamayun`:

| # | Що сталося | Причина | Виправлення |
|---|---|---|---|
| 1 | вивід `/run gamayun` не доходив до агента | у `/script apply -y` 16 команд не писали в контекст: перевірка була на `_auto_apply`, який `-y` вмикає так само, як агент | контекст пропускається лише всередині агента (`_in_agent`) |
| 2 | `/read f -> var` клав у змінну «context: injected…», а файл — у контекст | `/read` не знав про захоплення | при `-> var` змінна отримує текст файлу, контекст не чіпається |
| 3 | перший рядок скрипту йшов моделі як чат | BOM у файлі, збереженому PowerShell | скрипти читаються як `utf-8-sig` |
| 4 | скрипт питав `task = ?`, хоча сам задає `task` через `-> task` | попередній збір параметрів не знав про захоплення | ключі, що захоплюються кроком скрипту, не питаються |

## Висновки

1. **Пасивний старт дає малій моделі шанс на складній задачі.** Найкращий результат на T05 —
   у qwen3:1.7b (1.7b параметрів, 1 виклик LLM, 156 с на CPU), а не в 9b–35b моделях. Для
   1bcoder це аргумент на користь його головної ідеї: підготовку роблять офлайн-інструменти,
   модель лише ділиться ерудицією.
2. **Але пасивність має бути перевіреною.** Коли зв'язки промахуються (T09), мала модель не перевіряє
   їх власним `find`. Ланцюжок має містити перевірку, яка не залежить від ініціативи моделі.
3. **Супутники з історії змін — дешева перевірка без LLM**, яка закриває саме ту прогалину, що
   повторюється в усіх моделей (тести, стилі, снепшоти, повідомлення поруч з обраним файлом).
   Онтологія коду для цього не підходить.
4. **Великі моделі в протоколі `ACTION:` не розкриваються, частина просто «німа».** Адаптер нативних
   викликів зробив з «німої» gpt-oss:20b найкращу модель на T09 (4/4, AP 1.0) — не змінивши протоколу
   для 1b моделей. Моделі приносять із собою звички bash (`grep`, `sed -n`, `cat`), і харнес, який
   їх розуміє (`/grep`, переклад читань у `/read`), отримує модель такою, якою її дотренували.
   Наступний крок — подавати історію викликів у нативному форматі для моделей, що його вміють
   (Ollama `/api/show` → `capabilities: tools`).
5. **Для 1b моделей рішення треба звузити ще більше.** gemma3:1b отримала 0 навіть у пасивному режимі:
   на відкрите «print out list of the most relevant files» вона повторила рядок контексту. Наступна
   перевірка — бінарне питання на кожного кандидата у свіжому контексті:
   `/loop last split:line --jev "Does this file need to change for the task: …?" --keep pass`.

## Продукт: `TaskIndexSearch.txt`

Те саме, що `passive.txt`, але для власних задач: `C:\Projects\1bcoder\_bcoder_data\scripts\TaskIndexSearch.txt`.
Кличе справжні `gamayun search` і `simargl search` (без `idx.py`: нових задач в індексі ще немає),
питає модель про ключові слова, запускає `/ask` і, з `ontology_check=Y`, перевіряє відповідь
супутниками (`gamayun companions`) і просить модель переглянути список.

```
/script run TaskIndexSearch.txt project=sonar index=default ontology_check=Y task="..."
1bcoder --scriptapply TaskIndexSearch.txt --param project=sonar --param index=default --param ontology_check=Y --param task="..." --model qwen3:1.7b
```

key contains spaces»* (qwen3:1.7b, 6 хв): модель обрала `ManualProjectCreate.tsx`, `ProjectKeyInput.tsx`,
`constants.ts`; супутники додали снепшот `ProjectKeyInput`, `CreateProjectPage.tsx` і `core.properties`
